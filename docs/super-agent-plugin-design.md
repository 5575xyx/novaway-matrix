## 0. 先把「super-agent」定义清楚

### 0.1 它不是什么

「super-agent」不是「更强的单体 agent」，也不是「更大的模型 + 更多工具」。这些是**能力**的提升，不是**运行时**的提升。

一个 200K 上下文的 agent 仍然只能做一件事：收到一条用户消息，跑一轮 ReAct，返回。它的时间尺度是「一次请求」。

### 0.2 它是什么

> **super-agent 是一个常驻的、事件驱动的、多线程的运行时。它把「一次对话」升级成「一批持续推进的目标」。**

具体到可判定的**七个**特征：

| #   | 特征           | 判据（做没做到）                                                                                   |
| --- | -------------- | -------------------------------------------------------------------------------------------------- |
| 1   | **事件驱动**   | 用户不说话时，系统也会因为定时/外部事件/子任务完成而主动推进                                       |
| 2   | **多线程**     | 同时存在多个长生命周期目标，各自独立推进、共享记忆、互不串味                                       |
| 3   | **双路径分流** | 程序层（Fast）筛掉多数噪音，语义层（Slow）才判「要不要行动」；不是所有输入都烧一次全量 prefill     |
| 4   | **订阅直通**   | 已有人认领的 Thread 再来消息，直接投给订阅者，不经过 Router；Router 只负责新任务冷启动与跨任务协调 |
| 5   | **全双工**     | 长任务执行中仍可追加指令、改约束、喊停；不需要等上一轮跑完                                         |
| 6   | **会话淡化**   | 用户看到的是线程与目标，不是 Session 列表；Session 是内部实现                                      |
| 7   | **有监督**     | 卡住能被发现并处理（nudge → replan → abort），而不是「永远在思考」                                 |

反过来，缺少任意一条，就只是「一个带定时器的 chatbot」。

**第 4 条特别容易做错**：这里的「直通」是 **Thread → 订阅它的 Worker**，不是 Worker 之间互相开会。Worker 之间**不需要通信**——真要交换信息，交换的是产物（artifact / PR / 文件），不是对话。让两个 Worker 互发消息，等于把上下文耦合从「同一 Thread 内」扩散到「Worker 之间」，收益是零，代价是审计不了。

**第 6 条是产品要求，不是技术洁癖**：人的注意力上限大约 3–5 个并行任务（这是 DSH 观察到的、也与团队实际经验一致）。所以 UI 默认只突出 3–5 个活跃线程，其余折叠归档；`maxActiveThreads` 默认不能设成 50——那等于没有线程模型，只是把 Session 列表换了个名字。

### 0.3 与「万物皆插件」的关系

两件事解决的是**互相垂直**的问题：

```
                 万物皆插件（横向）               super-agent（纵向）
                 ─────────────────                ─────────────────
回答的问题        能力从哪来                        能力在什么时候、被谁、为了什么被调用
失败形态          加一个能力要改内核                 系统很强但不会自己动
验收方式          D1–D9：只加文件就生效              S1–S10：不说话时它在推进
共同底座          PluginHost / 贡献注册表 / KernelApi
```

**关键：super-agent 的每一层自己也是插件化对象。** 触发器、路由策略、Worker 类型、监督规则、通知通道，都必须是贡献点。否则做完 super-agent，内核会多出第二套硬编码，正好抵消掉前面的工作。

这一点决定了本文的写法：先讲运行时，再在 §12 把每一层映射回插件贡献点。

### 0.4 现状盘点（真实代码）

NovaWay 不是从零开始。已经有的资产比想象中多，缺的是把它们串成一个运行时。

| super-agent 要素 | 现有资产                                                  | 位置                                                            | 差距                                                                               |
| ---------------- | --------------------------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 定时触发         | `cron` 服务                                               | `src/cron/{cron,service,tasks}.ts`                              | 只有 cron，没有事件/条件/文件/Webhook                                              |
| 外部事件等待     | `monitor`、`subscribe`                                    | `src/tool/{monitor,subscribe}.ts`、`src/background/watchers.ts` | 是**工具**（模型主动调用），不是**触发器**（系统自己监听）                         |
| 后台任务         | `background/job.ts`、`resume.ts`                          | 可恢复、可重启                                                  | 只有「跑命令」一种类型                                                             |
| 子代理           | `task`、`task_status`、`agent_message`                    | `src/tool/task.ts`、`agent_message.ts`                          | 有地址、可续聊，但**父会话必须醒着**                                               |
| 团队             | `team/*`、`mailbox.ts`、共享任务板                        | 生产级设计见 `docs/ai-team-orchestration-design.md`             | 绑定一次 run，不是常驻组织                                                         |
| 工作流           | `dynamic-workflow/*`                                      | 见 `docs/dynamic-workflow-plan.md`                              | 一次性 run，不是常驻线程                                                           |
| 上下文压缩       | `compaction.ts`、`tool-budget.ts`、`stream-watchdog.ts`   | 已有 microcompact 与溢出处理                                    | 没有跨线程的记忆分层                                                               |
| 事件总线         | `bus/*`、`BusEvent.define`                                | 有类型化事件                                                    | 事件不驱动 agent，只驱动 UI                                                        |
| 编排 Agent       | `coordinator`（`agent.ts`）                               | 只委派、不写码                                                  | 是**一个 Agent**，不是一个运行时                                                   |
| 半双工续跑       | `watchers.ts` 的 idle-session resume                      | 有                                                              | 只服务 monitor/subscribe 两种任务                                                  |
| Agent Loop       | `session/prompt.ts` 的 `loop()` / `cancel()` / `resume()` | 有取消与恢复                                                    | **`prompt()` 同步返回**，一轮跑完才回；执行中无法追加指令（无 `start()`/`stop()`） |
| 流保护           | `stream-watchdog.ts`                                      | 只做流级超时                                                    | 没有「有输出但无进展」的判据                                                       |

**结论：NovaWay 现在是一个「很强的单线程 agent，带若干可恢复的后台任务」。** 差的是三件事：

1. 把「后台任务完成 → 唤醒 → 继续推进」从两个工具的私有实现，升级成运行时的一等公民；
2. 把 `prompt()` 从「同步等结果」改成「`start()` 立刻返回、`stop()` 随时中止」的全双工；
3. 在流级超时之上，加「是否真的在推进」的判据。

### 0.5 与现有几种做法的区别

「多开 Session」「用 /loop 轮询」「Agent Team」都是常见替代方案。它们的差别不是实现精粗，而是**是否解决了「人的注意力」这个真正的瓶颈**。

| 做法                           | 能并行 | 上下文连续           | 事件驱动  | 用户负担           | 本质问题                                           |
| ------------------------------ | ------ | -------------------- | --------- | ------------------ | -------------------------------------------------- |
| 手动多开 Session               | ✅     | ❌                   | ❌        | 高：3–5 个就到极限 | 人在做调度                                         |
| `/loop` 定时轮询               | ✅     | ✅                   | ❌ 是轮询 | 中                 | 空转烧钱、噪音大                                   |
| Agent Team（Team Lead 管细节） | ✅     | 团队内 ✅，跨团队 ❌ | ❌        | 中                 | Team Lead 也要理解细节，等于把注意力问题下移了一层 |
| **Super-agent**                | ✅     | ✅                   | ✅        | 低：只看结论       | —                                                  |

三者的关键区别：

- **`/loop` 是「我以为有事，去看看」**，Super-agent 是「有事才叫我」。前者成本随频率线性增长，后者随事件数增长。这是 G1 存在的意义。
- **Agent Team 是「团队内部编排」**，Super-agent 是「跨任务调度」。两者不冲突：Worker 内部完全可以是一个 Team（DSH 原文明确说了这点）。
- **手动多开会话**失败的根本原因不在工具，在人的注意力上限。所以解决方向不是「让 Session 列表更好用」，而是「让 Session 从用户视野里消失」。

**由此得出两条产品约束**（后面会反复用到）：

1. **Session 必须被淡化**：用户看到的是线程与目标。任何要求用户「切到第 4 个 Session 看看」的设计，都等于没有做 super-agent。
2. **主动动作必须可见可撤销**：用户越少盯着，就越需要能事后追溯「它替我做了什么」。所以每个主动动作都要有记录、有理由、能一键撤销。

## 1. 验收标准（先写验收，再写设计）

沿用插件文档的写法：验收是演练，不是功能清单。任何一条需要改内核文件才算通过，就不算通过。

### 1.1 十项演练

| 编号    | 演练                                                    | 必须生效                                                                                       | 禁止改动                                                                       |
| ------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **S1**  | 用户关掉页面，2 小时后回来                              | 期间定时器触发过 3 次，每次都有实际动作（检查/推进/记录），回来后能看到完整线程时间线与结论    | 无（纯运行期）                                                                 |
| **S2**  | 同一句「继续」在 3 个线程里各自生效                     | 三个线程分别基于**自己的**上下文推进，互不污染；各自产出可区分                                 | 无                                                                             |
| **S3**  | 加一个触发器插件（`fs.watch` 某目录）                   | 文件变化后自动开启/推进一个线程；不重启进程                                                    | `src/cron/*`、`src/background/*`、`src/session/prompt.ts`                      |
| **S4**  | 加一个路由策略插件（「带 `#fast` 前缀的消息不调 LLM」） | 该前缀消息由代码直接处理并返回，token 消耗为 0；其余消息不受影响                               | `src/session/prompt.ts`、`src/tool/registry.ts`                                |
| **S5**  | Thread 已被某个 Worker 订阅，再来一条新消息             | 程序直接投给订阅者并唤醒它；Router 不参与该链路；发布者不阻塞                                  | `src/tool/agent_message.ts`、`src/team/mailbox.ts`、`src/superagent/router.ts` |
| **S6**  | 一个线程卡死（工具挂起 / 反复失败）                     | Watchdog 在 N 分钟内识别，按策略 nudge → replan → abort；其他线程不受影响                      | `src/session/stream-watchdog.ts`、`src/session/prompt.ts`                      |
| **S7**  | 线程跨进程重启（杀进程再拉起）                          | 线程状态、待办、等待中的事件全部恢复；未完成的工具调用有明确结论（replayed 或 abandoned）      | 无                                                                             |
| **S8**  | 停用所有 super-agent 插件                               | 退化为现在的单线程对话；不报错、不残留定时器                                                   | 任何 `builtin.*`                                                               |
| **S9**  | 长任务执行中追加指令、改约束、喊停                      | 追加的指令在**不打断当前工具**的前提下进入下一段；`stop()` 在 200ms 内生效；不需要等上一轮跑完 | `src/session/prompt.ts` 之外的任何文件（该文件本身要允许被改造，见 §6.5）      |
| **S10** | 向 Watchdog 询问「这个线程为什么卡住」                  | 返回结构化诊断（卡在哪一步、重复了什么错误、建议动作），并且诊断能被开发者追问                 | 任何源码（只有 `/plugin/diagnostics` 与诊断查询 API 属于既有接口）             |

### 1.2 三项硬门禁

| 门禁            | 判定方式                                                                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **G1 空闲成本** | 空闲 1 小时（10 个活跃线程、无事件）的后台 CPU 时间 < 30s、token 消耗为 0。**这是一条占空比约束（<0.83%），不是时长约束**：更短的测量窗口按比例取阈值，见 §15.2 |
| **G2 唤醒延迟** | 事件发生到线程开始推进 < 2s（P95）；冷启动恢复 < 10s                                                                                                            |
| **G3 隔离**     | 任一线程崩溃/超预算/被中止，不影响其他线程；错误只出现在该线程                                                                                                  |

### 1.3 什么不算通过

- 用 cron 定时给模型发「请检查一下」让它自己回复 —— 这是**轮询**，不是事件驱动，G1 会直接失败。
- 把线程实现成「多个 session」但没有共享记忆与租约 —— S2 会因上下文串味失败。
- Watchdog 只看「有没有输出」 —— S6 里「一直有输出但没进展」的线程会被漏判。
- 用一个 Router 中转所有消息 —— S5 失败，且线程数一多就会排队。
- 让 Worker 之间互发消息来「协作」—— 这不是 DSH 的直通。直通是 Thread→订阅者；Worker 之间交换的是产物，不是对话（§0.2 第 4 条）。
- 用 `while (true) { sleep(5000); check() }` 实现「保活」—— 进程活着不等于任务在推进，S6/G1 都会失败。

## 2. 目标架构

### 2.1 五层

```
┌───────────────────────────────────────────────────────────────────────┐
│ ⑤ Watchdog        监督：进度判据、卡住识别、升级动作                     │
├───────────────────────────────────────────────────────────────────────┤
│ ④ Router          分流：fast/slow、订阅直通、拥堵批处理、投机执行        │
├───────────────────────────────────────────────────────────────────────┤
│ ③ Worker          执行：inline task / background job / team / workflow  │
├───────────────────────────────────────────────────────────────────────┤
│ ② Thread          目标：长生命周期、独立上下文、可等待、可恢复            │
├───────────────────────────────────────────────────────────────────────┤
│ ① Trigger         驱动：timer / event / webhook / fs / git / condition  │
└───────────────────────────────────────────────────────────────────────┘
        ▲                                                    ▲
        └────────── 全部以插件贡献点实现（§12）───────────────┘
```

**数据流向**（正常路径）：

```
Trigger 命中
  → 生成事件（去重/合并）
  → Router.fastPath(event)  ── 命中 ──► 确定性处理（0 token）──► 写 event
  │
  └─ 未命中
       → Router.pick(event) → ThreadID（新建 or 复用）
       → Thread.enqueue(event)
       → Thread 调度 Worker（inline / background / team / workflow）
       → Worker 产出 → Thread 记录 → 可能触发下游 Trigger
```

**关键设计：Trigger 不直接调 Worker。** 中间必须经过 Thread，否则就退化成「事件一来就跑一次」，没有状态、没有去重、没有优先级，也无法等待多件事再一起决策。

### 2.2 与现有 Session 的关系

Thread 不是 Session 的替代品，是它的**上一层**：

| 概念       | 时间尺度 | 持久化                                | 上下文                 |
| ---------- | -------- | ------------------------------------- | ---------------------- |
| Thread     | 天/周    | `thread` 表                           | 目标 + 长期记忆 + 待办 |
| Session    | 小时     | `session` 表（已有）                  | 对话消息               |
| Worker run | 分钟     | `background job` / `team run`（已有） | 任务提示               |

一个 Thread 在生命周期内会产生**多个** Session（每次推进一段，上下文超了就新开一个并携带摘要）。这样两个现有机制都保留：

- `session/compaction.ts` 继续负责单次 Session 内的压缩；
- Thread 层只负责「这个 Session 该带什么进上下文」（§4.4）。

不改成「一个 Thread 一个超长 Session」，因为那会让上下文管理退回到全量重放。

### 2.3 新增的内核服务

| 服务            | 文件                         | 职责                                                     |
| --------------- | ---------------------------- | -------------------------------------------------------- |
| `TriggerEngine` | `src/superagent/trigger.ts`  | 注册触发器、接收事件、去重、合并、节流、派发给 Router    |
| `ThreadManager` | `src/superagent/thread.ts`   | 线程 CRUD、状态机、租约、上下文装配、事件队列            |
| `Router`        | `src/superagent/router.ts`   | fast/slow 判定、线程选择、订阅直通、拥堵批处理、投机执行 |
| `WorkerPool`    | `src/superagent/worker.ts`   | 统一封装 task/background/team/workflow 四种执行体        |
| `Watchdog`      | `src/superagent/watchdog.ts` | 三层进度判据、卡住检测、升级动作                         |
| `SuperAgentApi` | `src/superagent/api.ts`      | 对插件暴露的统一接口（KernelApi 的一部分）               |

数据表：`thread`、`thread_event`、`thread_turn`、`thread_lease`、`trigger_state`。

### 2.4 一条 Trigger 的完整生命周期

这是本文后续所有章节的骨架。DSH 把一条任务从「发现」到「处理」拆成四段，缺任何一段都会在真实流量下出问题：

```
① 事件过滤          ② 事件路由          ③ 上下文组织         ④ 提前行动
   Filter             Route              Context             Speculate
   ────────           ─────              ───────             ─────────
   程序层 Fast        归到哪条 Thread     装配 L0–L5          只读投机
   语义层 Slow        是否要新建           Inline / Spill        （可选）
   去重/白名单        直通 or 冷启动        链式召回 ID
      │                  │                    │                    │
      ▼                  ▼                    ▼                    ▼
    §3.3,§5.2          §5.3,§5.4            §4.4,§4.5,§4.6       §5.6
```

| 阶段       | 核心问题                    | 失败的后果                         |
| ---------- | --------------------------- | ---------------------------------- |
| ① 过滤     | 这条消息值得让 Agent 介入吗 | 噪音全部烧 token，G1 挂            |
| ② 路由     | 它属于哪条线，谁已经在管    | 上下文串味，两个线程各自做矛盾决策 |
| ③ 组织     | 该带多少上下文进窗口        | 带多了稀释注意力，带少了反复读文件 |
| ④ 提前行动 | 能不能在用户开口前就准备好  | 变慢（但不影响正确性）             |

注意 ④ 是**可选的性能项**，①②③ 是**必选**。实现时可以先把 ④ 关掉。

## 3. TriggerEngine：让它自己动起来

### 3.1 为什么现在是「模型主动看」，要改成「系统主动叫」

现有 `monitor` / `subscribe` 的工作方式：模型调用工具 → 创建后台任务 → 任务完成时**唤醒当前会话**（`background/watchers.ts` 的 idle-session resume）。这是正确的，但有一个前提：**模型必须先想到要看**。

super-agent 的要求相反：**注册一次，之后一直看**。模型不需要在场。

| 维度     | monitor/subscribe（现有） | Trigger（目标）                     |
| -------- | ------------------------- | ----------------------------------- |
| 谁发起   | 模型                      | 用户配置 / 插件                     |
| 生命周期 | 跟随会话                  | 跟随线程或全局                      |
| 数量     | 几十个上限                | 上千个（需要索引与调度）            |
| 失败语义 | 通知模型                  | 进 `trigger_state`，按策略重试/告警 |
| 存在形式 | 工具调用                  | 插件贡献 `contributes.triggers`     |

`monitor` / `subscribe` 保留，作为「模型想临时看一眼」的手段；它们创建的 job 同时会被包装成一个临时 Trigger（§13.1），这样两条路径共用同一套调度与限流。

### 3.2 触发器类型

```ts
type TriggerContribution = {
  id: string
  kind: "timer" | "event" | "webhook" | "fs" | "git" | "condition" | "custom"
  /** 触发器自己的配置 schema，用于生成设置界面 */
  config?: JSONSchema7
  /** 纯函数：判断这个原始信号是否值得唤醒线程。必须快、必须无副作用。 */
  match(input: TriggerInput): boolean | Promise<boolean>
  /** 可选：把原始信号转成标准事件 */
  normalize?(input: TriggerInput): TriggerEvent | TriggerEvent[]
  /** 该触发器产生的线程解析规则（默认见 §3.5） */
  thread?: { mode: "new" | "reuse" | "broadcast"; key?: string }
}
```

| kind        | 输入                                                     | 典型用法                              |
| ----------- | -------------------------------------------------------- | ------------------------------------- |
| `timer`     | `{ at?: number; cron?: string }`                         | 每天 9 点复盘、每 30 分钟巡检         |
| `event`     | 总线事件 `{ type, properties }`                          | 任务完成、CI 状态、其他插件事件       |
| `webhook`   | `{ method, path, headers, body }`                        | GitHub 推送、Slack 消息、外部系统回调 |
| `fs`        | `{ path, change: "add" \| "change" \| "unlink" }`        | 监听日志目录、产物目录                |
| `git`       | `{ repo, ref, event: "push" \| "commit" \| "conflict" }` | 分支变动后自动审查                    |
| `condition` | `{ expression, every }`                                  | 「任务板上有超过 2 个 blocked」       |
| `custom`    | 插件自定义                                               | MQ 消费、数据库变更订阅               |

### 3.3 Fast path：先写代码，再想模型

这是 super-agent 与「定时给模型发消息」最本质的区别。每个事件进入 Router 前，先过一遍**确定性过滤器**：

```ts
type FastPathRule = {
  id: string
  /** 匹配原始事件 */
  when: (event: TriggerEvent) => boolean
  /** 命中后的确定性处理；返回 handled 表示不进入 LLM */
  handle: (event: TriggerEvent, ctx: FastPathContext) => Promise<FastPathResult>
  /** 处理失败时是否升级到 slow path */
  escalateOnError?: boolean
}

type FastPathResult = { handled: true; summary: string } | { handled: false }
```

内置规则（默认开启，代码实现，不消耗 token）：

| 规则           | 行为                                                |
| -------------- | --------------------------------------------------- |
| 事件去重       | 5 秒内相同 `(triggerID, dedupeKey)` 只处理一次      |
| 已知失败重放   | 连续 3 次相同错误 → 直接记 `known_issue`，不叫模型  |
| 心跳/空变更    | `monitor` 输出与上次完全一致 → 记一条 event，不唤醒 |
| 预算耗尽       | 线程已超预算 → 直接拒绝并通知，不进 LLM             |
| 明确的机械动作 | 例如「文件新增」且配置了固定动作（归档/移到某目录） |

**Fast path 是插件贡献点**（S4 验收的就是这个）。这样「哪些事情不值得叫模型」可以由团队/用户自己定义，而不是写死在内核。

预期效果：S1 里 2 小时的定时触发，如果都是「检查后无变化」，token 消耗应为 0，只有状态行记录。这就是 G1 能过的原因。

### 3.4 去重、合并与节流

事件风暴是必然的（一次 `git push` 可能触发 20 个文件变更、5 个 webhook）。规则：

| 机制   | 规则                                                                               |
| ------ | ---------------------------------------------------------------------------------- |
| 去重键 | `triggerID + dedupeKey`（默认由插件提供，缺省用事件内容的哈希）                    |
| 窗口   | 默认 5s；插件可配置；窗口内只保留**最后一条**并计数                                |
| 合并   | 同一线程在 `coalesceWindow`（默认 30s）内的事件合并成一个 prompt，附带全部原始事件 |
| 节流   | 每线程同时最多 1 个 turn 在跑；期间到达的事件进队列，按优先级排序                  |
| 丢弃   | 队列超过 `maxQueue`（默认 20）时丢弃最旧的 `low` 优先级事件并记一条 `overflow`     |

**拥堵时批处理**（Router 侧，§5.5）：当同时有 > N 个线程要推进时，Router 合并成一次 LLM 调用（多线程摘要 + 分别决策），而不是 N 次调用。这是成本与延迟的关键。

### 3.5 事件到线程的映射

| 模式        | 规则                                             | 例子                                 |
| ----------- | ------------------------------------------------ | ------------------------------------ |
| `new`       | 每个事件新建线程                                 | 每天一个新的巡检线程                 |
| `reuse`     | 按 `key`（默认 `triggerID`）找活跃线程，有则投递 | 「监控这个目录」系列事件都进同一线程 |
| `broadcast` | 投递给所有订阅该触发器的活跃线程                 | 「全公司公告」级别的变化             |

默认 `reuse`：绝大多数触发器应该积累上下文，而不是每次都从零开始。

### 3.6 插件贡献

```jsonc
{
  "triggers": [
    {
      "id": "watch-build",
      "kind": "fs",
      "entry": "./triggers/watch-build.js",
      "thread": { "mode": "reuse", "key": "build" },
    },
  ],
}
```

`activationEvents` 增加 `onTrigger:<id>`：触发器声明是 eager 的（要注册监听），但 `match`/`normalize` 的实现可以 lazy——第一次命中时再 import。

## 4. ThreadManager：把「一次对话」变成「一个目标」

### 4.1 Thread 是什么

> **一个 Thread = 一串相关的 Trigger + 一个持续存在的目标 + 它自己的上下文 + 它的待办 + 它的历史。**

DSH 的定义更简洁：**一条 Trigger 是一个点，一串相关的 Trigger 连成一条线，这条线就是 Thread。** 这个定义比「一个目标」更可操作，因为它直接给出了「新消息该进哪个 Thread」的判据——看来源标识（§5.3），不看语义。

举例：

| Thread 的来源 | 一条 Trigger     | 串成线                              |
| ------------- | ---------------- | ----------------------------------- |
| GitHub PR     | 一次 review 评论 | 同一个 PR 下的所有评论/推送/CI 结果 |
| 邮件          | 一封新邮件       | 同一 `thread-id` 下的全部往来       |
| IM 话题       | 一条群消息       | 同一话题（`thread_ts`）下的全部消息 |
| 定时巡检      | 一次 9:00 触发   | 每天 9:00 的触发（goal-anchored）   |

三条 Thread 可能是同一件事的三个侧面，也可能是三件并行的事——**这不重要**。重要的是一个 Worker 可以同时订阅多条 Thread，而 Thread 之间不需要知道彼此存在。

用户能看见的东西是「线程列表」：每个线程有标题、状态、最后活动时间、当前在干什么。模型能看见的东西是「这个线程的上下文」：目标、约束、已知事实、待办、最近发生的事。

现在的 `session` 相当于「一次推进」，Thread 是「很多次推进的容器」。

### 4.2 数据结构

```ts
type Thread = {
  id: string
  title: string
  /** 线程级目标，用户可编辑；进上下文的第一段 */
  goal: string
  /** 来源键：新消息靠它归到这条线（§5.3）。定时线程用 timer:<triggerID>。 */
  sourceKey: string
  /** 来源类型，用于 UI 图标与策略 */
  origin: "pr" | "mail" | "im" | "ci" | "timer" | "manual" | "plugin"
  /** 还没被任何 Worker 认领时为 undefined（§5.4 冷启动） */
  ownerWorkerID?: string
  /** 长期约束：用户说过的「不要动 prod」「预算 50 元」之类 */
  constraints: string[]
  status: "open" | "running" | "waiting" | "paused" | "done" | "failed" | "aborted"
  /** 当前正在跑的那个 turn（没有则 null） */
  activeTurn?: string
  /** 线程绑定的项目/工作目录，用于隔离 */
  cwd?: string
  /** 线程预算 */
  budget?: { tokens?: number; cost?: number; wallClockMs?: number }
  /** 已消耗 */
  usage: { tokens: number; cost: number }
  /** 该线程订阅的触发器 */
  triggers: string[]
  /** 最近的 session（上下文续接点） */
  lastSessionID?: string
  createdAt: number
  updatedAt: number
}
```

```ts
type ThreadEvent = {
  id: string
  threadID: string
  kind: "trigger" | "user" | "worker" | "watchdog" | "system"
  priority: "high" | "normal" | "low"
  payload: unknown
  /** 消费后置位；未消费事件是恢复的关键 */
  consumedAt?: number
  createdAt: number
}
```

```ts
type ThreadTurn = {
  id: string
  threadID: string
  /** 本次推进用的是哪个 session */
  sessionID: string
  reason: string // "trigger:watch-build" / "user" / "worker:abc"
  startedAt: number
  endedAt?: number
  outcome?: "progress" | "no-progress" | "blocked" | "failed" | "aborted"
  /** 这次推进的产出摘要，写进线程记忆 */
  summary?: string
  /** 进度判据的可观测事实（§7.2），outcome 由它算出来，不是模型说的 */

    blockersCleared?: number
    artifactsAdded?: number
    memoriesWritten?: number
    planChanged?: boolean
  }

```

### 4.3 状态机与租约

```
open ──enqueue──► running ──turn结束──► waiting ──event──► running
  │                  │                     │
  │                  ├──需要人──► paused ───┘（用户回答后继续）
  │                  ├──目标达成──► done
  │                  └──失败超限──► failed
  └──用户中止──────────────────────► aborted
```

**租约（lease）是并发正确性的核心**：

- 同一线程同一时刻只允许一个 turn 运行（单写者）。租约记在 `thread_lease`，带 `owner` 与 `expiresAt`。
- 进程崩溃后租约自然过期（默认 60s），恢复逻辑可以接管。
- 租约存在时投递的事件**只入队不执行**，避免两个进程同时推进同一线程。
- 这是 S2（三个线程互不污染）和 S7（重启恢复）能同时成立的前提。

**为什么不允许多个 turn 并行改同一线程**：Thread 的上下文是「读-改-写」的，两个 turn 并行会出现「基于同一份旧上下文各自做了矛盾的决定」。需要并行时，用多个 Thread 或 Worker（§6）。

### 4.4 上下文装配

每次开启新 Session 时，ThreadManager 按固定顺序装配上下文。**顺序固定、内容分层**，否则同一线程两次推进的提示会不一致（与插件文档 §4.2.1 的确定性要求同源）。

| 层            | 内容                                         | 预算占比 | 来源               |
| ------------- | -------------------------------------------- | -------- | ------------------ |
| L0 目标       | `goal` + `constraints`                       | 5%       | thread 表          |
| L1 长期记忆   | 精选笔记（不超过 N 条，按重要性×新鲜度排序） | 15%      | `thread_memory` 表 |
| L2 近期摘要   | 最近 K 个 turn 的 `summary`（每 turn 一行）  | 20%      | `thread_turn`      |
| L3 待办与阻塞 | 未完成项、被阻塞项、等待中的事件             | 10%      | thread 待办        |
| L4 当前事件   | 本次触发的事件原文                           | 10%      | `thread_event`     |
| L5 留白       | 给工具结果与推理                             | 40%      | —                  |

规则：

- L1/L2 是**摘要**，不是原文；原文在存储里，需要时用 ID 读回（§4.5、§4.6）。
- 任何一层超预算都按「最旧先丢、丢完标 `truncated`」处理，不静默截断内容。
- 装配结果可缓存：`(threadID, generation)` 为键，事件消费或记忆变更时代数 +1。

### 4.5 Inline & Spill（工作台与档案柜）

长任务最常见的问题不是「上下文不够」，而是「工具结果把上下文塞满了」。做法：

| 策略       | 规则                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------- |
| **Inline** | 小结果（< `inlineBytes`，默认 4KB）直接进对话                                                       |
| **Spill**  | 大结果写入 `thread_artifact`，对话里只留 `{ artifactID, 一行摘要, 大小 }`                           |
| **召回**   | 模型看到 artifactID 后可以用 `artifact_read(id)` / `artifact_search(query)` 读回片段（结构见 §4.6） |

这样做的收益：一次 `grep` 出 5000 行不会再吃掉半条上下文，而模型仍然能按需取回。

`session/tool-budget.ts` 已经做了「从新到旧保留、旧的替换成 stub」；这里把它从「丢内容」升级成「丢内容但保留句柄」——**丢弃必须可召回，否则就是有损压缩**。

**这一步对模型能力有硬要求，不能假设它自动生效**：OS 的缺页换入由硬件与内核处理，程序无感知；LLM 没有这个机制。东西被 spill 之后，模型必须自己意识到「我这儿还有一个引用」，再主动调 `artifact_read` 读回来。读不读、读多少，全靠它判断。

三条工程对策：

1. **spill 时给足线索**：不只是 `{ id, size }`，还要有一行具体摘要（`"grep: 37 matches in 12 files, top: src/auth/*.ts"`）。摘要质量决定模型会不会想起来去读。
2. **写进系统提示，而不是指望自觉**：「大结果已 spill，需要细节时调 `artifact_read`」必须显式说明。
3. **能力门槛**：弱模型在 spill 上的表现会显著退化（该读的不读，导致反复重做）。所以内置线程模板默认配强模型；诊断里记录 `artifact_read` 命中率，低到一定程度说明该调高 spill 阈值。

这与社区讨论里的判断一致：这套上下文替换**高度依赖模型**。设计上不能假设「所有模型都能用好 spill」。

### 4.6 链式召回（Chain of Recall）

Inline & Spill 解决「窗口里放什么」，链式召回解决「放不下之后怎么找回来」。做法很轻：**给所有对象编 ID，注入时顺手带上下一跳的 ID**，于是底层连成一张引用图。

```
群里有人问：「昨天那个登录问题修得怎么样了？」
                │
        消息上挂着 threadID = #42
                ▼
   Thread #42 ──owner──► Worker W-7
                │
        W-7 状态里挂着 prThread = #88
                ▼
   Thread #88（PR）──artifacts──► 修改记录 / CI 结果
```

Router 手上只有一条群消息，但顺着链能查到「改了哪个文件、测试过没过、卡在哪」。**靠的不是一个巨大的记忆库，而是一张能实时渲染的地图。**

实现约束：

| 要求               | 说明                                                                            |
| ------------------ | ------------------------------------------------------------------------------- |
| ID 必须稳定        | Thread / Turn / Worker / Artifact / Session 全部用不可复用的 ID                 |
| 引用必须双向可查   | 存 `parentID` 之外还要建反向索引（`artifact.thread_id`、`thread.owner_worker`） |
| 注入时带 ID 不展开 | 上下文里只写 `[thread:#42] [pr:#88]`，不把内容拉进来；需要时再调工具            |
| 深度受限           | 默认最多展开 2 跳，防止「顺着链把整个仓库读进来」                               |
| 每跳重校验权限     | 不能因为「从上一条链过来」就获得额外权限                                        |

与记忆检索的分工：记忆检索是**语义相似**，链式召回是**结构可达**。语义检索找「相关但无关联」的东西，链式召回找「确有关联但字面不相似」的东西。**不要把链式召回实现成向量检索**，那样就丢了「确定可查」这个核心价值。

### 4.7 用户插入与接管

用户可以在任意时刻往线程里说话（这就是「插入」）：

| 用户动作   | 语义                                                                                    |
| ---------- | --------------------------------------------------------------------------------------- |
| 普通消息   | 作为 `high` 优先级事件入队；若线程在 running，**不打断当前 turn**，下一个 turn 优先处理 |
| 「立刻停」 | 中止当前 turn，进入 `paused`，用户消息成为下个 turn 的起点                              |
| 改目标     | 更新 `goal`，代数 +1，后续上下文重装配                                                  |
| 回答确认   | 解除 `paused`，事件带答案入队                                                           |

**不打断当前 turn 是刻意的**：打断会让工具执行到一半被丢弃，产生「到底改没改」的不确定性——这正是 `docs/ai-team-orchestration-design.md` §8.5 强调的崩溃恢复问题。

## 5. Router：分流、直通与投机

### 5.1 分工：Router 只做两件事

这是整篇文章里最容易被误读、也最容易实现跑偏的一点。DSH 的 Router **不是 Planner**：

| 常见误解                          | DSH 的实际设计                                                                        |
| --------------------------------- | ------------------------------------------------------------------------------------- |
| Router 负责拆解任务、制定执行计划 | **Router 只做分拣与协调**；拆解与计划在 Worker 内完成（Worker 自己可以是 Agent Team） |
| Router 要用最强模型               | Router **可以用轻量模型**（因为它只做判断「归谁管」，不做推理）                       |
| 所有消息都过 Router               | **只有新任务冷启动与跨任务协调**才过 Router；已有 Thread 的消息直通订阅者             |

落到 NovaWay 的职责划分：

| 职责                   | 归属                                | 说明                                       |
| ---------------------- | ----------------------------------- | ------------------------------------------ |
| 要不要行动（triaged）  | Fast path 代码 → Slow path 轻量模型 | 见 §5.2                                    |
| 这条消息归哪个 Thread  | 程序（来源 ID / 订阅表）            | 见 §5.3、§5.4                              |
| 该不该新建 Thread      | Router（冷启动）                    | 唯一需要 Router 做判断的地方               |
| 跨 Thread 的冲突与汇总 | Router                              | 例如两个线程要改同一个文件                 |
| 计划和拆解             | Worker                              | Worker 内部可以是单个 agent，也可以是 team |
| 执行                   | Worker                              | 强模型                                     |

一句话：**Router 是分拣机 + 调度台，不是大脑。** 如果实现时发现 Router 的提示词越来越长、开始出现「第一步第二步」，那是把 Planner 塞进去了，应该挪到 Worker。

### 5.2 双路径判定（Fast → Slow → 直通）

判定分三层，顺序不能颠倒：

```
输入事件
  │
  ├─ ① 程序层（Fast Path）：确定性规则，0 token
  │     · 去重命中 → 丢弃
  │     · 白名单（心跳、纯状态同步）→ 只记录
  │     · 机械动作已配置（归档、移动、格式化）→ 直接执行
  │     · 预算耗尽 / 线程已暂停 → 拒绝并通知
  │     命中即结束，不进 ②
  │
  ├─ ② 语义层（Slow Path）：轻量模型判「要不要行动」
  │     输入：事件原文 + 该 Thread 的一句话摘要 + 策略提示词
  │     输出：{ act: boolean, reason, targetThread? }
  │     act=false → 记录并结束（不创建 turn）
  │
  └─ ③ 路由层
        · 事件已属于某 Thread 且该 Thread 有订阅者 → 直投订阅者（不进 Router）
        · 否则 → Router 冷启动：新建 Thread / 认领给某个 Worker
```

**② 是必要的，不能省。** 只有程序层过滤时，一条「看起来像任务」的闲聊会直接建线程烧钱；只有语义层时，每条群消息都要过一次 LLM，G1 必挂。DSH 的两层降噪正是这个分工，缺一层都会在真实流量下暴露。

② 的实现约束：

- 用**轻量模型**（Router 档），不用 Worker 档模型；
- 输入必须短：事件原文 + Thread 一句话摘要 + 策略；不带完整历史；
- 输出必须是**结构化判据**（`act` / `reason` / `targetThread`），不是自由文本；
- 判定结果与理由写进 `router_decision`，用户能查「为什么这条消息没被处理」；
- 判定器本身是**插件贡献点**（`RoutingPolicyRegistry`），团队可以按自己的流量特征调策略。

规则来源：内核默认 + 插件贡献（§12）。判定过程记进 `router_decision` 日志，便于回答「为什么这条消息烧了 token」。

### 5.3 选哪个线程（只在新任务时发生）

优先级从高到低，第一个命中即用：

1. 事件显式携带 `threadID`
2. **来源键命中**（`thread.source_key`，如 `github:pr:123`、`mail:<thread-id>`、`im:<topic-id>`）
3. 用户当前正在看的线程（UI 上下文）
4. 触发器声明的 `thread.mode = reuse` 且找到匹配线程
5. 新建线程

第 2 条是解决「新消息怎么关联到旧线程」的**唯一可靠方式**。它靠的是外部系统自带的标识，不是语义推理：

| 来源      | 来源键                                  |
| --------- | --------------------------------------- |
| GitHub PR | `github:pr:<owner>/<repo>#<number>`     |
| 邮件      | `mail:<message-id 所属的 thread-id>`    |
| IM 话题   | `im:<channel>/<thread_ts>`              |
| CI 运行   | `ci:<repo>:<workflow>`                  |
| 定时巡检  | `timer:<triggerID>`（即 goal-anchored） |

**不做的**：不把「语义相似」当作线程选择依据。曾经有过「用向量相似度把消息路由到最像的线程」的方案，问题是一个错误路由会让两个线程的上下文互相污染，且用户看不出发生了什么。宁可新建一个线程，也不要投错。

来源键缺失时（例如手写 webhook、没有稳定 ID 的系统），退化为「同触发器 + 时间窗内最近活跃」；再不行就新建。**插件作者有责任提供来源键**，manifest 校验时对 `kind: "webhook" | "git"` 但 `thread.key` 为空的触发器给出 warning。

### 5.4 订阅直通（Thread → Worker）

现有 Worker 通信要走 `agent_message` → mailbox → 目标会话，目标会话**必须醒着**才能读到。super-agent 的直通解决的是另一件事：**Thread 已经有主人了，后续消息不必再问 Router。**

```
第一次：Thread #42 出现
  → Fast/Slow 判定 act=true
  → Router 冷启动：新建 Worker W，W 订阅 Thread #42

后续：Thread #42 再来 20 条消息
  → Fast/Slow 判定
  → act=true 且 Thread 有订阅者 → 直接投给 W   （Router 完全不参与）
```

这是 DSH 原文里明确的设计：「将 Fast / Slow Path 过滤之后的消息直接路由了，全局 Router 层仅负责新任务的冷启动与跨任务协调」。

| 概念        | 语义                                                                      |
| ----------- | ------------------------------------------------------------------------- |
| subscribe   | Worker 订阅一个 Thread（一个 Thread 可有多个订阅者，如「主执行 + 审查」） |
| direct-pass | 投递不经过 Router，只做权限、去重、预算检查                               |
| 冷启动      | 没有订阅者时才找 Router                                                   |

实现要点：

- 订阅关系存在 `thread_subscription`（`thread_id + subscriber_id`），内存里有索引。
- 投递是**异步且不阻塞**的：发布者不等待订阅者处理（S5 要求发布者不阻塞）。
- 订阅者没醒着也能收：投递写成 `thread_event`，线程下个 turn 处理——这就是「半双工续跑」（`watchers.ts` 的 idle-session resume）的通用化。
- **Worker 之间的通信不在这个机制里**。两个 Worker 要交换信息，走产物（artifact / 文件 / PR），不走消息。原因见 §0.2 第 4 条：Worker 互发消息会把上下文耦合扩散到全局，且无法审计。
- 权限：只有同一团队/同一线程树内的订阅生效，防止跨项目窃听。

这条链路是 `team/mailbox.ts` 的**补充**，不是替代——Team 的「指令/报告」语义（见 team 设计 §1.2 的修正）继续用 mailbox；super-agent 的订阅用于**事件流**（新消息到达、产物更新），两者不要混。

### 5.5 拥堵时批处理

当同时有 > `batchThreshold`（默认 4）个线程要推进：

| 做法           | 说明                                                          |
| -------------- | ------------------------------------------------------------- |
| 合并为一次调用 | 一次请求里带多个线程的摘要 + 各自待处理事件，模型分别给出决策 |
| 结果按线程拆回 | 每条决策写回对应线程，触发各自的 Worker                       |
| 上限           | 单次最多合并 8 个线程；超出分批                               |

为什么有效：一次请求的固定开销（系统提示、工具块、缓存重建）被摊薄。这是 G1（空闲成本）与并发时的成本主因。

风险：合并会让单次请求变大，一旦超时就全部重来。所以：

- 合并请求不包含工具执行，只做**决策**（要不要推进、推什么），工具仍在各线程内执行；
- 合并请求失败时降级为逐个处理。

### 5.6 投机执行

「投机」= 在还不确定要不要的时候先做一部分，确定不要了就丢弃。

适用的三种场景：

| 场景              | 投机内容                      | 丢弃条件             |
| ----------------- | ----------------------------- | -------------------- |
| 触发器可能命中    | 预读相关文件/日志尾部         | `match()` 返回 false |
| 线程可能继续      | 预取上下文（装配好的 prompt） | 该线程本轮没被选中   |
| 路由可能选 A 或 B | 两个候选线程的上下文都预装配  | 只用一个             |

实现约束（很重要）：

- **只投机只读操作**。任何写操作、任何有副作用的工具调用，禁止投机。
- 投机结果带 `generation`，代数不符直接丢弃。
- 投机有独立预算（默认不超过线程预算的 5%）。
- 投机失败不影响主路径，只记一条 debug。

**这一条是「性能优化」不是「功能」**，允许在性能不达标时关闭；关闭后系统仍然正确。

## 6. Worker：四种执行体的统一接口

### 6.1 为什么需要统一

现在有四种「干活的东西」，接口各不相同：

| 执行体         | 现有实现             | 特点                       |
| -------------- | -------------------- | -------------------------- |
| inline task    | `tool/task.ts`       | 子会话，父会话等结果       |
| background job | `background/job.ts`  | 可恢复的进程/HTTP          |
| team run       | `team/*`             | 多人协作、共享任务板、预算 |
| workflow run   | `dynamic-workflow/*` | 脚本编排、可恢复           |

Thread 需要把它们一视同仁地「启动、等、发消息、停」。

### 6.2 统一接口

```ts
type WorkerHandle = {
  id: string
  type: "task" | "background" | "team" | "workflow"
  /** 启动；返回时表示已受理，不代表完成 */
  start(): Promise<void>
  /** 全双工：向运行中的 Worker 追加输入 */
  send(input: { text: string; meta?: unknown }): Promise<void>
  /** 等待到下一次产出（可能是中间进度） */
  next(): Promise<WorkerUpdate>
  /** 停止；返回是否干净结束 */
  stop(reason?: string): Promise<{ clean: boolean; partial?: string }>
}

type WorkerUpdate =
  | { kind: "progress"; summary: string; artifactID?: string }
  | { kind: "message"; text: string }
  | { kind: "done"; summary: string; result?: unknown }
  | { kind: "error"; error: PluginError; retryable: boolean }
```

`send()` 是关键：现在的 `task` 只能「等它跑完」，不能中途追加约束。有了 `send()`，「Worker 跑到一半用户改主意」不需要中止重来。

### 6.3 交接（handoff）

线程推进常常需要「换个人接着干」。交接规则：

| 情况                    | 做法                                                           |
| ----------------------- | -------------------------------------------------------------- |
| 同一 Worker 继续        | `send()`，保留其上下文（最省）                                 |
| 换 Worker，保留上下文   | 生成交接包：目标、已完成、已知事实、未决问题、文件清单         |
| 换 Worker，不保留上下文 | 只给目标与验收标准（用于「换条路重试」，避免锚定在失败路径上） |

交接包的结构是**结构化字段**，不是一段自然语言摘要——否则「模型总结模型」会稳定地丢失关键约束。

### 6.4 失败与重试语义

| 失败类型            | 重试             | 升级                     |
| ------------------- | ---------------- | ------------------------ |
| `timeout`           | 1 次（相同参数） | 换 Worker                |
| `capability_denied` | 不重试           | 询问用户（权限确认）     |
| `tool_unavailable`  | 不重试           | 跳过该工具，继续（降级） |
| `provider error`    | 3 次（指数退避） | 换模型 / 通知            |
| 反复相同错误        | 不重试           | 记 `known_issue`，转人工 |

**重试次数是线程级预算的一部分**：一个线程总重试次数超限后，无论什么错误都直接 `failed`，避免「无限重试烧钱」。

### 6.5 全双工：`start()` / `stop()`

这是现有架构最硬的一处改动。现在 `SessionPrompt.prompt()` 同步返回一个 `MessageV2.WithParts`——调用方必须等整轮跑完。所谓「用户能在执行中追加指令」目前并不成立：`cancel()` 是中止，不是插入。

目标接口（对应 S9）：

```ts
interface SessionRun {
  readonly id: string
  /** 立刻返回，不等执行 */
  start(): Promise<void>
  /** 追加指令：不打断正在执行的工具，在下一个安全点插入 */
  inject(input: { text: string; priority?: "user" | "system" }): Promise<void>
  /** 中止：软停（跑完当前工具）与硬停（立即 abort） */
  stop(input?: { hard?: boolean }): Promise<void>
  /** 事件流：文本增量、工具开始/结束、tokens、结束原因 */
  events(): AsyncIterable<SessionEvent>
}

interface Interface {
  // 保留现有同步语义，供内部一次性调用
  readonly prompt: (input: PromptInput) => Effect.Effect<MessageV2.WithParts, Image.Error>
  // 新增全双工
  readonly begin: (input: PromptInput) => Effect.Effect<SessionRun>
  readonly cancel: (sessionID: SessionID) => Effect.Effect<void>
}
```

**安全点（safe point）定义**：一个工具调用结束、下一个工具调用开始之前。`inject()` 的内容在这里被插入成一条 user 消息，模型在下一段推理里就能看到。**不要**在工具执行中途插入——那会让工具看到半截指令，产生不可复现的行为。

**与 `abortSignal` 的关系**：现有 `prompt.ts` 已有 `options.abortSignal`（第 1363 行传进 LLM 请求），`stop({ hard: true })` 直接复用它；`stop({ hard: false })` 则只设置一个「本轮不再发起新工具调用」的标记，等当前工具自然结束。软停是默认——硬停会丢弃工具结果（§4.7 的「不打断」原则）。

**为什么不能靠「多开几个 Session」绕过**：同一线程两个 Session 并行推进，会基于同一份旧上下文各自做矛盾决策（§4.3）。全双工必须在**同一 turn 内**实现，不是并发多 turn。

## 7. Watchdog：判断「是不是真的在推进」

### 7.1 三层监督

现有 `session/stream-watchdog.ts` 只解决第一层：流没有 chunk 就超时。super-agent 需要三层。

| 层         | 关注                   | 判据                                   | 现有                    |
| ---------- | ---------------------- | -------------------------------------- | ----------------------- |
| **流级**   | SSE 是否还活着         | 空闲超过 90s 且没有进行中的工具        | ✅ `stream-watchdog.ts` |
| **轮级**   | 这一轮是否有进展       | 本轮的产出与上轮相比是否**推进了目标** | ❌                      |
| **线程级** | 这个目标是否还值得继续 | 最近 N 轮是否都是 `no-progress`        | ❌                      |

### 7.2 进度判据（关键）

「有输出」不等于「有进展」。一个线程可以每轮都输出 2000 字，但目标一步没动。判据必须来自**可观测事实**，不能来自模型自评：

| 事实                                  | 来源                         | 权重 |
| ------------------------------------- | ---------------------------- | ---- |
| 待办完成数增加                        | 线程待办表                   | 高   |
| 阻塞项减少                            | 阻塞表                       | 高   |
| 产出物新增/变更（文件、artifact、PR） | 工具调用结果                 | 高   |
| 新事实写入长期记忆                    | `thread_memory`              | 中   |
| 决策变化（换了方案、缩小了范围）      | turn 的 `summary` 结构化字段 | 中   |
| 只是复述/解释/读文件                  | 无对应事实                   | 零   |

**实现方式**：每个 turn 结束时，由 `ThreadTurn.outcome` 写入，判定逻辑在代码里（读待办 diff、artifact diff），不是让模型说「我完成了」。

这一点和 `team/economy.ts` 的「验证档位由调度器按事实判定，不接受成员自报」是同一条原则。

### 7.3 卡住识别与升级

| 触发条件                  | 动作                                                                    | 通知             |
| ------------------------- | ----------------------------------------------------------------------- | ---------------- |
| 流空闲 > 90s 且有工具在跑 | 不管（工具自己的 timeout 负责）                                         | —                |
| 流空闲 > 90s 且无工具在跑 | 中止本轮流，重试一次                                                    | 无               |
| 连续 2 轮流级超时         | 换 Provider 重试                                                        | 日志             |
| 连续 2 轮 `no-progress`   | **nudge**：往线程里注入一条「当前无进展，请重新评估计划」的 system 事件 | 无               |
| 连续 4 轮 `no-progress`   | **replan**：要求产出新的计划并写回待办                                  | 通知用户（可选） |
| 连续 6 轮 `no-progress`   | **abort**：线程转 `paused`，等用户决定                                  | 必须通知         |
| 硬预算耗尽                | 立即 abort                                                              | 必须通知         |
| 同一错误重复 3 次         | 记 `known_issue`，转人工                                                | 通知             |

nudge → replan → abort 是递进的，中间任何一步出现进展就重置计数。

### 7.4 Watchdog 自己也是一个 Agent Session

这是很容易省掉、但省掉之后会明显变难用的一点。

如果把 Watchdog 做成一段固定的 if/else 检查代码，用户看到的是「线程暂停了」，然后无从追问「为什么」。DSH 的做法是：**Watchdog 本身是一个 Agent Session**，定时消息驱动，开发者可以向它提问、让它解释、让它调整策略。

| 形态                      | 好处                                                 | 坏处                                       |
| ------------------------- | ---------------------------------------------------- | ------------------------------------------ |
| 纯规则代码                | 便宜、确定、零延迟                                   | 只能回答「触发了哪条规则」，无法解释上下文 |
| **Agent Session（选定）** | 能回答「为什么判定为无进展」「建议怎么改」，能被追问 | 每次判定有成本                             |
| 每轮都用 Agent 判         | 最聪明                                               | G1 直接挂                                  |

折中方案：**规则判定在前，Agent 解释在后。**

```
规则层（每轮都跑，0 token）
  → 计算 facts（§7.2），得出 outcome
  → 触发阈值时，才创建/复用 Watchdog Session

Watchdog Session（按需，有成本）
  → 输入：该线程最近 K 个 turn 的 facts、错误、产物 diff
  → 输出：结构化诊断 { verdict, evidence[], suggestion, action }
  → 用户可继续追问（它就是个会话）
```

- Watchdog Session 是**独立的、只读的**：它能读线程状态，但不能改线程目标、不能直接执行修复（只能建议）。
- 它的预算单独计，不占线程预算——否则「监督」会把被监督的线程饿死。
- 同一线程在 10 分钟内只有一个 Watchdog Session，避免「一卡就开会」。
- 诊断结果写入 `thread_turn.facts` 之外的一张 `thread_diagnosis`，UI 上直接展示「卡在哪 + 为什么 + 建议」。

「只读」这条是硬约束：一个能改线程状态的 Watchdog，出问题时会和被监督者一起失控，等于没有独立控制回路。

### 7.5 外部控制回路

Watchdog 必须在**主系统之外**。如果它跑在 Agent Loop 内部，那么「Loop 死锁」这种故障它自己也一起死锁——这正是要防的情况。

三种部署形态：

| 形态             | 适用       | 说明                                                      |
| ---------------- | ---------- | --------------------------------------------------------- |
| 同进程独立定时器 | 桌面端默认 | 与主 Loop 隔离（独立 event loop task），Loop 卡死时仍能跑 |
| 独立进程         | server     | 崩溃可独立重启；通过 DB 通信                              |
| 外部 cron        | 极简部署   | 每分钟跑一次 `novaway watchdog`，无状态                   |

判定与动作全部通过数据库完成，不通过内存共享——这样三种形态的行为一致，也让 S7（重启恢复）自然成立。

### 7.6 为什么不做「自动换模型/自动改目标」

自动换模型会让成本与行为不可预测；自动改目标会让用户失去对线程的控制。Watchdog 的职责是**发现问题并升级**，不是替用户决定。唯一的自动动作是「重试」和「nudge」，两者都不改变目标。

## 8. 状态分离与恢复

### 8.1 三段式

super-agent 要能跨进程、跨设备存在，前提是把「算什么」「记什么」「在哪算」分开：

| 段       | 内容                               | 存放                      | 特性                     |
| -------- | ---------------------------------- | ------------------------- | ------------------------ |
| **计算** | Agent Loop、Router、Watchdog       | 无状态进程                | 可随时重启、可水平扩展   |
| **状态** | Thread、事件队列、待办、记忆、预算 | SQLite（本地）/ 服务端 DB | 事务性，单一真相         |
| **环境** | 文件、shell、浏览器、桌面壳        | 本地 daemon               | 有副作用，只能在一个地方 |

**推论**：Agent Loop 里不允许持有跨 turn 的内存状态。所有「记住的东西」必须落库。这条约束让 S7（重启恢复）从「尽量恢复」变成「必然恢复」。

### 8.2 恢复流程

```
启动
 → 读取所有 status ∈ {running, waiting, paused, open} 的线程
 → 对每个线程：
    1. 若租约未过期：跳过（另一个进程在跑）
    2. 若租约过期：接管，标记 reason="recovered"
    3. 若有未完成的 turn：
       - 该 turn 的最后一个工具调用状态？
         - 未开始 → 丢弃，事件回队
         - 已开始未完成 → 标记 unknown，写一条 `system` 事件让模型判断
         - 已完成 → 保留结果，从下一步继续
    4. 重放未消费事件（按 createdAt）
    5. 若线程在 waiting：检查触发器是否还注册；不在了就标 `orphaned`
```

「工具调用状态未知」这一点必须显式处理。参考 `team` 设计的崩溃恢复原则（工具操作级恢复），不能假装它没发生，也不能无脑重跑（可能已经写了文件）。

### 8.3 BYOM 与本地 daemon（端侧契约）

DSH 的关键取舍值得照抄：**不是把环境搬上云，而是把计算搬到能连上环境的地方。** 理由很实在——真实环境里有未提交的改动、私有凭据、特定硬件与工具链，全搬到云上跑出来的结果大概率不一样。

```
┌─────────────────┐        ┌──────────────────┐        ┌──────────────────┐
│ 计算（可替换）   │  HTTPS │ 状态（单一真相）  │        │ 环境（不可搬）    │
│ Agent Loop      │◄──────►│ Thread / Event    │        │ 你的电脑          │
│ Router/Watchdog │        │ Artifact / Memory │        │ 文件 / shell / 凭据│
└─────────────────┘        └──────────────────┘        └──────────────────┘
        │                                                       ▲
        └──────────── 命令下发 / 结果回收（JSON-RPC）─────────────┘
```

**本期（本地优先）**：计算、状态、环境都在一台机器上，daemon 是进程内模块。但接口按远程设计，将来只需换实现。

daemon 的契约（`src/superagent/daemon.ts`，对应插件文档的 `PluginTransport`）：

| 方法                                  | 语义                                             |
| ------------------------------------- | ------------------------------------------------ |
| `exec({ argv, cwd, timeoutMs, env })` | 执行命令，流式回传 stdout/stderr，返回 exit code |
| `readFile` / `writeFile` / `list`     | 文件操作，强制路径白名单                         |
| `watch({ path, recursive })`          | 文件变化事件（S3 的 `fs` 触发器用它）            |
| `spawn({ kind: "shell" \| "pty" })`   | 长驻进程（dev server、TUI）                      |
| `capabilities()`                      | 汇报本机能力：平台、可用工具链、GPU、已装依赖    |

三条安全约束，缺一条就不要开放远程接入：

1. **端侧发起、云端不能主动连**：daemon 主动向云端建连（长连接），不接受入站连接。这样家庭网络/NAT 后面也能用，且攻击面小得多。
2. **命令白名单 + 显式确认**：默认只允许 manifest 声明的命令类别；涉及 `rm`、`git push`、`sudo`、网络出站的操作必须端侧确认（人在电脑前才算数）。
3. **凭据不出端**：daemon 永不把凭据内容传给云端，只在端侧注入进程环境。

**「云端被攻破」这个风险必须写在文档里**（DSH 也明确提了）：一旦云侧被攻破，它连着的所有设备都危险。所以本期默认**不启用远程模式**，`superagent.remote = false`，本地模式不需要信任任何第三方。

### 8.4 跨设备（未来）

数据结构上留好：

- `thread` 与 `thread_event` 全部可序列化，无本地路径依赖；
- 环境绑定用 `environment` 字段（`local:<machineID>` / `remote:<id>`）；
- 未来做云端时，计算段上云、状态段进 DB、环境段留在本地 daemon，接口不用改。

**现在就把这个字段写上**，比未来改表便宜。

## 9. 多通道交互

### 9.1 两种通道，两套写法

super-agent 的输出不是只有「聊天框」：

| 通道               | 形式                                       | 长度     | 场景                         |
| ------------------ | ------------------------------------------ | -------- | ---------------------------- |
| **对话通道**       | 结构化消息（Markdown、工具卡片、artifact） | 不限     | 用户主动打开时               |
| **IM 通道**        | 纯文本                                     | ≤ 100 字 | 推送、提醒、需要人决策的通知 |
| **结构化异步通道** | 卡片 / 表单 / 状态行                       | 结构化   | 审批、进度、批量选择         |

同一个线程在不同通道上必须给出**不同粒度**的内容。把对话内容直接推到 IM 是最常见的失败：

| 场景     | 对话通道            | IM 通道                                              |
| -------- | ------------------- | ---------------------------------------------------- |
| 线程完成 | 完整报告 + 产物链接 | 「搞定：重构完成，3 个测试补上，详见线程」+ 一个按钮 |
| 需要决策 | 详细选项与影响      | 「要不要顺手也改 A？回「改」或「不改」」             |
| 卡住     | 诊断信息 + 建议     | 「卡了 20 分钟，重复同一个错误，已暂停」             |
| 进度     | 时间线              | 不推（默认）                                         |

### 9.2 通知的节流与归并

| 规则                             | 说明                            |
| -------------------------------- | ------------------------------- |
| 每线程每小时最多 1 条 IM（可配） | 超过则合并为「N 条更新」        |
| 同一事件类型 10 分钟内合并       | 避免事件风暴刷屏                |
| `low` 优先级默认不推             | 只在对话通道可见                |
| 用户 30 分钟无响应               | 不重发，转 `paused`，等下次打开 |

**默认少推**是对的：super-agent 越自主，噪音越大；推送的价值在于「需要人」，不在于「汇报进展」。

### 9.3 人类插入的三种方式

「异步 ReAct」意味着用户可以在任何时刻介入。三种介入方式的语义必须明确区分，否则会出现「我说了它没反应」或「它把我的补充当成新任务」：

| 方式                   | 语义                                       | 打断当前工具？ | 典型时机                        |
| ---------------------- | ------------------------------------------ | -------------- | ------------------------------- |
| **补充（inject）**     | 在当前 turn 的下一个安全点插入，作为新信息 | 否             | 「顺便注意一下 X」「用 Y 方案」 |
| **改目标（retarget）** | 更新线程 `goal`，下个 turn 生效            | 否             | 「不用修 login 了，先看支付」   |
| **中止（stop）**       | 软停/硬停当前 turn                         | 软停否，硬停是 | 「停一下，方案不对」            |

实现上分别对应 `SessionRun.inject()` / `threads.updateGoal()` / `SessionRun.stop()`（§6.5）。

**最容易做错的是「用户补充」**：如果实现成「中止当前 turn 再重新发起」，用户会看到工具白跑了；如果实现成「忽略直到下个 turn」，用户会觉得没反应。正确做法是**在当前 turn 内的安全点插入**——模型在下一段推理就能看到，工具不重复执行。

### 9.4 与插件权限统一

IM 通道里的一次「回「改」」等价于一次交互确认。它走的是同一套权限判定（插件文档 §10.7）：

- 通知里必须说明「这是哪个线程、哪个插件发起的、会影响什么」；
- 回复要能映射回具体的 `askID`，不能靠意图猜测；
- 超时未回复 = 拒绝，不是同意。

## 10. 可观测性与成本

### 10.1 线程视图（用户看的）

一个线程页至少要回答四个问题：

1. **它在干什么**：当前 turn 的动作（读什么、跑什么、等什么）
2. **它到哪了**：待办进度 + 最近 3 次有进展的 turn
3. **它花了多少**：token/成本/时间，与预算的对比
4. **它卡在哪**：阻塞项、等待中的事件、Watchdog 的最后一次判定

这四项全部来自结构化数据，不靠模型生成摘要。

### 10.2 指标（运维看的）

| 指标                                    | 用途                             |
| --------------------------------------- | -------------------------------- |
| `thread.turn.duration_ms{outcome}`      | 一轮推进耗时分布                 |
| `thread.turn.no_progress_streak`        | 卡住预警                         |
| `router.fastpath.hit_rate`              | 确定性过滤器有效性（目标 > 40%） |
| `router.decision{path}`                 | fast/slow 比例                   |
| `trigger.events_total{trigger,deduped}` | 事件量与去重效果                 |
| `trigger.wake_latency_ms`               | G2 门禁                          |
| `worker.run.duration_ms{type}`          | 四种执行体的耗时                 |
| `thread.budget.utilization`             | 预算使用率                       |
| `superagent.idle_cpu_seconds`           | G1 门禁                          |

### 10.3 成本控制

| 机制        | 规则                                                                      |
| ----------- | ------------------------------------------------------------------------- |
| 线程预算    | 创建时设定，`hard` / `soft` 两种；`soft` 到 80% 通知，`hard` 到 100% 中止 |
| 预占 + 结算 | 一次调用前预占估算成本，结束后按实际结算（与 team 的预算预占同源）        |
| 空闲零成本  | 没有事件时**不发起任何 LLM 调用**（G1）                                   |
| 批处理摊薄  | §5.5                                                                      |
| 缓存        | 上下文装配缓存 + 工具块稳定排序（插件文档 §4.2.1）                        |

## 11. 数据模型

```sql
CREATE TABLE thread (
  id             TEXT PRIMARY KEY,
  title          TEXT NOT NULL,
  goal           TEXT NOT NULL,
  constraints    TEXT,              -- JSON 数组
  source_key     TEXT,              -- github:pr:o/r#1 / mail:<tid> / im:<ch>/<ts> / timer:<id>
  origin         TEXT NOT NULL,     -- pr/mail/im/ci/timer/manual/plugin
  status         TEXT NOT NULL,     -- open/running/waiting/paused/done/failed/aborted
  owner_worker   TEXT,              -- 未被认领时为 NULL（§5.4 冷启动）
  active_turn    TEXT,
  cwd           TEXT,
  environment   TEXT,               -- local:<machineID> / remote:<id>
  budget        TEXT,               -- JSON
  usage         TEXT NOT NULL,      -- JSON: { tokens, cost, turns }
  triggers      TEXT,               -- JSON 数组
  last_session  TEXT,
  generation    INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE INDEX idx_thread_status ON thread(status, updated_at);
CREATE UNIQUE INDEX idx_thread_source ON thread(source_key) WHERE source_key IS NOT NULL;
-- 来源键唯一：同一条 PR / 邮件线不能有两个线程，这是 §5.3 的硬保证

CREATE TABLE thread_event (
  id           TEXT PRIMARY KEY,
  thread_id    TEXT NOT NULL,
  kind         TEXT NOT NULL,       -- trigger/user/worker/watchdog/system
  priority     TEXT NOT NULL,       -- high/normal/low
  dedupe_key   TEXT,
  payload      TEXT NOT NULL,
  consumed_at  INTEGER,
  created_at   INTEGER NOT NULL
);
CREATE INDEX idx_thread_event_pending ON thread_event(thread_id, consumed_at, created_at);

CREATE TABLE thread_turn (
  id           TEXT PRIMARY KEY,
  thread_id    TEXT NOT NULL,
  session_id   TEXT NOT NULL,
  reason       TEXT NOT NULL,
  outcome      TEXT,                -- progress/no-progress/blocked/failed/aborted
  facts        TEXT,                -- JSON: 进展判据的可观测事实（§7.2）
  summary      TEXT,
  started_at   INTEGER NOT NULL,
  ended_at     INTEGER
);
CREATE INDEX idx_thread_turn_thread ON thread_turn(thread_id, started_at);

CREATE TABLE thread_lease (
  thread_id    TEXT PRIMARY KEY,
  owner        TEXT NOT NULL,       -- pid:machineID
  expires_at   INTEGER NOT NULL
);

CREATE TABLE thread_artifact (
  id           TEXT PRIMARY KEY,
  thread_id    TEXT NOT NULL,
  kind         TEXT NOT NULL,       -- tool-output/file/log/report
  size         INTEGER NOT NULL,
  summary      TEXT,
  /** 小内容内联；大内容落文件，这里存路径 */
  inline       TEXT,
  path         TEXT,
  created_at   INTEGER NOT NULL
);
CREATE INDEX idx_thread_artifact_thread ON thread_artifact(thread_id, created_at);

CREATE TABLE thread_memory (
  id           TEXT PRIMARY KEY,
  thread_id    TEXT NOT NULL,
  text         TEXT NOT NULL,
  importance   REAL NOT NULL DEFAULT 0.5,
  source_turn  TEXT,
  created_at   INTEGER NOT NULL
);

CREATE TABLE thread_subscription (
  thread_id     TEXT NOT NULL,
  subscriber_id TEXT NOT NULL,      -- worker id 或 channel id
  kind          TEXT NOT NULL,      -- worker/channel
  created_at    INTEGER NOT NULL,
  PRIMARY KEY (thread_id, subscriber_id)
);
CREATE INDEX idx_subscription_subscriber ON thread_subscription(subscriber_id);

CREATE TABLE router_decision (
  id            TEXT PRIMARY KEY,
  event_id      TEXT,
  thread_id     TEXT,
  path          TEXT NOT NULL,      -- fast/direct/slow/new-thread/dropped
  rule          TEXT,               -- 命中的 FastPath 规则 id
  act           INTEGER,            -- slow path 判定结果
  reason        TEXT,               -- 模型给的理由（slow）或规则说明（fast）
  model         TEXT,               -- slow path 用的模型
  tokens        INTEGER DEFAULT 0,
  duration_ms   INTEGER,
  created_at    INTEGER NOT NULL
);
CREATE INDEX idx_router_decision_time ON router_decision(created_at);

CREATE TABLE thread_diagnosis (
  id            TEXT PRIMARY KEY,
  thread_id     TEXT NOT NULL,
  turn_id       TEXT,
  verdict       TEXT NOT NULL,      -- stuck/no-progress/slow/healthy
  evidence      TEXT,               -- JSON 数组：facts + 错误
  suggestion    TEXT,
  action        TEXT,               -- nudge/replan/abort/none
  watchdog_sess TEXT,               -- 对应 Watchdog Session（可追问）
  created_at    INTEGER NOT NULL
);
CREATE INDEX idx_diagnosis_thread ON thread_diagnosis(thread_id, created_at);

CREATE TABLE trigger_state (
  trigger_id   TEXT NOT NULL,
  scope        TEXT NOT NULL,
  status       TEXT NOT NULL,       -- active/paused/failed/blocked
  last_fired   INTEGER,
  fire_count   INTEGER NOT NULL DEFAULT 0,
  last_error   TEXT,
  PRIMARY KEY (trigger_id, scope)
);
```

设计取舍：

- **事件与 turn 分开存**：事件可能被多个 turn 消费（broadcast），turn 是执行记录，两者生命周期不同。
- **artifact 与 memory 分开**：artifact 是「原料」，可能很大；memory 是「结论」，小且重要。混在一起会让上下文装配无法按重要性筛选。
- **不用一张大表存所有内容**：`thread_event.payload` 只放小事件；大内容一律走 artifact，避免事件表膨胀。
- **`source_key` 建唯一索引**：这条约束把「同一条 PR 只能有一个线程」从约定升级为数据库保证。没有它，两个并发 webhook 会各建一个线程，然后各自推进、互相矛盾。
- **`router_decision` 会增长很快**，保留 7 天，之后按天聚合到 `router_decision_daily`；它是回答「为什么这条消息没被处理」的唯一依据。

## 12. 与插件体系的关系（最关键的一章）

### 12.1 新增的贡献点

插件文档定义了 18 个扩展点（tool/agent/provider/…）。super-agent 再加 6 个，全部走同一套 Manifest、注册表、生命周期：

| #   | 贡献点       | 接口                              | 谁来实现                                         |
| --- | ------------ | --------------------------------- | ------------------------------------------------ |
| 19  | 触发器       | `TriggerRegistry.register`        | `builtin.triggers.*`（cron/fs/git/webhook）      |
| 20  | 快速路径规则 | `FastPathRegistry.register`       | 内核默认 + 第三方                                |
| 21  | 路由策略     | `RoutingPolicyRegistry.register`  | 内核默认 + 第三方（S4）                          |
| 22  | Worker 类型  | `WorkerTypeRegistry.register`     | `builtin.worker.{task,background,team,workflow}` |
| 23  | 监督规则     | `WatchdogPolicyRegistry.register` | 内核默认 + 第三方                                |
| 24  | 通知通道     | `ChannelRegistry.register`        | `builtin.channel.{im,desktop,webhook}`           |

（编号接续插件文档 §3 的 18 个扩展点，共 24 个。）

```jsonc
// 一个 super-agent 插件的完整 manifest
{
  "name": "acme-monitor",
  "apiVersion": 2,
  "activationEvents": ["onTrigger:watch-logs"],
  "contributes": {
    "triggers": [{ "id": "watch-logs", "kind": "fs", "entry": "./trigger.js" }],

```

### 12.2 KernelApi 的扩展

插件文档 §5.2 的 `KernelApi` 增加一段（第三方 `PluginContext` **不开放**）：

```ts
interface KernelApi {
  // …已有的 tools/agents/sessions/llm/background/scheduler/events/storage…

  readonly threads: {
    open(input: { goal: string; title?: string; triggers?: string[]; budget?: Budget }): Promise<ThreadHandle>
    get(threadID: string): Promise<ThreadInfo>
    post(input: { threadID: string; text: string; priority?: "high" | "normal" | "low" }): Promise<void>
    wait(threadID: string, input?: { until?: "done" | "waiting"; timeoutMs?: number }): Promise<ThreadInfo>
    close(threadID: string, reason?: string): Promise<void>
    list(input?: { status?: ThreadStatus[] }): Promise<ThreadInfo[]>
  }

  readonly channels: {
    publish(channelID: string, payload: unknown): Promise<void>
    subscribe(channelID: string, handler: (payload: unknown) => void): Disposable
  }

  readonly triggers: {
    register(trigger: TriggerContribution): Disposable
    fire(triggerID: string, payload: unknown): Promise<void> // 测试与手动触发
  }
}
```

**第三方为什么拿不到 `threads`**：一个第三方插件若能开线程，就能绕过预算、绕过 Watchdog、在自己的上下文里读到不该读的共享记忆。第三方需要「长时间做事」时，用工具 + `background` 已经够（`background` 在 `PluginContext` 里是可用的，只是不能 `run` 任意代码）。

### 12.3 第一方插件如何变成「可被调度的能力」

这是两套设计真正咬合的地方。做法是给每个能力插件加一个**能力声明**（不是新字段，复用现有 manifest）：

| 能力插件           | super-agent 视角                    | 声明方式                                            |
| ------------------ | ----------------------------------- | --------------------------------------------------- |
| `builtin.office`   | 一个 Worker 可以「读文档 / 改文档」 | 现有 tools 贡献即足够，无需额外声明                 |
| `builtin.browser`  | 一个线程可以「盯着网页变化」        | `contributes.triggers` 提供一个 `web-watch` 触发器  |
| `builtin.schedule` | 定时能力本身                        | 提供 `timer` 触发器 kind 的实现                     |
| `builtin.team`     | 一个 Worker 类型                    | `contributes.workerTypes` 注册 `team`               |
| `builtin.workflow` | 一个 Worker 类型                    | `contributes.workerTypes` 注册 `workflow`           |
| `builtin.publish`  | 一个触发器 + 一个 Worker            | 「发布完成后回调」用 trigger，「批量发布」用 worker |

原则：**super-agent 不新增「能力」，只新增「调度能力的方式」。** 任何在 super-agent 里出现的具体业务逻辑，都说明它应该是一个插件。

### 12.4 与 team / workflow 的边界（不要重复造）

三套东西都涉及「多个执行体协作」，边界必须写死，否则实现时会互相长进去：

|            | super-agent Thread         | team run                      | workflow run                  |
| ---------- | -------------------------- | ----------------------------- | ----------------------------- |
| 时间尺度   | 天/周，常驻                | 一次编排（分钟~小时）         | 一次脚本执行                  |
| 谁定义结构 | 用户目标 + 触发器          | 团队模板（岗位/名册）         | TypeScript 脚本               |
| 上下文     | 跨 run 持续，分层装配      | 单次 run 内                   | 单次执行内                    |
| 调度者     | Router + ThreadManager     | Team 的调度器                 | 工作流引擎                    |
| 产出       | 线程状态 + artifact + 会话 | report + 任务板               | journal + 结果                |
| 失败恢复   | 线程级（租约 + 事件重放）  | 工具操作级                    | journal 重放                  |
| 关系       | **容器**                   | **可被 Thread 启动的 Worker** | **可被 Thread 启动的 Worker** |

规则：

1. **Thread 不实现团队协作**。需要多人分工时，启动一个 `team` Worker，Team 内部的事 Thread 不管。
2. **Team 不知道 Thread 的存在**。Team 只接收「目标 + 预算 + 上下文包」，返回 report。这样 Team 可以独立测试、独立演进。
3. **Workflow 不持有长期状态**。一次脚本执行完就结束；要长期推进，外面套 Thread。
4. **三者共享预算与产物**：Worker 的花费计入线程预算；Team/Workflow 的产物注册为 thread artifact，这样链式召回能查到。

一句话：**Thread 是容器，Team 是组织，Workflow 是脚本。** 三者可以嵌套（Thread → team Worker → 内部再起 task），但不能互相替代。

### 12.5 依赖方向（与插件文档 B1 一致）

```
superagent（内核）──► plugin-api / shared
      ▲
      └── builtin.triggers / builtin.worker.* / builtin.channel.* （第一方插件）
```

`src/superagent/**` 加入 `kernel.manifest.json` 的 `kernel` 列表；它不得 import 任何具体触发器/Worker 实现。S3/S4 的「禁止改动」就是这条规则的验收。

## 13. 兼容与迁移

### 13.1 现有机制的映射

| 现有                   | 映射为                          | 迁移方式                                                                       |
| ---------------------- | ------------------------------- | ------------------------------------------------------------------------------ |
| `cron` 服务            | `timer` 触发器                  | 保留表与调度器，外面包一层 Trigger 适配器                                      |
| `monitor` 工具         | `fs`/命令触发器的**临时实例**   | 工具实现改为「创建临时 Trigger + 返回 jobID」，行为不变                        |
| `subscribe` 工具       | `http` 轮询触发器的**临时实例** | 同上；`src/background/watchers.ts` 的 resume 逻辑保留（临时 Trigger 也可恢复） |
| `background job`       | Worker 类型 `background`        | 加 `WorkerHandle` 适配层                                                       |
| `task` / `task_status` | Worker 类型 `task`              | 适配层；`agent_message` 升级为 `send()`                                        |
| `team run`             | Worker 类型 `team`              | 适配层；mailbox 保留，另加 channel                                             |
| `dynamic-workflow run` | Worker 类型 `workflow`          | 适配层（已有 `journal`，恢复语义天然对齐）                                     |
| `coordinator` agent    | 线程模板 `builtin.orchestrator` | 保留为普通 Agent；另提供「用 coordinator 推进线程」的模板                      |
| 会话内对话             | 线程 `mode: "chat"`             | 默认每会话隐式一个 chat 线程，迁移期不改变现有行为                             |

**关键：迁移期默认关闭 super-agent。** 配置项：

## 14. 里程碑

依赖关系：**S-M0 依赖插件文档的 M0**（需要 PluginHost 与 KernelApi）。其余可并行。

### S-M0｜数据与租约（2 周）

- `TriggerEngine`：注册、去重、合并、节流、事件→线程映射

### S-M3｜多线程语义（3 周）

- 上下文装配（L0–L5）、artifact spill 与链式召回
- 线程选择规则、用户插入与接管、预算预占与结算
- 通过：**S2**；G2 测量

### S-M4｜Watchdog（2 周）

- 三层监督、进度判据（读事实而非自评）

## 15. 测试策略

### 15.1 演练即测试

```ts
test("S1: a thread advances while the user is away", async () => {
  const kernel = await bootTestKernel({ superagent: { enabled: true } })
  const thread = await kernel.threads.open({ goal: "watch build", triggers: ["drill-timer"] })

  await kernel.triggers.fire("drill-timer", { at: Date.now() })
  await kernel.threads.wait(thread.id, { until: "waiting", timeoutMs: 5_000 })

  const turns = await kernel.threads.turns(thread.id)
  expect(turns.length).toBe(1)
  expect(turns[0].outcome).not.toBe("failed")
  // 关键：没有新事件时不产生 turn
  expect((await kernel.threads.turns(thread.id)).length).toBe(1)
})

test("S5: a new message on a claimed thread bypasses the router", async () => {
  const kernel = await bootTestKernel({ superagent: { enabled: true } })
  const thread = await kernel.threads.open({ goal: "watch PR", sourceKey: "github:pr:o/r#1" })
  await kernel.threads.claim(thread.id, { worker: "w1" })
  const before = kernel.metrics.routerInvocations()

  await kernel.triggers.fire("gh-comment", { sourceKey: "github:pr:o/r#1", body: "add a test" })
  await kernel.threads.wait(thread.id, { until: "waiting", timeoutMs: 5_000 })

  expect(kernel.metrics.routerInvocations()).toBe(before) // Router 完全没参与
  expect((await kernel.threads.turns(thread.id)).at(-1)?.reason).toContain("direct")
})

test("S9: inject does not interrupt the running tool", async () => {
  const kernel = await bootTestKernel({ superagent: { enabled: true } })
  const run = await kernel.session.begin({ sessionID, text: "run the slow test" })

  await kernel.waitForToolStart("bash")
  await run.inject({ text: "also update the changelog" }) // 安全点插入
  await kernel.waitForToolEnd("bash")
  expect(kernel.toolCalls("bash")).toHaveLength(1) // 工具没有被重跑

  await run.stop({ hard: false }) // 软停
  for await (const e of run.events()) if (e.type === "end") expect(e.reason).toBe("soft-stop")
})
```

### 15.2 空闲成本（G1）

```ts
const G1_CPU_SECONDS_PER_HOUR = 30 // §1.2 的门禁本体

test("G1: idle threads cost no tokens", async () => {
  const kernel = await bootTestKernel({ superagent: { enabled: true } })
  for (let i = 0; i < 10; i++) await kernel.threads.open({ goal: `t${i}` })
  const before = kernel.metrics.llmCalls()
  const windowMs = 60_000
  await sleep(windowMs)
  expect(kernel.metrics.llmCalls()).toBe(before)
  // 按比例换算：门禁是占空比（30s/1h），不是绝对秒数
  expect(kernel.metrics.idleCpuSeconds()).toBeLessThan((windowMs / 3_600_000) * G1_CPU_SECONDS_PER_HOUR)
})
```

阈值只允许从 `G1_CPU_SECONDS_PER_HOUR` 推导一处。PR 上跑 60s 比例窗口，1 小时全量窗口放夜间任务（`verify:superagent --full`）。

这一条在本版修订前是坏的：§1.2 写「1 小时 < 30s」，本节却写死 `toBeLessThan(5)`，60s 窗口的 5s 折算成小时是 300s——测试比门禁宽松 10 倍，门禁形同虚设。

### 15.3 隔离（G3）

故障注入清单：

- 线程 A 的工具无限挂起 → A 被 Watchdog 处理，B/C 正常
- 线程 A 超预算 → A `paused`，B/C 正常
- 触发器插件抛错 → 该触发器 `failed`，其他触发器正常
- 通道订阅者处理慢 → 发布者不被阻塞
- 租约被另一个进程持有 → 当前进程跳过，不重复推进

### 15.4 恢复（S7）

- 在 turn 执行的三个位置杀进程：工具调用前 / 调用中 / 调用后
- 断言：前 → 事件回队；中 → `unknown` 标记且有 system 事件；后 → 结果保留并继续
- 断言：租约过期后可被新进程接管，未过期则跳过

### 15.5 Slow path 与路由质量

这一节没有它，「过滤」就是一句空话。

| 测试          | 方法                                                      | 通过线                             |
| ------------- | --------------------------------------------------------- | ---------------------------------- |
| Fast 覆盖率   | 用真实会话历史（脱敏）回放，统计被 Fast 层挡掉的比例      | > 40%（低于说明规则太弱，G1 会挂） |
| Fast 误杀     | 人工标注 100 条「应该行动」的消息，统计被 Fast 丢弃的比例 | < 2%                               |
| Slow 判定准确 | 同上标注集，统计 Slow 判定 `act` 与人工一致的比例         | > 90%                              |
| 判定延迟      | Slow path 单次耗时 P95                                    | < 800ms                            |
| 判定成本      | Slow path 单条 input+output token                         | < 1200                             |

**误杀的代价远高于误放**：误放只是多烧一次 token，误杀是「用户说了话，系统毫无反应」。所以 Fast 层规则宁可保守——只挡「明确无意义」的（去重、心跳、白名单），不挡「可能是任务」的。

回放集要长期保存（`test/fixture/routing-corpus/`），每次改路由规则都跑一遍，防止「调优 A 场景把 B 场景搞坏」。

### 15.6 上下文装配质量

| 测试           | 方法                                                     |
| -------------- | -------------------------------------------------------- |
| 装配确定性     | 同一线程同一代数装配两次，逐字节相同（快照测试）         |
| 分层预算       | L0–L5 各自超预算时，丢的是该层最旧内容，且标 `truncated` |
| spill 可召回   | 强制 spill 一个大结果，断言 `artifact_read` 能取回原文   |
| 召回质量       | 断言摘要包含关键词（文件数、命中数、top 路径）           |
| 跨 turn 一致性 | L1/L2 在同一线程的连续两个 turn 里，重复内容不超过 20%   |

### 15.7 与插件体系的联合验收

`bun run verify:all` = `verify:plugins`（D1–D9、B1–B3）+ `verify:superagent`（S1–S10、G1–G3）。

联合验收要求同时满足三条：

- 关掉所有 super-agent 插件（S8）后，D1–D9 仍然全绿；
- 关掉所有能力插件（D7）后，S1–S10 的「线程跑起来」仍然成立（只是什么都干不了，但调度不崩）；
- `bun run verify:all` 在 **Node 22 与 Bun 两个运行时**下都通过（插件 API 不得依赖 Bun-only）。

这是两条体系互不依赖的证明。

## 17. 决策记录

| #   | 问题                        | 决定                                                                          | 理由                                                 |
| --- | --------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------- |
| Q1  | Thread 是否替代 Session     | 不替代，Thread 在 Session 之上                                                | 保留现有 compaction 与消息模型，避免全量重放         |
| Q2  | 是否允许同一线程并行多 turn | 不允许，单写者 + 租约                                                         | 并行会基于同一旧上下文做出矛盾决策                   |
| Q3  | 线程归属是否用语义相似度    | 不用；用外部来源键（PR 号 / 邮件 thread-id / IM topic）/ 显式 ID / 触发器 key | 误路由会污染两个线程，且用户不可见                   |
| Q4  | 是否定时唤醒模型做巡检      | 不做；必须由触发器驱动 + fast path 过滤                                       | 轮询违反 G1                                          |
| Q5  | Watchdog 是否自动换模型     | 不自动；只重试与 nudge                                                        | 成本与行为不可预测                                   |
| Q6  | 第三方能否创建线程          | 不能                                                                          | 绕过预算与共享记忆隔离；用 background 已足够         |
| Q7  | IM 推送默认策略             | 默认少推；`low` 不推；每小时每线程最多 1 条                                   | 越自主噪音越大，推送价值在「需要人」                 |
| Q8  | 投机执行的范围              | 只投机只读操作，且有独立小预算                                                | 写操作投机会产生无法回滚的副作用                     |
| Q9  | 进度判据来源                | 可观测事实（待办/阻塞/产物/记忆），不接受模型自评                             | 同 team 的「验证档位不由成员自报」                   |
| Q10 | 跨设备支持时间              | 本期不做，但数据结构预留 `environment`                                        | 现在留字段比未来改表便宜                             |
| Q11 | fast path 是否内置业务规则  | 只内置 5 条通用规则，其余全部插件化                                           | 业务规则写进内核等于第二种硬编码                     |
| Q12 | 事件到线程默认映射          | `reuse`                                                                       | 绝大多数触发器应积累上下文                           |
| Q13 | Router 是否需要强模型       | 不需要；用轻量模型                                                            | Router 只做分拣与冷启动，不做计划（§5.1）            |
| Q14 | 线程归属靠什么判定          | 外部来源键（PR 号/邮件 thread-id/IM topic_ts）                                | 语义相似路由会不可见地污染两条线程（§5.3）           |
| Q15 | Worker 之间能否互发消息     | 不能；交换产物不交换对话                                                      | 对话耦合无法审计；DSH 的直通是 Thread→订阅者（§5.4） |
| Q16 | 上下文 spill 的前提         | 必须有可靠摘要 + 系统提示说明 + 强模型                                        | 弱模型不会主动召回，效果显著退化（§4.5）             |
| Q17 | Watchdog 形态               | 规则判定在前，Agent Session 解释在后；只读                                    | 纯规则无法解释，纯 Agent 太贵（§7.4）                |
| Q18 | 是否支持远程 daemon         | 本期不支持，默认关闭                                                          | 云侧被攻破会波及所有设备（§8.3）                     |
| Q19 | 人类插入的默认语义          | 补充 = 下一个安全点插入，不打断工具                                           | 打断会丢弃工具结果，产生「改没改」的不确定性（§9.3） |
| Q20 | 活跃线程上限                | 默认 5，可调但 UI 只突出 3–5 个                                               | 人的注意力是真实瓶颈（§0.2 第 6 条）                 |

**没有照抄的两点**：

1. **DSH 说 Router 可以很轻**，但没说清「轻到什么程度」。本设计给了硬边界：Router 只做「归谁管 / 要不要新建」，任何计划性内容都算违规，并写进 S4 的禁止改动清单。
2. **DSH 说 Watchdog 是 Agent Session**，但没说成本和频率。本设计加了「规则判定在前」与「10 分钟一次」的上限，否则 Watchdog 会成为第二个烧钱源头。

## 19. 结语

两套设计合起来只有一句话：

> **插件体系让内核不知道「有什么能力」；super-agent 让内核不知道「什么时候用」。**

判断这两件事是否都做到了，不看架构图，看两条命令：

```bash
bun run verify:plugins      # D1–D9 + B1–B3：只加文件就有能力，停用就干净
bun run verify:superagent   # S1–S10 + G1–G3：不说话时它在推进，卡住能被发现
```

如果某一天发现「要加一个定时任务得改 `cron/`」，说明触发器还没插件化；如果发现「要让它自己盯着某个东西得改 `session/prompt.ts`」，说明线程与触发器还没接上。这两种情况都应该是配置或插件，不是内核改动。

推进建议：插件文档的 M0 必须先做——super-agent 的每一层都注册在 PluginHost 上，没有它就得再造一套。之后按 §14.1 的错位表推进，同一时期只改一条线的核心文件。
