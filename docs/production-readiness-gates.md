# 生产就绪门禁：从「能跑」到「可发布」

> 配套文档：`docs/production-grade-absorption-plan.md`（内核对齐 cc、桌面端对齐 ZCode）。
> 本文回答一个更严格的问题：**那份方案做完，能不能算生产级？**
> 答案：只能到 L1（内部日用），接近 L2。要到 L3 / L4，必须补齐本文的 C1–C7。
>
> 评估快照：2026-10-27。所有“现状”结论都来自当前工作树，附文件级证据。

---

## 0. 一句话结论

**A/B 类工作解决“主路径闭环 + 交互完成度”，C 类工作解决“事故率”。**

生产环境的事故大多不在主路径上，而在四类地方：

1. **模型在真实任务上的表现**（没有度量，等于没有质量）；
2. **外部输入与执行边界**（凭据、注入、插件、SSRF、MCP）；
3. **分发链路**（签名、更新、回滚、安装失败）；
4. **坏了之后能不能查**（诊断包、崩溃、日志）。

这四类，cc 和 ZCode 都只能给“思路”，给不了“我们的答案”。所以必须自建，且必须进 P0。

## 1. 发布分级：L0–L4

不要用“生产级 / 非生产级”二元判断。用五级，每级有明确门槛、指标与承诺。

| 级别 | 名称       | 使用者       | 核心承诺                         | 允许的失败             | 累计人周 |
| ---- | ---------- | ------------ | -------------------------------- | ---------------------- | -------- |
| L0   | 可演示     | 开发者       | 主路径能走通                     | 任何环节都可能坏       | 已完成   |
| L1   | 内部日用   | 团队 5–15 人 | 每天用不丢数据、不卡死           | 需要手动重启 / 手动修  | 5–7      |
| L2   | 小范围外发 | 100 人内测   | 主路径稳定、问题可诊断           | 局部功能不可用，可回滚 | 12–16    |
| L3   | 公开测试   | 公开下载     | 三平台可用、可更新、可回滚       | 已知问题清单内         | 24–32    |
| L4   | 商业 GA    | 付费 / 企业  | 数据不丢、版本可回退、有支持流程 | 仅计划内维护窗口       | 40–55    |

### 1.1 各级别的硬门槛

| 门槛         | L1               | L2                   | L3                    | L4                               |
| ------------ | ---------------- | -------------------- | --------------------- | -------------------------------- |
| 自动测试全绿 | 必需             | 必需                 | 必需                  | 必需                             |
| 三平台 smoke | 本机             | 本机 + CI 1 平台     | 三平台 CI             | 三平台 + 真机                    |
| Eval 基线    | 至少 1 组        | 3 provider × 20 任务 | 全 provider × 30 任务 | 全 provider × 50 任务 + 回归门禁 |
| 凭据存储     | 文件 0600 可接受 | 系统 keychain        | 系统 keychain         | keychain + 轮换                  |
| 代码签名     | 可无             | Windows 签名         | Windows + macOS 公证  | 双平台 + 可复现构建              |
| 更新回滚     | 手动重装         | 版本钉住             | 灰度 + 自动回滚       | 分阶段 + 遥测驱动                |
| 诊断包       | 日志             | 一键导出             | 一键导出 + 脱敏校验   | 支持工单集成                     |
| 迁移回滚     | 备份             | 备份 + 演练          | 自动备份 + 回滚脚本   | 双写 / 在线迁移                  |
| 安全评审     | 自查             | 威胁模型             | 外部渗透              | 年度复审                         |

> L1 与 L2 的分界线不是功能多少，而是**“出问题能不能查、能不能退”**。

### 1.2 各级别的用户可见差异

| 能力 | L1         | L2                 | L3                  | L4                  |
| ---- | ---------- | ------------------ | ------------------- | ------------------- |
| 安装 | 源码 / npm | 安装包（未签名可） | 签名安装包          | 商店 / 企业分发     |
| 升级 | 重装       | 手动检查           | 自动检查 + 一键升级 | 灰度 + 自动回滚     |
| 崩溃 | 手动重启   | 重启后恢复会话     | 自动恢复 + 提示     | 无感恢复            |
| 报错 | 控制台     | 错误卡片           | 错误卡片 + 诊断     | 错误分类 + 自助修复 |
| 支持 | 口头       | 群内反馈           | 工单 / 诊断包       | SLA                 |

## 2. C1：Agent 质量 eval（最高优先级）

### 2.1 为什么这是第一位

内核管道修得再完美，如果模型在真实任务上工具调用成功率只有 70%，产品依然不可用。而现有测试锁不住这个：

- 单元测试验证“代码逻辑”，不验证“模型行为”；
- golden transcript 用录制响应，不验证“真实 provider”；
- 知识库 / 记忆已有 eval（`src/knowledge/eval.ts`、`test/memory/task-eval.test.ts`），但**没有 Agent 任务级 eval**。

**结论：没有 eval，A1–A12 做完也不知道是变好还是变坏。**

### 2.2 现状

| 项                 | 现状 | 证据                                                    |
| ------------------ | ---- | ------------------------------------------------------- |
| RAG eval           | 有   | `packages/novaway/src/knowledge/eval.ts`                |
| 记忆 eval          | 有   | `packages/novaway/test/memory/{eval,task-eval}.test.ts` |
| Agent 任务 eval    | 无   | —                                                       |
| Provider scorecard | 无   | —                                                       |
| 提示词回归门禁     | 无   | —                                                       |

### 2.3 要建什么

**1. 任务集（30 → 50 条）**

按能力分 6 类，每类 5–10 条，全部可自动判定：

| 类别     | 例子                       | 判定方式                   |
| -------- | -------------------------- | -------------------------- |
| 代码修改 | 修一个失败测试、加一个函数 | 测试通过 + diff 在允许范围 |
| 代码探索 | 找出调用链、解释模块职责   | 关键文件命中 + 无越界修改  |
| 多步工具 | 查日志 → 改配置 → 验证     | 步数上限 + 最终状态        |
| 权限交互 | 触发 ask 后允许 / 拒绝     | 事件序列 + 不越权          |
| Office   | 生成 PPT / 改 Excel        | 文件可打开 + 关键字段      |
| 运营     | 小红书文案 + 发布草稿      | 结构完整 + 不实际发布      |

**2. 运行器**

- 给定任务：workspace 快照 + prompt + 期望；
- 跑完整轮（真实模型或 cassette）；
- 采集：成功、步数、工具调用、token、成本、耗时、错误；
- 输出 JSON + 汇总表；
- 支持 `--provider` / `--model` / `--repeat 3`。

**3. Provider scorecard**

对每个 provider / model 记录：

| 指标                | 说明                          |
| ------------------- | ----------------------------- |
| 任务成功率          | 通过数 / 总数                 |
| 工具调用成功率      | 有效 tool call / 总 tool call |
| 平均步数            | 越低越好，过低说明偷懒        |
| JSON schema 合规率  | 参数解析失败次数              |
| 并行工具支持        | 是否支持一次多调用            |
| thinking block 兼容 | 是否回传 / 是否需清理         |
| 平均成本            | 每任务 token × 单价           |
| P95 时延            | 首 token + 总时长             |

**4. 提示词回归门禁**

- 任何系统提示词 / Agent prompt 变更，必须跑 eval；
- 成功率下降 > 3 个点或成本上升 > 20%，CI 阻断；
- 结果存档，可对比历史。

### 2.4 落点

- 新增 `packages/novaway/eval/`（任务定义、运行器、判定器）
- 新增 `packages/novaway/eval/tasks/*.yaml`
- 复用 `test/lib/effect.ts` 与 `packages/llm` cassette
- 新增 `docs/eval.md`（如何加任务、如何看结果）
- CLI：`novaway eval run --suite core --provider deepseek`

### 2.5 验收

- 30 条任务可一键跑完，输出 scorecard。
- 至少 3 个 provider（如 DeepSeek / Qwen / GLM）有基线数字。
- 故意改坏一条提示词，门禁能拦住。
- 单任务可复现：同一 cassette 两次结果一致。

### 2.6 人周

3–5 人周（任务集 2 周、运行器 1 周、scorecard 1 周、门禁 1 周）。

## 3. C2：安全（不只是权限）

权限管的是“Agent 能不能做”，不管“外部输入能不能骗 Agent 做”。

### 3.1 现状与风险

| 面        | 现状                                  | 风险                                                 | 证据                                    |
| --------- | ------------------------------------- | ---------------------------------------------------- | --------------------------------------- |
| 凭据存储  | `auth.json` 明文 JSON，`chmod 0600`   | Windows 上 mode 无效 → 明文落盘；备份 / 同步会带走   | `packages/novaway/src/auth/index.ts`    |
| 插件执行  | 插件是 in-process JS 模块             | 插件可读所有 key、任意 fs / net                      | `packages/plugin/src/index.ts`          |
| webfetch  | 仅允许 http/https；5MB 上限；30s 超时 | 无内网 / 回环 / 重定向校验 → SSRF；无域名策略        | `packages/novaway/src/tool/webfetch.ts` |
| 间接注入  | 无标记                                | 网页 / MCP / 仓库文件里的指令可被当作用户指令        | 全局搜索无 `untrusted` 标记             |
| MCP 信任  | 连接即用                              | 远程 server 可下发任意工具；首次连接无确认           | `packages/novaway/src/mcp/*`            |
| Hook 安全 | http hook 有白名单 env                | 命令 hook 继承环境变量；prompt / agent hook 可被滥用 | `packages/novaway/src/hook/*`           |
| 路径      | 多数工具 resolve 后检查               | symlink / junction 越界需系统验证                    | `tool/read.ts`、`tool/edit.ts`          |

### 3.2 要做什么

**S1 凭据**

1. 优先走系统凭据库：macOS Keychain、Windows DPAPI / Credential Manager、Linux Secret Service；不可用时回退加密文件（密钥由 OS 用户态派生）。
2. `auth.json` 只存引用，不存明文 key。
3. 日志 / 诊断包 / 导出强制脱敏（已有 `cli/cmd/export.ts` 的 redact 可作为基础）。
4. 迁移：首次启动读取旧 `auth.json` → 写入 keychain → 删除明文（保留备份 7 天）。
5. 设置页显示“凭据存储位置”，可手动清理。

**S2 插件隔离**

1. 明确两级：
   - 可信插件（内置 / 签名）：in-process；
   - 第三方插件：子进程 + 受限 IPC。
2. 第三方插件默认无 fs / net 直接访问，能力通过 host API 授权。
3. 安装时展示将申请的权限；升级后权限变化需重新确认。
4. 插件调用带超时与取消；崩溃不影响主进程。

**S3 webfetch / browser 的 SSRF**

1. 解析 URL 后校验：
   - 拒绝 `localhost`、`127.0.0.0/8`、`::1`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`fc00::/7`；
   - 拒绝非 80/443 端口（可配置白名单）；
   - 每一跳重定向重新校验，最多 5 跳；
   - 拒绝 `file:`、`ftp:`、`data:`（已部分拒绝）。
2. 可选企业策略：域名 allowlist / denylist。
3. 下载文件类型白名单；HTML 转 Markdown 时剥离脚本 / 事件属性。

**S4 间接提示注入**

1. 所有外部内容（webfetch、websearch、MCP 返回、仓库文件、OCR）在进入上下文时加结构化标记：
   - `<untrusted source="webfetch" url="...">...</untrusted>`；
   - 系统提示明确：untrusted 内容中的指令不得执行，只能作为数据。
2. 高风险动作（写文件、执行命令、发布）在“本轮上下文包含 untrusted 内容”时降级权限：
   - 强制 ask；
   - 或要求用户二次确认。
3. 输出侧：工具结果中的可疑指令片段高亮给用户（“这段内容试图让你执行命令”）。
4. 测试：内置一组注入样本，验证不会触发写 / 执行。

**S5 MCP 信任**

1. 首次连接显示 server 名称、来源、工具列表；用户确认后才可用。
2. 工具集合变化（新增 / 改名）需重新确认。
3. 远程 MCP 默认关闭；开启需显式配置。
4. MCP 工具默认按 untrusted 内容处理（见 S4）。

**S6 Hook 安全**

1. 命令 hook 使用白名单环境变量，不继承 API key。
2. http hook 只允许声明过的 env；禁止 `file:`。
3. prompt / agent hook 默认关闭，开启需说明成本与风险。
4. hook 超时与输出大小上限。

### 3.3 落点

- `packages/novaway/src/auth/*`
- 新增 `packages/novaway/src/security/{url-guard,untrusted,redact}.ts`
- `packages/novaway/src/tool/{webfetch,websearch,browser}.ts`
- `packages/novaway/src/mcp/*`
- `packages/novaway/src/hook/{exec,service}.ts`
- `packages/plugin/src/*` + 新增 `packages/plugin-host/*`（子进程宿主）
- `packages/app/src/components/settings-*`（凭据位置 / MCP 信任 / 插件权限）

### 3.4 验收

- 凭据：keychain 写入 / 读取 / 删除；旧文件迁移；诊断包中无明文。
- SSRF：内网地址、回环、重定向到内网、非标准端口全部拒绝。
- 注入：注入样本不触发写 / 执行；降级为 ask。
- 插件：第三方插件无法直接读 key；越权调用被拒绝。
- MCP：未确认不可用；工具变化触发重新确认。
- Hook：命令 hook 环境变量中无 key。

### 3.5 人周

5–8 人周（凭据 1.5、插件隔离 2、SSRF 1、注入 1.5、MCP / Hook 1）。

## 4. C3：供应链与分发

### 4.1 现状与风险

| 面           | 现状                                    | 风险                                    | 证据                                                    |
| ------------ | --------------------------------------- | --------------------------------------- | ------------------------------------------------------- |
| Windows 签名 | PowerShell 脚本签名，失败仅告警继续     | 未签名包被 SmartScreen 拦截；用户流失   | `script/sign-windows.ps1`、`electron-builder.config.ts` |
| macOS 签名   | `APPLE_CERTIFICATE` 存在时才签名 + 公证 | 无证书即未公证，Gatekeeper 拦截         | `electron-builder.config.ts`                            |
| 更新校验     | `verifyUpdateCodeSignature: false`      | 更新包不校验签名 → 供应链攻击面         | `electron-builder.config.ts`                            |
| 降级         | `allowDowngrade: true`                  | 可被诱导降级到有漏洞版本                | `desktop/src/main/updater.ts`                           |
| 灰度         | 无                                      | 坏版本全量推送，只能靠用户重装          | `updater.ts`                                            |
| 回滚         | 无自动回滚                              | 同上                                    | —                                                       |
| 版本握手     | sidecar 仅健康检查                      | 桌面端与 CLI 版本偏差可能导致协议不兼容 | `desktop/src/main/server.ts`                            |
| npm 安装     | 平台包 180MB，失败静默跳过              | 国内网络下高频失败                      | `README.md` 已记录                                      |
| 许可证       | 109 依赖，未见审计流程                  | 合规风险                                | 根 `package.json`                                       |

### 4.2 要做什么

**D1 签名**

1. Windows：证书进 CI secret；签名失败**阻断**发布（不再“继续无签名”）。
2. macOS：CI 必须配置证书；`hardenedRuntime` + `notarize` 强制；公证失败阻断。
3. 产物校验：发布后自动验证签名与公证状态。
4. 安装包与可执行文件都签；更新包也签。

**D2 更新链路**

1. `verifyUpdateCodeSignature: true`；签名不匹配拒绝安装。
2. `allowDowngrade` 改为默认 false，仅在显式“修复模式”允许。
3. 灰度：
   - 发布先 5% → 24h 观察 → 25% → 100%；
   - 观察指标：启动失败率、崩溃率、首轮失败率（本地统计，用户可选上报）。
4. 自动回滚：
   - 新版本启动连续失败 N 次 → 提示回退；
   - 提供“回退到上一版本”按钮；
   - 保留上一版本安装包。
5. 通道：stable / beta / dev 已有，补“版本钉住”与“跳过此版本”。

**D3 安装失败恢复**

1. 安装器检测平台包缺失 / 解包失败，给出可执行修复步骤。
2. `novaway doctor` 一键检查：安装方式、平台包、postinstall 占位、registry、版本。
3. 国内镜像：安装器内置回退源（npm 官方 → npmmirror → 自建）。
4. 失败日志落盘，可一键导出（见 C4）。

**D4 版本与协议**

1. sidecar 启动时握手：返回内核版本、API 版本、能力清单。
2. 桌面端与内核 API 版本不匹配时：
   - 兼容：继续；
   - 不兼容：明确提示并阻止危险操作。
3. CLI / SDK / ACP 同样带版本头；服务端可拒绝过旧客户端。

**D5 依赖与许可证**

1. CI 生成许可证清单（license-checker 或等价）。
2. 禁止 GPL / AGPL 进入分发物（除非单独评估）。
3. 依赖体积预算：桌面安装包与 npm 包各设上限。
4. 锁定版本 + 审计新依赖（`bunfig.toml` 的 `minimumReleaseAge` 已有，保留）。

### 4.3 落点

- `packages/desktop/electron-builder.config.ts`
- `script/sign-windows.ps1`
- `packages/desktop/src/main/updater.ts`
- `packages/desktop/src/main/server.ts`（握手）
- `packages/novaway/src/cli/cmd/*`（doctor）
- 新增 `.github/workflows/release.yml`（或等价 CI）
- 新增 `docs/release.md`

### 4.4 验收

- 未签名包无法发布（CI 阻断）。
- 更新包签名校验失败时拒绝安装。
- 灰度配置生效，可暂停 / 回滚。
- 新版本连续启动失败可回退。
- `novaway doctor` 能定位三类常见安装失败。
- 许可证清单生成，无禁用协议。

### 4.5 人周

3–5 人周（签名 1、更新与回滚 1.5、安装恢复 1、版本握手 0.5、许可证 0.5）。

## 5. C4：诊断与支持

### 5.1 现状

| 项         | 现状                              | 证据                                             |
| ---------- | --------------------------------- | ------------------------------------------------ |
| 日志       | 分级日志 + JSONL trace            | `@novaway/core/util/log`、`cli/cmd/run/trace.ts` |
| 导出       | `novaway export` 带 redact        | `cli/cmd/export.ts`                              |
| 调试命令   | 11 个 `debug` 子命令              | `cli/cmd/debug/*`                                |
| 统计       | `novaway stats`                   | `cli/cmd/stats.ts`                               |
| 一键诊断包 | 无统一入口                        | —                                                |
| 崩溃捕获   | Electron 侧有 logging，无统一上报 | `desktop/src/main/logging.ts`                    |
| 用户反馈   | 无内置入口                        | —                                                |

### 5.2 要做什么

**P1 诊断包（`novaway doctor --bundle`）**

收集：

- 环境：OS / 版本 / 安装方式 / 架构 / 时区 / locale；
- 版本：CLI、内核、桌面端、sidecar、SDK；
- 配置：脱敏后的 config（不含 key）；
- 日志：最近 2000 行 + 最近 3 个 trace；
- DB：schema 版本、迁移记录、表行数（不含内容）；
- 连接：provider 列表（不含 key）、MCP server 列表（不含 token）；
- 失败：最近 20 条错误（分类 + 堆栈）；
- 性能：首屏、turn 时长、工具时长（聚合）。

约束：

- 默认不含 prompt / 文件内容 / 路径（可选开启）；
- 生成 zip，展示将包含的文件清单；
- 本地生成，不上传。

**P2 崩溃与卡死**

1. 主进程 / 渲染进程崩溃：写 crash 文件，重启后提示“上次异常退出，是否发送诊断包”。
2. 卡死检测：主线程阻塞 > 5s 记录堆栈。
3. 会话级恢复：崩溃时正在跑的工具标记 `interrupted`，重启后可继续。

**P3 用户反馈入口**

1. 设置 → 帮助 → “反馈问题”：生成诊断包 + 打开 issue 模板。
2. 错误卡片上的“报告此问题”带上下文（错误分类、trace id）。
3. 不上传；用户自行附到 issue / 群。

**P4 支持视图**

设置 → 诊断：

- 当前状态（模型 / 工具 / MCP / LSP / DB）；
- 一键自检（provider 连通、工具可执行、权限规则、磁盘空间）；
- 一键修复常见项（重建缓存、重装平台包、修复权限文件）。

## 7. C6：数据耐久与迁移

### 7.1 现状

| 项       | 现状                        | 风险                          | 证据                           |
| -------- | --------------------------- | ----------------------------- | ------------------------------ |
| 迁移数量 | 36 个 SQL 迁移              | 跨版本升级路径未演练          | `packages/novaway/migration/*` |
| 回滚     | 无 down / rollback          | 坏迁移只能靠备份              | 同上                           |
| 备份     | 未见自动备份                | 升级失败可能不可恢复          | —                              |
| 多实例   | 桌面 sidecar + CLI 可同时写 | WAL 之外有迁移竞争            | `storage/db.ts`                |
| 会话体积 | 未知                        | 10 万消息后 DB 膨胀、查询变慢 | —                              |
| 保留策略 | 有归档，无清理              | 磁盘无限增长                  | `session/session.ts`           |
| 崩溃半写 | 有 `interrupted` 标记       | 覆盖不全                      | `session/recovery`（待建）     |

### 7.2 要做什么

**R1 迁移安全**

1. 每个迁移带 `up` 与 `down`（至少可回滚到上一个 schema）。
2. 升级前自动备份 DB（`db.sqlite.bak.<version>`），保留最近 3 个。
3. 启动时检查 schema 版本：
   - 高于当前程序 → 拒绝启动并提示升级；
   - 低于 → 自动迁移；
   - 迁移失败 → 自动回滚 + 恢复备份 + 可读错误。
4. 迁移演练：CI 用 3 个历史版本 DB 样本跑升级 + 回滚。

**R2 多实例**

1. 单写者模型：同一 DB 只允许一个内核进程写入。
2. 启动时获取文件锁；已有进程则连接已有 server（或明确拒绝）。
3. 桌面 sidecar 与 CLI 通过 API 协作，不各自打开写连接。
4. 迁移期间排他锁；其他进程等待或提示。

**R3 数据保留**

1. 归档会话可配置保留期（默认永久，可选 90 / 180 天）。
2. 工具输出大文件：超过阈值落盘，DB 只存引用。
3. DB 体积监控：设置页显示大小；提供 `VACUUM` / 清理入口。
4. 导出 / 导入：单会话、单项目、全量。

**R4 崩溃恢复**

1. 启动扫描：`running` 消息 / 工具 / 任务 → `interrupted`。
2. 半写 part：缺 `finish` 的 part 标记未完成，不参与上下文重建。
3. 幂等：按 `callID` 去重。
4. 用户可选“继续上一轮”或“重新开始”。

### 7.3 落点

- `packages/novaway/src/storage/{db,migration}.ts`
- `packages/novaway/migration/*`（补 down）
- 新增 `packages/novaway/src/storage/backup.ts`
- 新增 `packages/novaway/src/storage/lock.ts`
- `packages/novaway/src/session/recovery.ts`（新增）
- `packages/app/src/components/settings-data.tsx`（新增）

## 13. 结论

**做完主方案（A/B），到 L1；做完本文（C1–C7），到 L3；要达到 L4，还需要一轮以稳定性和支持为中心的迭代。**

具体说：

- **“对齐”**：A/B 做完，内核行为接近 cc，桌面交互接近 ZCode。这是“像不像”的问题。
- **“生产级”**：C1–C7 做完，才是“会不会坏、坏了能不能查、能不能退”的问题。

两者不是同一个维度。只做 A/B 就对外发布，最可能的事故不是“交互不如 ZCode”，而是：

1. 某个 provider 上工具调用失败率 30%，没人知道；
2. 用户的 API key 明文躺在 `auth.json` 里；
3. 未签名安装包被 SmartScreen 拦，用户以为装坏了；
4. 升级到坏版本，只能让用户手动卸载重装；
5. 用户报“卡住了”，没有日志、没有诊断包，只能猜。

这五条，A/B 一条都解决不了。所以：

**建议的发布路径是 L1 → L2 → L3，每一级都先补该级的 C 类门禁，再放量。** 不要跳过 L2 直接公开下载。
