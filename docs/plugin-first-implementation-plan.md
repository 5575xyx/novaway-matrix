# 万物皆插件优先实施计划

> 状态：实施中（2026-11-11）；M0 HTTP 启停与 persisted-enabled v2 冷启动路径已接线；SDK/Novaway/App 与根级 typecheck、根级 lint（含 warnings）已通过。完整故障恢复/关闭清理门槛、D1–D9 全行为验收、生产 B2、最终 B3 与统一独立 worktree 黄金路径仍未全部通过，且 `verify:plugins` 仍保留 D3–D9 known-red；因此“万物皆插件”全计划未验收完成。阶段 0 证据见 [`plugin-first-baseline-2026-11-08.md`](./plugin-first-baseline-2026-11-08.md)、[`plugin-first-migration-map.md`](./plugin-first-migration-map.md) 和 [`plugin-first-boundary-2026-11-08.json`](./plugin-first-boundary-2026-11-08.json)。
> 后续路线：[`super-agent-plugin-design.md`](./super-agent-plugin-design.md)，仅在本计划完成并验收后启动实现。
> 目标：先达到可验证的“万物皆插件”，以小而稳定的内核、可组合的第一方/第三方能力插件，以及有用且经过集成验证的默认发行组合交付；本计划不实现 Super-Agent 运行时。

> 设计依据：[`plugin-system-unification-design.md`](./plugin-system-unification-design.md)。

## 1. 范围与执行约束


本轮将插件设计落到生产调用链：运行时 Host 与 HTTP API、ToolRegistry/Agent/Skill/Command、各领域贡献点、宿主 UI、打包与默认发行组合，并通过 D1–D9、B1–B3 及全仓回归。插件是否完成，以行为验收为准，不以目录迁移、Manifest 数量或原型测试代替。

### 1.2 明确不在本轮实现的内容

- 不实现 TriggerEngine、Thread、Router、Worker Pool、Super-Agent Watchdog、Channel、BYOM daemon 等 Super-Agent 运行时。
- 不因“以后需要”提前建设 Super-Agent 专属行为和调度逻辑。通用 Manifest、Host、权限、注册表应保留清晰扩展能力，但不把未来 contribution 的运行行为列入本轮 DoD。若现有 Plugin API 已声明 Super-Agent contribution kind，本轮只在设计明确要求时保留类型/Schema 兼容性；不得因此提前实现 Trigger、Router、Thread 等消费者，也不得把未运行的 contribution 标为已验收。
- 不把“所有代码必须卸载”当作目标。稳定的内核原语、执行循环和安全边界可以留在内核；具体可替换的领域实现必须通过插件接入。
- 不把 capability 声明或进程内 API 包装描述为安全沙箱。进程内第三方代码的信任级别必须显式说明；真正隔离需由独立进程/Worker transport 等实现并单独验收。

### 1.3 操作约束（全程有效）

- 不重启应用或服务进程，不提交代码，除非用户明确改变授权。
- 如用户的“不重启应用或服务进程”约束导致无法进行真实 UI 验证，应报告未验证，不得宣称完成，也不得自行重启。
- 全程不执行 git commit；任何可能需要重启既有进程的验证先停下并说明限制，等待用户授权。
- 开始每个实现任务前，先查看工作区状态和目标文件现状；保留所有既有改动，不覆盖、不清理、不回滚与本任务无关的用户工作。

## 2. 设计与实现的控制原则

### 2.1 内核边界按职责与证据决定

内核保留运行插件系统所需的最小稳定原语：进程/应用宿主、配置与数据访问的受控接口、Agent 执行循环及消息协议、工具调用协议、注册/调度基础设施、授权与安全边界、持久化/事件基础、LLM 通信协议和必要 UI 宿主扩展点。具体能力是否留在内核，须逐项说明“不能插件化”的原因；不能仅以当前调用方便、已有静态 import 或暂时没有替代实现为依据。

仓库现有 13 个核心工具候选（`read/write/edit/apply_patch/glob/grep/bash/task/task_status/todowrite/question/skill/tool_search`）是**审查清单，不是不可变名单**。逐个区分执行/安全原语与领域能力，记录保留、拆分或迁移结论及证据。

### 2.2 单一生产路径与有限兼容桥

所有第一方与明确支持的第三方插件通过同一套 Manifest、Host、注册表、生命周期和贡献冲突/覆盖规则运行。旧 custom tools、Extension、旧 Plugin hooks 可以按迁移需要暂时适配，但对于任一能力只能存在一个生效的执行路径：不得同时注册、双重调用或让旧路径作为长期旁路。每条兼容桥都要登记所有者、迁移任务、行为对照测试和删除条件。

### 2.3 动态调整必须有证据

阶段 0 的差距矩阵以代码、测试和运行路径为证据，而不是把计划描述当作当前事实。已有的 Manifest/API、贡献注册表、Host 原型和能力上下文先验证其真实边界、调用方式、资源所有权及测试覆盖；只补生产缺口，不重复造已有部件。任何阶段因新证据改变顺序或设计，记录原因、影响的验收项和新的回归范围。

## 3. 阶段计划与退出门槛

所有阶段按依赖 DAG 的可交付切片推进；下列次序是默认约束，不取代阶段 0 产出的真实依赖 DAG。阶段门槛未通过，不进入依赖它的调用点迁移。每个 milestone 的专项门禁不能替代全仓回归。

### 阶段 0：建立基线、边界与差距矩阵（M0 前置）

**产物**

1. 以 `plugin-system-unification-design.md` 的 D1–D9、B1–B3 为目标基准，逐项建立状态矩阵：未实现、原型、部分接线、生产可用、已验收。每个状态附对应源码、调用链、测试和运行证据；找不到证据就标为未验证。
2. 形成内核职责表、能力候选表和 import/调用依赖 DAG。每个候选记录：当前实现、消费者、贡献类型、capability、宿主范围、迁移风险、旧桥及其删除条件。
3. 执行并记录 `kernel.manifest.json` / B1 边界扫描当前基线；区分真实依赖违规与待迁移技术债，不以移动文件掩盖依赖。
4. 审核现有 Host 原型、Effect Layer、InstanceState、handler/ToolRegistry 组装和 `plugin_state` 持久化现状，明确原型与生产行为的差异。M0 只补通用运行时地基，不要求重做已满足验收的组件。
5. 核验插件 API、贡献种类、能力模型和 D1–D9 的设计一致性；本轮未实现的 Super-Agent contribution 不作为插件阶段的先决条件或通过项。

**退出门槛**

- 基线矩阵和依赖 DAG 经代码证据支持；候选内核边界和兼容桥均有书面理由。
- Host 的实例作用域、资源所有权、启动/关闭和故障恢复方案已明确。
- B1 扫描可重复运行，当前违规有分类和责任阶段；不得静默扩大 kernel 白名单。
- M0 已有能力不重造；未有能力不以“原型存在”标记完成。

### 阶段 1：接通 instance-scoped Runtime Host 与 HTTP 生命周期（补齐 M0 生产接线）

**实施范围**

1. 在实例 HTTP API 的 Effect Layer/服务图中构造并共享唯一的 instance-scoped Runtime Host。handler、ToolRegistry、诊断查询必须取得同一实例 Host；不得使用全局 Host、按请求重复创建 Host，或伪造 `InstanceRef` 绕过 Effect 生命周期。
2. 固化 Host 的状态模型、插件激活去重、资源所有权、错误诊断和关闭清理。明确其与 instance/server 生命周期的关系，并覆盖多实例并发与实例释放。
3. 让 plugin toggle 从仅写 enabled 状态变成真实状态转换，定义状态和持久化顺序：
   - 启用：校验 → `activating` → 建立资源/贡献 → 激活成功后持久化 `enabled` 并发布 generation/change；失败时释放部分资源、保留一致的 disabled 状态并报告诊断。
   - 停用：进入 `draining`，阻止新调用；按约定等待或取消在途调用；释放订阅、计时器、资源与贡献；成功后持久化 disabled 并发布变更。
   - 同一插件的并发切换串行化且幂等；数据库写入、资源释放或事件发布失败时，定义补偿/恢复行为，不允许 API、数据库和 Host 长期显示互相矛盾的状态。
4. 明确 list/diagnostics 对 discovered、validated、activating、active、draining、disabled、failed、overridden 等状态的含义；诊断输出插件来源、错误、贡献和相关 generation。
5. 将 in-flight 行为写入契约：当前轮持有的快照可在既定边界内完成；停用期间不接受新调用；下一轮必须读取新快照。不能把“当前轮不崩”解释为插件释放资源后仍能继续调用，也不能要求同步热更新所有已经开始的操作。

**退出门槛**

- HTTP API 测试覆盖 enable/disable、激活失败、重复请求、并发切换、实例隔离、释放清理和诊断状态。
- 实际 handler 与 ToolRegistry 证明使用同一个实例 Host；无全局单例或绕过 Effect 生命周期。
- toggle 真正改变后续可见贡献；停用资源释放后无残留；D7/D9 的后端契约通过。
- 不需要重启既有服务来完成测试；若真实环境验证需要重启，停止并按操作约束报告未验证。

### 阶段 2：收敛注册/执行路径，迁移 Tool、Agent、Skill、Command（M1）

**实施范围**

1. 逐一清点 ToolRegistry 中 legacy custom tools、Extension、旧 Plugin hooks、Runtime contributions 的注册和执行路径，画出迁移前/后的单路径图。合并重复的兼容桥任务清单；对每种旧机制明确迁移批次与可删除条件。
2. 建立统一的贡献解析、命名、排序、冲突/override、默认值和安全策略。任何能力不得在 Runtime contribution 与 legacy 路径双重出现；冲突必须有确定结果和诊断。
3. 引入可验证的 registry generation/cache invalidation：并发调用持有不可变快照；热切换对新调用生效；在途调用遵循阶段 1 的 drain/完成规则；缓存及 Effect 服务作用域不跨 instance 污染。
4. 将 Tool、Agent、Skill、Command 纳入同一插件生命周期，并覆盖 MCP/Skills 组合等实际消费者；保留主循环所需的稳定协议与安全控制，不为迁移而增加不必要的 Agent Loop 分支。
5. 按依赖与调用证据逐项减少 `session/prompt.ts` 等入口对 team、memory、office、cron 等具体实现的静态依赖。按场景选用同步稳定 API、注册表或异步事件，不把所有交互强制改成事件；每条路径有替代行为测试。
6. 对 13 个核心工具候选逐个提交边界结论和迁移测试，不要求整组同批迁移。

**退出门槛**

- D1、D2、D7、D8、D9 的相关端到端测试通过；`tool_search`、提示词、Agent/Skill/Command UI 与实际执行结果一致。
- 旧桥在其负责能力迁移后删除，或登记有明确外部兼容理由；无双重执行、隐藏 fallback、静态能力目录。
- 当前快照/下一轮快照、覆盖插件停用后内置贡献恢复、实例间缓存隔离有自动化测试。

### 阶段 3：迁移 Provider 与领域能力（M2–M4；按依赖 DAG 切片）

**建议的切片，不是刚性顺序**

1. Provider/模型适配与 transform；
2. Office 格式、engine、读写、previewer；
3. Scheduler、event source 及 memory/knowledge/database；
4. Browser/computer/media；
5. Integrations；
6. Team/workflow 与其他可替换领域能力。

实际顺序以阶段 0 依赖图、共享文件冲突和可独立验收的垂直切片为准。Scheduler/event source 在本轮只按通用插件贡献接入，不因此实现 Super-Agent 的 Trigger/Router/Thread 语义。迁移 Team/Workflow 时保留已有生产行为、数据协议和执行语义；先记录行为基线，再切换其能力实现，不把现有产品化语义误当作待重写的基础设施。

**每个能力切片必交付**

- 一份调用点/依赖图和当前行为基线；
- Manifest 与 contribution/capability 契约；
- 安装、激活、调用、停用、重新启用、诊断测试；
- 权限缺失、缺凭证、外部服务失败和资源释放路径；
- 旧静态分发/旧桥移除证明；
- 对应的 D 项映射和 B1 扫描结果。

Provider 与 Office 分别通过 D3、D4 及其契约测试。其他类型的验收矩阵必须在开工前补充；不能因暂无专门 D 编号而免除契约测试。

### 阶段 4：宿主 UI、发布驱动、打包与默认发行组合（M5）

**实施范围**

1. 把 UI view/rail/settings、previewer、tool result renderer、publish driver 等接入插件贡献模型；明确 UI 扩展隔离边界，不因采用 Solid ESM 就默认认为插件代码安全或可热卸载。
2. 覆盖实际宿主面（server/web、desktop、TUI/CLI 中适用的部分），明确哪些 contribution 能力由哪个宿主支持、缺失时的诊断和降级行为。所有支持的宿主都走同一 Manifest/Host 契约，不允许 UI/桌面端另设静态能力清单。
3. 将默认发行组合作为版本控制中的 manifest/lock 或等价机器可验证配置，列明内置插件、版本、必选/可选、默认启用状态和兼容约束。
4. 建立黄金产品路径：干净安装 → 显示默认能力 → 缺模型凭证时给出配置引导 → 配置后完成核心会话与文件工作流 → 停用可选插件后相关能力消失、基础体验仍可用 → 重新启用恢复。
5. 覆盖安装/发现、启停、依赖缺失、无凭证引导、升级/降级兼容、失败恢复和默认组合升级。可选插件不能使核心启动不可用；不可恢复错误应给出清晰诊断。

**退出门槛**

- D5、D6、D7、D8、D9 及目标宿主的集成验收通过；默认发行组合满足定义的黄金路径。
- UI 能反映安装/启用/缺依赖/失败/覆盖状态，且与后端 Host/generation 一致。
- 真实 UI 验证按第 5 节约束执行；无法验证的部分明确登记，不得用构建成功代替 UI 验收。

### 阶段 5：整体验收与“万物皆插件”结项

1. 在独立 fixture/worktree 中运行 D1–D9，检查每项禁止修改文件；所有未通过项列为未完成，不以人工检查或局部测试替代。
2. 执行 B1–B3：依赖方向、性能预算、资源泄漏/并发/错误恢复及全仓回归。性能报告至少拆分插件发现/manifest 解析、激活、启动总开销和每轮拦截器开销；以设计文档 §0.3、§15.4 为权威预算（20 个插件冷启动新增开销 < 400ms、每轮拦截器总开销 < 15ms、停用无残留定时器/监听），并记录测试机器、缓存状态、计时边界和重复测量结果。若预算定义与实现测量口径冲突，先修订设计并统一 CI 门禁，不得任选较宽口径报通过。
3. 全仓验证按仓库约定运行：root lint/typecheck；在 `packages/novaway` 运行全量测试；在 `packages/app` 运行构建及获授权的 UI 测试。专项 `verify:plugins` 不能替代以上门禁。
4. 审核内核职责表、真实 import/调用图和默认发行组合：不存在静态能力目录、静态分发分支或绕过 Host 的第一方执行路径；仍保留的内核原语均有记录理由。
5. 只有 D1–D9、B1–B3 及适用的全仓回归全部满足，才将本计划标记完成。受运行约束或环境阻塞而未运行的测试记录为“未验证/阻塞”，不是通过。
6. 本阶段完成即结束“万物皆插件”计划。本计划不包含 Super-Agent 的实现验收或交错排期。

## 4. Host toggle 状态与故障恢复约定

此表是阶段 1 的实施输入；具体状态类型可按现有代码调整，但语义不能缺失。

| 场景 | 必须保持的行为 |
| --- | --- |
| 首次启用 | 同一插件只激活一次；贡献/资源建立成功后对后续请求可见。 |
| 部分激活失败 | 释放已取得资源；不发布 active；诊断保留失败原因和可重试状态。 |
| 重复/并发启用 | 幂等，不能重复注册贡献、重复启动 watcher 或覆盖已完成状态。 |
| 停用 | 先阻止新调用，再按契约 drain/取消在途调用，最后逆序释放资源和贡献。 |
| 释放失败 | 明确进入 failed/cleanup-pending 等诊断状态；提供重试/实例关闭清理机制，不谎报完全停用。 |
| 持久化失败 | 通过补偿或恢复流程使持久化状态与实际运行状态最终一致；API 返回可诊断失败。 |
| generation 更新失败 | 不暴露半更新快照；保持旧快照或完整提交新快照，并使后续请求可恢复。 |
| 实例关闭 | 所有该实例插件资源逆序释放；不得影响其他实例。 |

## 5. 验收矩阵与验证约束

| 验收层 | 必须证明 | 不能替代它的证据 |
| --- | --- | --- |
| 单元/契约 | Manifest 校验、贡献冲突、capability、生命周期、错误映射 | 文件存在或类型通过 |
| 架构门禁 | B1 扫描、依赖 DAG 与允许边界 | 目录名叫 `plugins` |
| API/运行时集成 | 实例 Host、toggle、generation、诊断、恢复 | registry 单测 |
| D1–D9 行为演练 | 不改指定内核文件即可添加/停用/覆盖并观察实际行为 | 设计文档、手动 mock |
| B2 性能/泄漏 | 指定环境、插件数量和计时边界下的可重复结果 | 未说明环境的单次计时 |
| B3 全仓回归 | lint、typecheck、novaway 全量测试、app 构建；适用的宿主测试 | 插件专项门禁 |
| UI/发行体验 | 默认发行组合和目标宿主黄金路径 | 编译通过或截图 |

涉及 UI 或本地开发服务的测试若需要重启既有进程，立即停止该项，记录精确阻塞和未验证范围，等待用户授权；不得自行重启。

## 6. Super-Agent 后续独立路线
