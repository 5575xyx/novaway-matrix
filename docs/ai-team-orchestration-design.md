# AI 团队编排（Team Orchestration）产品设计

> 版本：v3（2026-10-29，补齐生产级门禁与差异化论证）
> 目标：把「AI 员工 → 团队 → 主智能体按团队编排」做成一套**可验证、可预算、可隔离、可观测**的生产级能力。
> 定位：团队是**持久的组织资产**，不是临时子代理；对外是一个**复合子代理**（brief in → report out），对内是一条**带验收与返工的确定性流水线**。
> 现有实现：`packages/novaway/src/team/*`、`packages/app/src/pages/team.tsx`、`handlers/team.ts`。
> 修订记录见 §23。

---

## 0. 执行摘要

1. **首版只做一个场景，先证明价值。** 首个场景是「针对一次代码变更，完成多角度只读审查，输出去重后、带复现证据的问题清单」。用户首次使用只需三步：选内置团队 → 填目标与预算 → 看结果。岗位 / 员工 / 编制三层在数据模型上保留，完整员工库放在高级入口，不要求用户先完成组织搭建才能拿到第一份结果。
2. **产品形态从「群聊」改为「控制面 + 一次编排」。** 团队页只做四件事：建团队 / 管名册 / 管模板 / 看运行历史；页面里的对话框移除。真正的对话发生在主聊天区，由输入框旁的**团队选择器**决定这次会话能调用哪些团队。
3. **核心实体是 `TeamRun`，不是消息。** 一次编排 = 一份 Plan + 若干团队运行 + 每个团队的任务 / 报告 / 裁决 + 最终集成。所有环节可审计、可中断恢复。
4. **验收分三层，通过状态只能由验证环节写入。** 标准（含版本与验证方式）、证据（绑定代码快照与验证器版本）、结果（`pass / fail / unverified`）分开存；成员报告只表达「我认为完成」。主观质量必须有明确评分规则或指定责任人，**不存在「manual 就信任成员陈述」这条捷径**。
5. **四项硬约束先于功能：预算预占、隔离优先、权限交集、崩溃恢复到工具操作级。** 预算要「调用前原子预占 + 调用后结算」，否则并发调用会一起超支；隔离要先于多团队并行；权限必须是「会话 ∩ 项目 ∩ 团队 ∩ 任务范围」的交集，且不能靠换成权限更高的员工绕开；崩溃恢复要能回答「这个工具到底执行没执行」。
6. **差异化表述要更正。** CC 的 agent teams 已经包含队长 / 成员、共享任务、任务依赖、跨成员权限同步，「比 `task` 子代理强」不足以支撑「独有」。本方案可辩护的优势是：**可复验交付（验证器 + 证据与代码快照绑定）、预算硬约束、崩溃后可恢复、团队模板可复用与跨团队产物版本管理**。这些必须由对照实验证明，见 §17。
7. **岗位、人、编制三层要分清。** 岗位（agent）是能力模板，员工（人）是具体的人，编制是团队里的一行。同一个岗位可以有多个不同的人（A 团队的产品经理是小明，B 团队的是小红），同一个人也能进多个团队；会话只是这次 run 的工作现场，不是身份。
8. **可靠性属于首个可用版本，不是后续打磨。** 格式错误、超时、权限阻塞、进程重启、取消，这五种情况在阶段一就要有明确定义的结果。
9. **「生产级」被拆成六个可判定门禁（G1–G6）**，见 §18；每个门禁都有验证方式、现有基础、缺口和所属阶段，做不到判定的不算达成。发布还要过 §21.3 的七条门禁。
10. **卖点不是「多代理团队」，而是「可复验交付 + 成本可控 + 可本地审计 + 组织可复用」**，见 §20。前三者是工程活，竞品缺乏动力做；后者沉淀为用户资产，换产品等于放弃积累。§17 的 A/B/C 对照实验负责证明它，文档不负责宣称。

## 1. 背景与问题

### 1.1 现状

当前已有：

| 能力                                                                                                                                       | 位置                                |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------- |
| 团队与名册（`Team` / `Member`，成员目前挂在会话上，待迁移为「人」）                                                                        | `packages/novaway/src/team/team.ts` |
| 共享任务板（`pending / in_progress / completed / failed / cancelled`，`blocks` / `blockedBy` / `claim` / `ready`）                         | `src/team/task-list.ts`             |
| 邮箱（`send / drain / list / team`）                                                                                                       | `src/team/mailbox.ts`               |
| 团队 HTTP 接口（list/create/detail/remove/member/message）                                                                                 | `handlers/team.ts`                  |
| 团队页（团队列表 + 成员 + 任务 + 群聊 + 发送）                                                                                             | `packages/app/src/pages/team.tsx`   |
| 内核侧工具（`team_create` / `team_delete` / `task_create` / `task_claim` / `task_update` / `task_wait` / `agent_message` / `task_status`） | `src/tool/*`                        |
| 用量汇总（按会话树归属）                                                                                                                   | `src/session/usage.ts`              |

### 1.2 现在这套跑不起来的地方

1. **控制面与观测面混在一起。** 邮箱同时承担「下指令」和「聊天记录」，页面上的输入框既像群聊又像派单，导致消息风暴、语义歧义、UI 无法区分指令/报告/闲聊。
2. **「完成」靠模型自评。** 队长说完成、主智能体说没完成，两次都是自由文本，无法逐条核对，也无法证明「这一轮到底改没改」。
3. **没有预算与上限。** `sendTeamMessage` 用 `forkIn` 直接拉起 `SessionPrompt.prompt`，无超时、无取消、无重试上限、无 run 记录；失败只写一条消息。
4. **权限会静默吃掉整条流水线。** 成员卡在确认框时页面只会「没有回复」，用户完全不知道发生了什么。
5. **并发无隔离。** 多团队同时改同一个仓库 = git index 冲突 + 测试互相污染。
6. **团队绑定会话。** `TeamTable.root_session_id` 让团队成为「某次会话的产物」，无法作为可复用的组织资产被主智能体跨会话调度；`team_create` 还强制一个根会话只有一个团队。
7. **成员与会话绑死。** `TeamMemberTable.session_id` 既是成员身份又是运行载体，带来两个后果：① 同一团队跑两次，两轮历史交织，队长和成员都会读到别人的上下文；② 一个「人」在结构上只能属于一个团队，无法表达「A 团队的产品经理是小明、B 团队的产品经理是小红」这种同岗位不同人的编制。

### 1.3 目标与非目标

**目标**

- 首版：一次代码变更的多角度只读审查，产出可复验的问题清单。
- 团队可被主智能体**跨会话、跨项目**按需调用（指定团队，后期 Auto 全集）。
- 一次编排从下达 brief 到最终交付，全程**可看、可停、可追问、可重跑**。
- 两级验收有清单、有证据、有上限、有裁决记录。
- 多团队并行时互不干扰，集成在**最终合并版本**上重新验收。

**非目标（本设计不做）**

- 不做「团队群聊」这种产品形态；团队页不提供对话输入框。
- 不替代内核现有的 `task` 子代理（单层委派仍然保留，用于轻量并行）。
- 不做跨机器分布式调度（本机进程内 + worktree 隔离即可）。
- 不引入云端账号、计费、远端编排服务。
- 首版不做：Auto 多团队、任务级工作区、员工级长期记忆、员工排名。

### 1.4 首个场景与首版边界

选场景的判断标准：**范围清晰、可复验、能与现有单代理方式直接对照、失败成本低**。

| 项       | 内容                                                                          |
| -------- | ----------------------------------------------------------------------------- |
| 场景     | 对一次变更（一个 PR / 一段 diff / 一个目录）做多角度只读审查                  |
| 输入     | 变更范围、审查维度（性能 / 安全 / 测试覆盖 / 代码质量）、预算                 |
| 输出     | 去重后的问题清单：每条含文件路径 + 行号、证据、影响、建议；允许「没发现问题」 |
| 不做什么 | 不改代码、不跑需要网络的命令、不触发外部副作用                                |
| 内置团队 | 「代码审查团队」模板，开箱可用，无需配置                                      |
| 对照基线 | 单 Agent 直接审查；单 Agent + 同等验证器（关键对照，见 §17）                  |

首版明确**不要求**用户理解岗位 / 员工 / 编制的区别：模板里已经编好，用户只填目标。高级入口才出现员工库与兼任规则。

## 2. 设计原则

| #   | 原则                     | 落地含义                                                                                                 |
| --- | ------------------------ | -------------------------------------------------------------------------------------------------------- |
| P1  | **团队 = 复合子代理**    | 对外只有 `brief → report`；内部循环（拆解 / 分配 / 判定 / 返工）封装在团队内，主智能体不感知             |
| P2  | **控制面 ≠ 观测面**      | `Task` / `Report` 驱动状态，`Note` 只给人看，永不影响调度                                                |
| P3  | **验收可复验**           | 标准带版本与验证方式；证据绑定代码快照；通过状态只由验证环节写入，成员自述不算数                         |
| P4  | **调度确定性**           | 循环、预算、超时、取消、状态持久化由内核 runner 负责；LLM 只产出内容                                     |
| P5  | **隔离先于并行**         | 团队间独立 worktree；团队内**写操作串行、只读可并行**；最终合并版本再整体验收                            |
| P6  | **失败可降级**           | 任何上限触发都产出「部分完成 + 卡点 + 需要用户决策」的结构化报告，绝不无限重试或静默挂死                 |
| P7  | **身份与工作分离**       | 员工是身份，run 才是工作；每次 run 使用任务级子会话                                                      |
| P8  | **可审计、可恢复**       | 每个工具操作有日志与检查点；能回答「执行了没有」；「回放历史」与「重跑得到同样结果」是两件事，不混为一谈 |
| P9  | **权限取交集，不可提权** | 有效权限 = 会话 ∩ 项目策略 ∩ 团队策略 ∩ 任务范围，由工具执行入口强制；换人不能换出更高权限               |
| P10 | **预算预占**             | 调用前原子预占、调用后结算；队长的返工额度与主智能体的驳回额度共享同一份累计上限                         |

## 3. 概念模型

```text
岗位（Job = Agent 模板，全局复用）              ← 内置角色 + 用户自定义
 └ 默认模型 / 系统提示词 / 工具 / 技能 / 权限提示
        │  1 个岗位可以被多个「人」认领
        ▼
员工（Employee = 人，全局员工库）                ← 设置 → AI 员工
 ├ id / name（小明、小红）/ job（产品经理）
 └ 覆盖项：model? / skills? / prompt? / tier / memory?
        │  同一个人可加入多个团队；同一个岗位可以有多个人
        ▼
TeamProfile（团队模板 = 编制的花名册）           ← 团队页管理
 ├ name / purpose / policy（预算·上限·权限画像）
 ├ roster[]：{ memberID, employeeID, job, role, order, canAutoDispatch, overrides }
 └ captain：必须恰好一个（指向 roster 中某个成员）

Mission（持久目标，可跨多次运行）                 ← 团队页 / 运行页
 ├ id（内部）/ number（M-001，单调分配、删除不复用）
 ├ goal / status（独立于任何一次运行的成败）
 └ baseSHA + worktree：第一次获准执行时准备，之后多次 Run 复用同一份
        │  1 个 Mission 可以有多次 TeamRun（这次没做好，下次接着做）
        ▼
TeamRun（一次编排，主聊天区触发）                 ← 选择器 + 主智能体
 ├ mode: team | auto
 ├ missionID?：属于哪个持久目标（临时任务可空）
 ├ goal / brief / acceptance[] / budget / deadline
 ├ plan：{ version, teams[]: { profileID, brief, acceptance[], deps[], artifacts[] } }
 │        └ 用户可见；批准绑定「plan 版本 + 团队范围 + 预算上限」三要素
 ├ approval：{ planVersion, approvedAt, approvedBudget }
 └ rounds：main→captain 最多 2 轮（计入共享累计尝试上限）

TeamRunTeam（一次团队运行，配置快照在此冻结）
 ├ rosterSnapshot[]：{ memberID, employeeID, job, name,
 │                     effective: { model, promptHash, skills[], permissionProfile } }
 │        └ 冻结本次实际生效的配置与版本，而不仅是名字和岗位
 ├ captainSession（任务级子会话）
 ├ tasks[]（扩展的 AgentTask：acceptance + assignee = 成员人）
 ├ rounds：captain→member 最多 3 轮
 ├ report / verdict / reworkReasons[]
 └ events[]（不可变日志）

TaskSession（任务级子会话）
 └ parentID = 本次 run 的主会话，继承成员的岗位 + 覆盖项 + 权限画像，run 结束归档
```

### 3.1 岗位、人、编制

这是本方案最容易搞混的一层，先定死：

| 层                          | 是什么                                               | 数量关系              | 例子                    |
| --------------------------- | ---------------------------------------------------- | --------------------- | ----------------------- |
| **岗位（Job / Agent）**     | 能力模板：提示词、工具、默认模型、技能               | 1 个岗位被 N 个人认领 | 「产品经理」            |
| **员工（Employee / 人）**   | 具体的人：名字 + 岗位 + 个人覆盖                     | 1 个人可进 N 个团队   | 小明（产品经理）        |
| **编制（Roster / Member）** | 团队模板里的一行：引用某个人，可加本团队内的职责说明 | 1 个团队有 N 行       | A 团队的产品经理 = 小明 |

推论：

- **同一个 agent 出现在不同团队，默认是不同的「人」**：A 团队的「产品经理」是小明，B 团队的「产品经理」是小红。两人能力模板相同，但名册、汇报线、用量、记忆、评价各自独立 —— 这是本设计的默认心智模型。
- **想让两个团队共用同一个人**也成立：两边编制行引用同一个 `employeeID`，模型里天然支持；此时他的**档期**需要排队（默认一个人同一时刻只干一个团队的活），见 §10.1。
- **一个团队内允许多个人同岗位**：A 团队可以有两个「产品经理」，但必须是两个不同的人（小明、小红），队长按职责与负载把任务派给其中某一个人。
- **同一个人在一个团队里只占一个编制**：需要「一人多角」时走单独的**兼任**规则（同一员工在多个团队任职是允许的，在同一团队重复占位默认禁止），见 §5.2。
- **团队之间互不感知**：小明在 A 团队的队长、任务、评价对 B 团队不可见；只有升到 Run 层（主智能体）才可能同时看到。
- **会话不是身份**：员工是持久的人，会话是这次 run 里的工作现场。同一个人被两个团队同时调用时，各自有独立的任务级子会话，互不污染上下文。

术语约定：

- **岗位（Job）**：能力模板，等价于今天的 `Agent`（提示词 / 工具 / 默认模型 / 技能）。
- **员工（Employee）**：具体的人，`name + job + 覆盖项`，存于全局员工库，可加入多个团队。
- **编制（Member / Roster slot）**：团队模板里的一行，引用某个员工；同一团队允许多人同岗位。
- **队长（Captain）**：编制中唯一的负责人；负责拆解、路由、裁决、返工、对上报。
- **主智能体（Main Agent）**：用户直接对话的会话；产出 Plan、发起 `team_run`、做最终验收。
- **Run**：一次完整编排；有 ID、预算、状态、事件日志。
- **Note**：人类可读的附带说明，**不参与任何判定**。

### 3.2 目标与运行分两层

「一次运行」和「一件长期的事」不是同一个东西。混在一起会导致：这次没做好，下次从零开始，用户积累的上下文和代码差异全部丢失。

| 层                  | 是什么                                         | 生命周期                                       | 例子                      |
| ------------------- | ---------------------------------------------- | ---------------------------------------------- | ------------------------- |
| **Mission（目标）** | 用户长期要达成的事：独立业务状态、稳定显示编号 | 跨多次运行存活；号码单调分配、删除后**不复用** | 「把下载流程改好」`M-003` |
| **TeamRun（运行）** | 一次编排：Plan → 执行 → 验证 → 交付            | 一次性；有预算、状态机、事件日志               | `M-003` 下的第 2 次运行   |

三条关键约束：

1. **工作区属于 Mission，不属于 Run。** 第一次获准执行的运行才准备工作区（worktree），此后多次运行**复用同一份工作区与同一个固定 `baseSHA`**；对外展示的是从 `baseSHA` 到当前内容的**累计差异**，而不是每次运行各算各的。
2. **状态互不推导。** 运行结束不自动完成目标；目标完成也不停止正在跑的运行。目标状态由用户或当前成员显式维护。
3. **编号只给人看。** 模型、工具与数据库统一用内部 id；`M-001` 只出现在界面上，不进提示词，避免模型拿编号做「ID 转换」的额外工作。

「跑完一次运行」「产生一份通过验收的交付」「把代码合并进主干」是**三件独立的事**：

| 动作       | 落点                            | 判据                                       |
| ---------- | ------------------------------- | ------------------------------------------ |
| 跑完       | `team_run.state` 进入终态       | 全部团队结束、预算结算完毕                 |
| 已验证交付 | `team_run.state = done`         | 合并快照上所有验收项都 `pass`              |
| 合并       | `team_run.merge_state = merged` | 显式合并动作成功；**不由验收结果自动触发** |

这条分层的意义在于措辞诚实：`done` 的界面文案应该是「**已验证交付**」，而不是「已完成」。

- **默认模式**：`指定团队 | Auto`，决定新会话选择器的初始值。

- **运行历史**是团队页的主要价值：点开一次运行，进入**运行看板**（§4.3）。

### 4.2 输入框团队选择器

位置：主聊天区输入框底部左侧、与「电脑控制」同一行；总控关闭时不占位。

```text
┌────────────────────────────────────────────────────────────────┐
│ 随便问点什么…                                                   │
│                                                                │
│ [+] ⚠ 跳过所有确认 ▾ │ [👥 团队：Auto ▾]  …   glm-5.3-flash  ➤  │
└────────────────────────────────────────────────────────────────┘
```

取值：

| 选项             | 语义                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| 不显示团队 chip  | 本次会话不注入团队目录，主智能体不会调用 `team_run`                      |
| 指定：`<团队名>` | 只注入该团队的目录与能力；主智能体可多次调用它                           |
| `Auto`           | 注入全部 `autoEligible` 团队的目录；主智能体可任选、可并行、可跨团队协作 |

行为约定：

- 选择即写入会话字段（`session.teamMode` / `session.teamIDs`），刷新与恢复后保持。
- 选择器只决定「可用哪些团队」，**不改变权限档位**；权限仍由输入框那份唯一开关决定，并被派生的任务级子会话继承。
- **Plan 审批的语义必须明确**（「可否决」和「必须批准」是两件事）：

| 模式     | 默认行为                       | 何时需要显式批准                                | 批准绑定什么                         |
| -------- | ------------------------------ | ----------------------------------------------- | ------------------------------------ |
| 指定团队 | 自动批准（不阻塞用户）         | 预估成本超过会话预算的 50%，或 brief 里含写操作 | `plan.version` + 团队范围 + 预算上限 |
| Auto     | **必须显式批准**，未批准不派发 | 始终                                            | 同上                                 |

- 批准是一次**带版本的授权**：Plan 被修改（加团队、改验收、改预算）即 `version+1`，旧批准失效，需要重新确认。超时未批准 → `awaiting_approval` 保持，不自动放行。
- 批准时冻结**预算上限**：执行中即使实际花费低于预估，也不允许超过批准上限；要超需重新批。

### 4.3 运行看板（Run Board）

从团队页的运行历史，或聊天区的运行卡片进入。

```text
┌ 运行 run_01J… · 代码审查 + 测试编排 ─────────────────────────────┐
│ 状态：审查中（第 2 轮）  预算 412k / 600k  墙钟 6m12s   [停止]     │
│ ┌ Plan ────────────────────────────────────────────────────────┐ │
│ │ ① 代码审查团队  deps: —      验收 5 条  ✅ 已交付             │ │
│ │ ② 测试编排团队  deps: ①       验收 3 条  🔁 返工中（2/2）      │ │
│ └──────────────────────────────────────────────────────────────┘ │
│ ┌ 测试编排团队 ────────────────────────────────────────────────┐ │
│ │ 队长判定 → 驳回：                                            │ │
│ │  ✗ AC-2 覆盖率 ≥ 80%：实测 72%（evidence: coverage.json）     │ │
│ │  建议：为 payments/refund 补边界用例                          │ │
│ │ 任务：补 refund 边界用例 → 成员「测试覆盖评估」第 2 轮          │ │
│ └──────────────────────────────────────────────────────────────┘ │
│ 事件流（可展开，只读）…                                          │
└──────────────────────────────────────────────────────────────────┘
```

看板要求：

- **每个「通过」都能点开看到证据**：验证器版本、绑定快照、实际输出；只有 `unverified` 的项会明确标注。
- **每个「驳回」都能看到 failed criteria 与建议**，以及它对应第几次尝试、消耗了多少预算。
- **每个阻塞都能一键跳到对应会话处理**，并标出「换成别人也没用」的动作（权限类）。
- 头部同时显示两类状态：**运行状态**（`running / blocked / paused / done / partial / failed / exceeded / cancelled`）与**当前阶段**（`executing / reviewing / reworking / merging` 等）。并行团队各自有自己的阶段，运行状态是它们的聚合（规则见 §8.1）。
- **「跑完」「已验证交付」「已合并」分开显示**：`done` 的文案是「已验证交付」，合并状态单独一行（`未合并 / 已合并 / 合并失败`）+ 独立的合并动作；不要用一个绿色勾把三件事混成一件（§3.2）。
- **成本分两列**：`已结算` 只统计提供方权威回报的用量；`用量不明` 按预占额保守计入额度上界，**不冒充实际花费**。超支判断看「已结算 + 用量不明 + 在途预占」之和。
- **截断要可见**：本轮上下文有省略项时（brief 被截、验收项超条数），头部显示「上下文有 1 处截断」并可展开（§6.4）。

### 4.4 阻塞与权限

- run 启动时按团队成员生成**权限画像**（见 §11），有效权限是「会话授权 ∩ 项目策略 ∩ 团队策略 ∩ 任务范围」。
- 局部阻塞不冻结整次运行：某成员等待确认时，无依赖的其他团队继续执行；只有**所有剩余工作都无法推进**时才进入全局 `blocked`。看板显示「运行中，2 项待确认」。
- **权限阻塞不能靠换人解决**：同一个受限动作不因为换成一个「权限更高」的员工就变得允许；换人只适用于能力不匹配、执行者失效、档期冲突。
- 同一动作被拒绝后，在本次运行内保持拒绝，不重复弹窗；要改判定必须由用户显式放行。
- 队长可以把被阻塞的任务**拆小或延后**，但必须在报告里记录 blocker 与等待时长；超过等待上限则上升给主智能体，主智能体再上升给用户。

## 5. 数据模型

新增表（Drizzle，扩展 `src/team/team.sql` 或新文件）。命名沿用现有 `snake_case` 列 + `camelCase` 领域对象。

### 5.1 `employee`（员工库：人）

| 列                          | 类型     | 说明                                                       |
| --------------------------- | -------- | ---------------------------------------------------------- |
| `id`                        | text PK  | `emp_…`                                                    |
| `name`                      | text     | 人名（小明 / 小红），团队内用于称呼                        |
| `job`                       | text     | 岗位，即原 `Agent` 名（`build` / `product-manager`…）      |
| `model`                     | text?    | 个人覆盖，缺省跟随岗位                                     |
| `skills`                    | json?    | 个人覆盖，缺省跟随岗位                                     |
| `prompt`                    | text?    | 个人补充提示词（叠加在岗位提示词之后）                     |
| `tier`                      | text?    | 成本档位（`fast` / `standard` / `deep`），供 Auto 路由参考 |
| `archived_at`               | integer? | 归档，不物理删除（历史 run 要能解析）                      |
| `created_at` / `updated_at` | integer  |                                                            |

唯一约束只对 `name` 做**建议性**校验（重名给出提示但不禁止），因为「小明」完全可能出现在两个团队。

### 5.2 `team_profile`（团队模板 = 编制表）

| 列                          | 类型          | 说明                                                                                |
| --------------------------- | ------------- | ----------------------------------------------------------------------------------- |
| `id`                        | text PK       | `tprof_…`                                                                           |
| `name` / `description`      | text          | 展示                                                                                |
| `captain_member`            | text          | 必须是名册里某个 `member_id`，且 role=captain                                       |
| `policy`                    | json          | `{ budgetTokens, maxCaptainRounds, maxMainRounds, permissionProfile, concurrency }` |
| `auto_eligible`             | integer(bool) | 是否参与 Auto 选择                                                                  |
| `version`                   | integer       | 编辑递增，run 记录所用版本                                                          |
| `created_at` / `updated_at` | integer       |                                                                                     |

`team_profile_member`（编制行）：

| 列                  | 说明                                                |
| ------------------- | --------------------------------------------------- |
| `id`                | `mem_…`，团队内唯一，**这才是成员身份**             |
| `profile_id`        | 所属团队模板                                        |
| `employee_id`       | 引用哪个人                                          |
| `role`              | `captain` \| `worker`；每个模板恰好一个 captain     |
| `duty`              | 本团队内的职责说明（同一个人在不同团队可以不一样）  |
| `can_auto_dispatch` | 是否允许 Auto 模式自动派活给这个人                  |
| `order`             | 展示顺序                                            |
| `overrides`         | json：本团队内的模型 / 技能覆盖（优先于员工级覆盖） |

约束与语义：

- `(profile_id, employee_id)` **默认唯一**。同一团队有两个产品经理，是指两个不同的人（小明、小红），本来就不冲突；不需要放宽唯一性。
- **兼任（同一员工在一个团队占两个编制）默认禁止**。确有需要时单独开启 `allow_concurrent_roles`，并对每个额外编制写明 `duty`；此时唯一约束退化为 `(profile_id, employee_id, duty)`，且两个编制不能同时是 captain。
- `(profile_id, id)` 唯一：成员身份在团队内不可重复使用。
- 删除员工时按 `archived_at` 处理；编制行保留引用，展示为「已归档」。
- 改名（小明 → 小明明）是员工级操作，所有团队同时生效；如果用户想让 A 团队叫别的名字，应新建一个人。
- 同一员工在**不同团队**任职不受此约束限制，那是常态。

**模板是「复制」，不是「绑定」**（这是不变量，不是实现细节）：

- 发起运行时，把名册与策略**复制**进 `team_run_team.roster_snapshot`；运行只认快照，**不读模板的实时内容**。
- 编辑模板（改名、换人、调策略）对**已在跑**的运行零影响；改动只作用于下一次运行。
- 删除模板不删除历史运行；正在跑的运行继续跑完，只是不能再基于它新建运行。

> 迁移：现有 `TeamTable` / `TeamMemberTable`（会话内团队）保留为**临时团队**的运行时形态。`TeamMemberTable` 需要一次表结构迁移：新增 `member_id`（PK）、`employee_id`（可空）、`job`、`duty`，并把 `session_id` 降级为可空的「会话缓存」字段（仅临时团队使用，不再作为身份）。

### 5.3 `team_run`

| 列                          | 说明                                                                                          |
| --------------------------- | --------------------------------------------------------------------------------------------- | ------ | ---------------------------------------------------------------- |
| `id` `run_…`                |                                                                                               |
| `session_id`                | 发起的主会话                                                                                  |
| `mission_id`                | 所属持久目标；临时任务可空（见 §3.2）                                                         |
| `directory`                 | 工作目录                                                                                      |
| `mode`                      | `team` \| `auto`                                                                              |
| `goal` / `brief`            | 用户目标 + 结构化 brief（json）                                                               |
| `acceptance`                | json 数组（全局验收，Auto 必填）                                                              |
| `plan` / `plan_version`     | json（团队清单 + 依赖 + 各自验收 + 产物声明）/ 版本号                                         |
| `approval`                  | json `{ planVersion, approvedAt, approvedBudget, approvedBy }`                                |
| `state`                     | 生命周期状态，见下表（**与团队阶段分开**）                                                    |
| `phase`                     | 聚合出的当前阶段（`executing / reviewing / reworking / merging / verify-merged`），仅用于展示 |
| `round_main`                | 主→队长轮次                                                                                   |
| `attempts`                  | json `{ business, formatRetry }`：**共享累计**尝试计数，换人 / 拆任务 / 新一轮都不重置        |
| `budget`                    | json `{ tokens, cost, wallMs }`（批准的硬上限）                                               |
| `usage`                     | json 快照 `{ reserved, settled, unknown }`（预占 / 已结算 / 用量不明三者分开）                |
| `merged_verification`       | json：最终合并版本的验收结果                                                                  |
| `merge_state` / `merged_at` | `unmerged                                                                                     | merged | merge_failed`/ 时间：**与`done` 无关\*\*，合并是独立动作（§3.2） |
| `context_manifest`          | json：每轮实际投喂给模型的内容与省略项（§6.4）；只在需要复盘判定时读                          |
| `started_at` / `ended_at`   |                                                                                               |
| `error` / `terminal_reason` |                                                                                               |

运行生命周期状态（终态加粗）：

| 状态                | 含义                                                  |
| ------------------- | ----------------------------------------------------- |
| `planning`          | 主智能体正在出 Plan                                   |
| `awaiting_approval` | 等待用户/主智能体批准（绑定 plan 版本与预算）         |
| `running`           | 至少一个团队可推进                                    |
| `blocked`           | **所有**剩余工作都无法推进（全部等待确认 / 等待依赖） |
| `paused`            | 进程重启后待用户决定继续或放弃                        |
| **`done`**          | 全部团队交付 **且** 合并版本通过全局验收              |
| **`partial`**       | 部分团队交付、部分达到上限；合并版本通过但覆盖面不足  |
| **`failed`**        | 无法产出可交付结果（关键团队失败且无返工额度）        |
| **`exceeded`**      | 预算 / 时间 / 尝试次数超限                            |
| **`cancelled`**     | 用户取消                                              |
| **`needs_review`**  | 存在「无法确认是否执行成功」的工具操作，需人工核对    |

`done` 的含义严格限定为「本次运行产出了一份在合并快照上通过全部验收的交付」，**不表示已经合并进用户分支**。
界面对应文案是「已验证交付」；合并状态由 `merge_state` 单独表达。

### 5.4 `team_run_team`

`run_id` / `profile_id`（临时团队时为空）/ `profile_version` / `state` / `round_captain` / `report`(json) / `verdict`(json) / `worktree` / `usage`(json) / `roster_snapshot`(json)。

`roster_snapshot` 冻结本次运行使用的编制**与当时实际生效的配置**。只冻结名字和岗位不够：模型、提示词、技能、权限画像变了，同样一份报告就无法解释。

```json
{
  "captain": "mem_A1",
  "policyVersion": 3,
  "members": [
    {
      "memberID": "mem_A1",
      "employeeID": "emp_xiaoming",
      "name": "小明",
      "job": "product-manager",
      "effective": {
        "model": "provider/model-a@1.2",
        "promptHash": "sha256:…",
        "skills": ["spec-review", "risk-analysis"],
        "permissionProfile": "review-readonly",
        "agentConfigVersion": 7
      }
    }
  ]
}
```

**快照给审计看，投影给模型看，两者不是一回事。**

`roster_snapshot` 可以很全（模型、提示词哈希、技能、权限画像），但**投进提示词的成员信息必须很小**：
只投影 `{姓名, 团队角色, 职责, 是否队长}`，不投影性格、忙碌状态、可用性、历史评价 ——
这些要么会诱导模型做「谁更靠谱」的推断，要么会泄露它不该用来做决定的信息。

已冻结的一次运行**不会因为名册变化被原位打补丁**：运行中途有人被归档，本次运行仍按快照里的身份与权限继续，
变化只影响下一次运行。

`team_run_team` 另存 `phase`（`queued / dispatching / executing / reviewing / reworking / merging / done / failed / blocked / cancelled`）、`depends_on`（团队 id + 依赖产物的版本）、`artifacts_out`（本团队产出的产物及其版本）。

### 5.5 任务扩展

复用 `AgentTaskTable`，在 `metadata` 中约定（避免大改表）：

```ts
metadata: {
  runID?: string
  memberID?: string // 编制成员（人）
  employeeID?: string // 员工（人）的全局 id
  job?: string // 岗位，便于按岗位统计与路由
  assigneeSession?: string // 该成员本次 run 的任务级子会话
  attempts?: { business: number; formatRetry: number } // 与 run 级共享计数同步
  acceptance?: Array<AcceptanceRef> // 见 §6.2；派发前必须补齐并通过校验
}
```

**任务注入按「自己的」截断，并且要能区分两种空：**

- 只注入当前成员在这次运行里**自己负责**的非终态任务；别人的任务不注入（队长看全队）。
- 注入受条数与字符预算限制。真实为空 → 明确写「当前无待办」；被上限截掉 → 写「另有 N 项未列出」，
  **不列出被排除项的 id**。
- 排序必须稳定（按 `order`），不能按更新时间抖动；否则同样的输入两次运行会看到不同的上下文，行为无法复现。

> 验收与证据**不放在任务 metadata 里长期保存**：它们要绑定版本、快照和验证器，字段会长得很快。任务只存引用（`acceptance_ids` / `verification_ids`），实体放独立的验证表（§5.7）。

### 5.6 `team_run_event`（不可变日志）

`id` / `run_id` / `seq` / `at` / `kind` / `payload`(json) / `lease_epoch`。

事件类型：`plan.created` `plan.approved` `task.assigned` `tool.started` `tool.finished` `report.submitted` `verification.recorded` `verdict.rejected` `budget.reserved` `budget.settled` `budget.exceeded` `blocked` `unblocked` `artifact.produced` `downstream.invalidated` `merged.verified` `cancel.requested` `cancel.settled` `checkpoint`。

约束：

- `seq` 单调递增；**状态与事件在同一事务里写**，不允许「状态改了但事件丢了」。
- 事件不可修改；更正靠追加新事件。
- 事件是审计真相源，但**不等于可重放执行**：回放只还原决策链，重跑是否得到同样结果需要另行定义（§8.5）。

### 5.7 验收与验证表

| 表                  | 关键列                                                                                                                                                         |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `team_acceptance`   | `id` / `run_id` / `task_id?` / `spec_id` / `version` / `text` / `kind`(`test\|diff\|file\|rubric\|human`) / `expected` / `verifier_id` / `owner`               |
| `team_verification` | `id` / `acceptance_id` / `attempt` / `snapshot_id`(代码树哈希) / `verifier_version` / `outcome`(`pass\|fail\|unverified`) / `measured` / `evidence_ref` / `at` |

关键点：

- **通过状态只写在 `team_verification.outcome`**，`Report` 里的说法只是声明。
- 每一份验证绑定 `snapshot_id`（git tree hash + worktree 路径 + 未提交改动摘要）。代码变了，旧证据自动失效。
- `verifier_id` 指向**受控验证配置**（不是报告里现写的命令）：`{ kind: "command", run: "bun test <paths>", timeout, env: "test" }` 或 `{ kind: "rubric", rubricPath, grader: "verifier-session" }` 或 `{ kind: "human", owner }`。

### 5.8 工具操作日志与检查点

| 表                    | 关键列                                                                                                                                                                           | 用途                           |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `team_run_op`         | `id` / `run_id` / `task_id` / `session_id` / `tool` / `idempotency_key` / `started_at` / `finished_at` / `outcome`(`ok\|failed\|unknown`) / `effect`(json, 脱敏) / `lease_epoch` | 回答「这个工具到底执行了没有」 |
| `team_run_checkpoint` | `run_id` / `task_id` / `seq` / `state`(json)                                                                                                                                     | 任务级断点，重启后从这里继续   |

`outcome = unknown` 的判据：进程在工具执行期间崩溃、或子进程被杀且没有拿到退出码。这类操作不得自动重跑，只能进入 `needs_review`。

### 5.9 账本

| 表                | 关键列                                                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `team_run_ledger` | `id` / `run_id` / `actor`(`captain\|member\|verifier\|integrator`) / `reserved_tokens` / `reserved_cost` / `settled_tokens` / `settled_cost` / `state`(`reserved\|settled\|released\|unknown`) / `at` |

账本两条规则：

1. **用量不明就记 `unknown`，不许补零、不许估算、不许拿预占额冒充花费。** 提供方没有回报用量时条目进入 `unknown`：
   不计入「已结算」，但**按预占额保守计入承诺量**，防止之后继续超支。
2. **承诺量 = `reserved + settled + unknown`**，并发判断与超支告警都只看这个和。界面必须分列展示「已结算」与「用量不明」，
   不允许合成一个「大约花了多少」。

## 6. 协议

### 6.1 三种信封

```ts
type Task = {
  id: string
  subject: string
  scope: { paths?: string[]; note?: string } // 影响面，用于占用登记
  acceptanceIDs: string[] // 指向 team_acceptance；派发前必须非空且全部校验通过
  inputs: { artifacts?: string[]; brief?: string }
  assignee: string // 成员 id（mem_…，指向「人」），不是岗位、不是会话
  job?: string // 岗位名；同岗位多人时由队长按此 + 负载路由
  budget?: { tokens?: number; wallMs?: number }
  deps?: string[]
}

type Report = {
  taskID: string
  claim: "done" | "partial" | "blocked" | "failed" // 成员自己的声明，不决定验收
  summary: string
  assertions: Array<{ criterion: string; basis: string; artifacts?: string[] }>
  artifacts: string[] // 文件路径 / 产物 id
  blocker?: { kind: "permission" | "missing_input" | "dependency" | "timeout"; detail: string }
}

type Note = { from: string; to: string; content: string } // 永不驱动状态
```

规则：

- 邮箱只承载 `Note`；`Task` / `Report` 走存储 + 调度器（页面展示时可附加 Note）。
- 成员报告里 `claim: "done"` **只是声明**；任务的最终状态由 `team_verification` 决定。
- 报告缺少任一 `acceptance` 项的 `assertions` → 调度器直接判「需补齐」，不经 LLM。

### 6.2 验收标准的三层

| 层   | 存哪                        | 内容                                                                               | 谁写                               |
| ---- | --------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------- |
| 标准 | `team_acceptance`           | 标准 ID、版本、验证方式（`test / diff / file / rubric / human`）、预期结果、责任人 | 主智能体出 Plan 时生成，用户可编辑 |
| 证据 | `team_verification`         | 关联任务与尝试、`snapshot_id`（代码树哈希）、验证器版本、实际输出、证据引用        | 验证环节                           |
| 结果 | `team_verification.outcome` | `pass / fail / unverified` + 实测值                                                | 验证环节                           |

```ts
type Acceptance = {
  id: string
  version: number
  text: string
  kind: "test" | "diff" | "file" | "rubric" | "human"
  expected?: string // 例如 "exit 0" / "coverage >= 80%" / "包含文件路径"
  verifier: VerifierRef // 受控配置，见下
  owner?: string // human / rubric 的裁决人
}

type VerifierRef =
  | { kind: "command"; run: string; timeoutMs: number; env: "test" | "sandbox" }
  | { kind: "rubric"; rubricPath: string; grader: "verifier-session" | "human" }
  | { kind: "human"; owner: string }
```

约束：

- **`verifier` 必须来自受控配置**，不能是报告里现写的任意命令；执行前校验命令白名单、工作目录与超时，禁止在验收阶段执行网络与写操作。
- **证据绑定快照**：`snapshot_id` = 提交树哈希 + 未提交改动摘要。任何验收都必须声明它验证的是哪个快照；后续代码变更会让旧证据自动失效。
- **`human` 与 `rubric` 不豁免**：`rubric` 必须给出评分规则与阈值，由独立 verifier 会话打分；`human` 必须指定责任人并等待其确认。**不存在「标记为 manual 就采信成员自述」的路径。**
- 验收项本身也要防诱导：优先写**覆盖面与证据要求**（「覆盖 X / Y / Z 三个维度，发现的问题必须附证据，允许没有发现问题，并说明检查范围与局限」），而不是「至少列出 N 个问题」——后者会诱导模型凑数。

### 6.3 裁决（Verdict）

```ts
type Verdict = {
  decision: "accept" | "reject" | "insufficient" // insufficient：证据缺失或无法验证
  failed?: Array<{ criterion: string; measured: string; suggestion: string }>
  notes?: string
  evidenceRefs?: string[] // 指向 team_verification
}
```

约束：

- `reject` 必须至少一个 `failed`，每项必须有 `measured` 与 `suggestion`；否则判无效，按 `insufficient` 处理并消耗一次格式重试（不消耗业务返工额度）。
- 裁决者默认是**独立 verifier 会话**（只给 brief + report + 证据元数据，不给完整聊天历史）；可配置为 `main` 亲裁。两种模式都不允许跳过 `team_verification`。
- 验收结论与代码快照不一致（例如快照变了）→ 自动 `insufficient`，要求重新验证，而不是沿用旧结论。

### 6.4 投喂给模型的上下文也要有账

队长判错，很多时候不是判断力差，而是**它看到的 brief 被截断了，而没人记录这件事**。所以每次派发都冻结一份 `context_manifest`：

| 字段            | 说明                                                              |
| --------------- | ----------------------------------------------------------------- |
| `brief`         | 实际投喂的 brief（截断后的，不是用户原始意图）                    |
| `acceptance`    | 本轮验收项的 `id + version`（全文在 `team_acceptance`，不重复存） |
| `rosterVersion` | 本轮使用的名册快照版本                                            |
| `feedback`      | 上一轮打回意见的原文                                              |
| `omitted`       | 被省略 / 截断的条目及原因（超预算、超条数、内容过长）             |
| `truncated`     | 布尔：是否存在截断；为真时界面必须显示，报告里也要说明            |

原则与 `unverified` 完全一致：**截断必须可见**。不允许「悄悄少给几条」，然后在复盘时怪模型没看到。

粒度取舍：只记 brief、验收 id、打回意见与省略项，不存验收项全文 —— 前者便宜且够用；后者只有在需要完整复盘
「为什么判错」时才值得，属于按需开启的高级诊断。

## 7. 上下文与成本

| 环节            | 传什么                                                   | 不传什么                       |
| --------------- | -------------------------------------------------------- | ------------------------------ |
| 主智能体 → 队长 | 结构化 brief：目标、范围、约束、相关文件、验收清单、预算 | 完整对话历史                   |
| 队长 → 成员     | 单个 `Task` + 必要 brief 片段 + 相关文件路径             | 其他成员的任务与报告           |
| 成员 → 队长     | `Report`（声明 + 证据引用）                              | 长篇过程叙述（留在会话里即可） |
| 队长 → 主智能体 | 团队级 `Report` + 验证结果引用                           | 成员原始消息流                 |
| 跨团队          | 结构化产物 + 版本（`api-schema.json@v2`）                | 团队间自由聊天                 |

### 7.1 预算：预占 + 结算

只在调用前「检查余额」不够：多个并发任务会同时看到余额充足，然后一起超支。做法：

1. 每次 LLM / 工具调用前，按**成本上界**向 `team_run_ledger` 原子预占（`state = reserved`）。
2. 调用结束后按实际用量结算（`settled`），释放多余预占。
3. 队长、成员、验证器、重试、集成**共用同一份运行账本**。
4. 预留一部分额度给验收与收尾（默认 15%），避免「活干完了但没钱验收」。
5. 供应商无法给出成本上界时，明确允许的超额比例（默认 10%），超了即 `exceeded`。
6. **用量拿不到就不许编。** 提供方没有回报实际用量时，条目记 `state = unknown`：不计入「已结算」，但按预占额
   保守占住额度。承诺量 = `reserved + settled + unknown`。这一条把「成本敢说出口」变成可核对的事实，而不是一个估算值。

### 7.2 尝试预算共享，不按轮次赠送

两级循环会相乘：主智能体每次驳回，队长又获得完整的内部返工额度。因此：

- `attempts.business` 按**原始交付目标累计**，换人、拆新任务、进入新一轮**都不重置**。
- `attempts.formatRetry` 单独计数（格式不对、字段缺失），默认上限 3，不影响业务额度。
- 上限是**整个 run 的**：`business ≤ maxBusinessAttempts`（默认 6），而不是每题 3 次 × 2 轮 = 6 次给到每个任务。

### 7.3 默认值：实验配置，不是产品承诺

| 项                       | 实验起始值 |
| ------------------------ | ---------- |
| 单任务 tokens            | 60k        |
| 单团队 run tokens        | 200k       |
| 单次编排 tokens          | 600k       |
| 业务尝试上限（整个 run） | 6          |
| 格式重试上限             | 3          |
| 单团队墙钟               | 30 min     |
| 单次编排墙钟             | 90 min     |

这些数字**需要实测校准**，不作为产品默认值对外承诺。用户侧展示的是：

- 预计费用**区间**（低 / 高），而不是精确值；
- 预计**时间范围**；
- **硬上限**（超过即停，并输出降级报告）。

## 8. 核心流程

### 8.1 状态机（运行状态与团队阶段分开）

运行（`team_run.state`）是聚合结果：

```text
planning ─▶ awaiting_approval ─▶ running ─┬─▶ done
     │              │                    ├─▶ partial
     │              └─(否决)─▶ cancelled  ├─▶ failed
     └─▶ cancelled                        ├─▶ exceeded
                                          ├─▶ needs_review
                                          ├─▶ paused ──(恢复)──▶ running
                                          └─▶ blocked ──(处理)──▶ running
```

团队（`team_run_team.phase`）各自独立推进：

```text
queued ─▶ dispatching ─▶ executing ─▶ reviewing ─┬─▶ merging ─▶ done
             │              ▲                    │
             │              └── reworking ◀──────┘
             └─▶ blocked ──(处理)──▶ executing
                        └─▶ failed / cancelled
```

聚合规则：

- `running`：至少一个团队可推进（执行 / 评审 / 返工 / 合并）。
- `blocked`：**所有**未完成团队都在等待确认或依赖，没有任何可推进的工作。
- `done`：所有团队 `done` **且** `merged_verification.outcome = pass`。
- `partial`：部分团队完成、部分达到上限；合并版本通过验收，但覆盖面不足以称完成。
- `failed` / `exceeded` / `cancelled` / `needs_review` 为终态（`needs_review` 可转为任意终态，需人工确认）。

### 8.2 单团队模式（指定团队）

```text
用户消息（选择器 = 代码审查团队）
 → 主智能体：是否调用 team_run？（可先追问，可先只读）
 → team_run({ profile, goal, brief, budget })
   → Plan（团队、任务草案、验收清单、预计区间）→ 按 §4.2 决定是否等待批准
   → 派生 captainSession（任务级子会话）
   → 队长：拆解 tasks[]（每条 acceptance 必须非空且通过校验）
        → 按「人」派单：同岗位多人时按 duty 与当前负载挑一个
        → 每个人拿到本次 run 专属的任务级子会话
   → 成员执行 → Report（声明 + 证据引用）
   → 验证环节写入 team_verification → 队长裁决
        ├ accept → 团队 Report
        └ reject → 重排（可换同岗位的另一个人），消耗共享业务额度
 → verifier 复验 → 主智能体汇总 → 回复用户
```

### 8.3 Auto 多团队模式

```text
用户消息（选择器 = Auto）
 → 主智能体产出 Plan（团队清单 + 各自 brief/acceptance + deps + 产物声明 + 预计区间）
 → 用户显式批准（绑定 plan 版本、团队范围、预算上限）
 → 按 DAG 分层并发：可并行的团队同时起（受全局并发与隔离策略限制）
 → 每个团队内部走 §8.2 的循环，产出团队 Report 与 artifacts_out（带版本）
 → 依赖满足后，下游团队以上游**指定版本**的产物作为 inputs
 → 主智能体验收：全部 accept → 合并 worktree → 在**合并结果**上跑全局验收 → done
   任一 reject → 打回对应队长（failed criteria + 建议）→ 该团队 reworking
```

### 8.3.1 同一岗位多人的路由

编制里有两个「产品经理」时，队长不能只说「交给产品经理」，必须落到具体的人：

```text
队长拆解出 Task
 → 若岗位只有一个人：直接派给他
 → 若岗位有多个人：
     1) 先看 duty（本团队内的职责说明）
     2) 再看当前是否忙（有 in_progress 任务的人排后）
     3) 再看 tier / 历史表现记录（只做参考，不做排名，见 §12）
     4) 仍无法区分 → 轮询分配，并在事件里记录理由
 → 派单写入 Task.assignee = memberID（人），而不是 job
```

跨团队同理：A 团队的小明和 B 团队的小红是**两个独立成员**，各自只出现在自己团队的编制里；主智能体在 Run 层看到的是「A 团队队长」「B 团队队长」，不直接指挥个人。

### 8.4 返工循环（累计额度）

```text
team:  拆解 → 分配 → 执行 → 收 Report → 验证 → 裁决
        ├ accept：交付
        └ reject：把 failed criterion 变成新 Task
                   （沿用原成员；若判定「能力不匹配」可换同岗位的另一个人）
                   attempts.business+1；超上限 → escalate（不重置）
        └ 格式问题（字段缺失 / 结构不合法）：attempts.formatRetry+1，单独上限

main:  收团队 Report → 验证结果核对 → 裁决
        ├ accept：进入集成
        └ reject：reworkBrief = { failed[], suggestions[] } → 团队重新进入 team 循环
                   attempts.business+1（与团队内返工共享同一计数）
                   超上限 → 降级报告

降级报告 = { 已完成项, 未达成项 + 实测值, 卡点, 已花费用, 建议的用户决策 }
```

### 8.5 取消、恢复、幂等

**取消的语义是三段式**，不能一收到请求就标 `cancelled`：

1. **停止新派发**：不再创建任务、不再起子会话；`state = running（cancelling）`。
2. **中断在途调用并回收**：取消 `Scope`、中断会话、回收受控子进程（shell / monitor / 浏览器）。
3. **记录已发生的影响**：把已写入的文件、已执行的工具、已花费的预算写进 `cancel.settled` 事件，然后才置 `cancelled`。

**恢复必须到工具操作级**，事件日志本身不够：

| 场景                       | 处理                                                    |
| -------------------------- | ------------------------------------------------------- |
| 工具未开始                 | 安全重跑                                                |
| 工具已成功、结果**已写库** | 不重跑（用 `idempotency_key` 查已有结果）               |
| 工具已成功、结果**未写库** | `outcome = unknown` → 进入 `needs_review`，禁止自动重跑 |
| 工具执行中被杀             | 视同 `unknown`，先核对副作用（diff / 文件 / 进程）      |
| 合并已开始但未完成         | 检查合并提交是否存在，必要时回滚                        |

配套机制：

- **任务级检查点**（`team_run_checkpoint`）：每完成一个任务写一条，重启从最近检查点继续。
- **状态与事件原子写入**：同一事务，避免「状态已改、事件没写」。
- **租约 epoch**：每个执行者持有 `lease_epoch`；租约失效后，旧执行者提交的任何结果都会被拒绝（防止僵尸进程覆盖新状态）。
- **幂等键**：`run_id + task_id + attempt + tool + 参数哈希`。

**「回放」与「重跑」在产品文案上必须区分**：回放只还原当时的决策链与证据，不保证重新执行会得到相同结果（模型、网络、依赖版本都可能变）。

### 8.6 下游失效（产物版本）

DAG 依赖关系不够用：上游返工改了接口，下游基于旧接口的「通过」必须作废。

- 每个团队产出 `artifacts_out`：`{ name, version, hash }`。
- 依赖记录的是**具体版本**：`deps: [{ teamID, artifact, version }]`。
- 上游产生新版本 → 找出所有引用旧版本的下游结果，标记 `stale`，其证据与裁决一并失效，需要重新验证。
- 合并阶段的全局验收会再兜一层：**任何 stale 结果都不能进入 `done`**。

## 9. 调度器设计

放在内核 `src/team/orchestrator.ts`（新增），职责只有「不变量」，不生成内容：

| 责任     | 说明                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------- |
| 循环     | 团队内轮次、主→队长轮次、DAG 依赖推进                                                               |
| 预算     | 调用前原子预占、调用后结算；超预占即拒绝发起调用                                                    |
| 尝试     | 维护共享的 `attempts.business` / `formatRetry`；换人与新一轮都不重置                                |
| 超时     | 每个任务带 `deadline`，超时归为 `failed(blocker=timeout)`                                           |
| 取消     | 三段式（停止派发 → 中断回收 → 记录影响）                                                            |
| 幂等     | 幂等键 + 检查点 + 租约 epoch                                                                        |
| 持久化   | 状态与事件同事务写；不可变事件日志                                                                  |
| 验证     | 只执行受控验证配置；绑定代码快照；记录验证器版本                                                    |
| 并发     | worktree 分配、团队内单写者、集成串行队列                                                           |
| 路由校验 | `assignee` 必须在 `roster_snapshot` 内；Auto 模式还需 `can_auto_dispatch`；同岗位多人必须显式指定人 |
| 寻址失败 | 快照里的成员已被归档 / 删除时，**整轮派发失败并列出问题成员**；不跳过、不静默改派给别人             |
| 失效传播 | 上游产物版本变化 → 标记下游结果 `stale`                                                             |

LLM 参与点仅四处：主智能体出 Plan、队长拆解 / 裁决、成员执行、verifier 裁决。其余全是确定性代码。

**一条硬规则（来自 §24.2 ① 的反面教训）：内核里不允许出现「屏障」类对象。**

| 禁止                                           | 原因                                                                                 | 允许的替代                          |
| ---------------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------- |
| 「等所有成员回复齐」的 barrier / gather record | 收齐才唤醒会把「一个成员慢」放大成「整轮卡住」，且必然要写「谁算回复、少一个怎么办」 | 队长在自己的运行内部决定何时汇总    |
| 回复计数、完成 Run、汇总唤醒                   | 内核一旦计数，就要为计数本身定义语义，规则会越叠越厚                                 | 队长通过任务板与验证状态自己判断    |
| 内核替成员把结果「拼」成队长的输入             | 拼接规则不可验证，且会掩盖某个成员其实没交东西                                       | 成员结果写进任务板/产物，队长自己读 |

判断标准很简单：**这段逻辑里如果有「数量」和「等」两个字，它就不该在内核里。**

反过来，跨轮次的「派发 → 验证 → 打回」是允许的，因为它等的不是「几条回复」，而是**验证器的确定结论**。

## 10. 隔离与并发

### 10.1 隔离先于并行

**首版采用「团队间隔离、团队内串行」**，不要在团队内并行写：

1. **团队级 worktree**：每个 `team_run_team` 一个 worktree（分支 `novaway/team/<run>/<profile>`）。
   - 注意 worktree 的边界：它有独立 `HEAD` 与 index，但**共享仓库对象**，也不提供进程与外设隔离。因此 worktree 不能替代写者串行。
2. **团队内写操作串行，只读可并行**：
   - 同一时刻只允许一个成员对团队 worktree 做写操作（编辑 / 依赖安装 / 格式化）。
   - 只读分析（读文件、跑只读检查）可以并行。
   - 理由：即使编辑不同文件，也可能同时改动 git index、lock 文件，或让测试读到别人未完成的改动。
3. **资源隔离**：测试端口、临时目录、测试数据库必须按团队分配（端口段 + `TMPDIR` + db 名后缀），并在任务环境里注入；路径占用登记**不能阻止工具越界写入**，只是第一道提示。
4. **成员级会话隔离**：每次 run 为每个编制成员派生一个任务级子会话（`parentID = run 的主会话`），run 结束归档。同一个人被多个团队同时调用时，各自拿到独立会话，上下文、待办、工具历史都不共享。
5. **员工并发额度**：一个员工同时参与多个 run 是允许的，用**可配置并发额度**（默认 2）限流，而不是「一人只能一个 run」。真正需要独占的是共享可变资源（员工级记忆、外部账号、独占设备），对这些资源加锁，而不是对人加锁。

> 任务级工作区（每个任务独立 worktree）留到有明确性能需求时再做，首版不做。

### 10.2 集成

- 队长把团队 worktree 合回集成分支；**集成由主智能体（或专职 integrator 角色）串行执行**。
- 合并冲突本身是一个**可验收任务**：`acceptance = [{ 测试通过 }, { 无未解决冲突标记 }, { 变更范围与计划一致 }]`。
- **合并后必须重新验收**：所有团队 `pass` 只是中间状态；只有在**最终合并版本**上跑通全局验收（构建 / 测试 / 静态检查）才能进入 `done`。
- 集成失败 → 生成返工任务回到对应团队，而不是让主智能体手工救火。
- 上游返工导致产物新版本 → 依据 §8.6 标记下游 `stale`，合并验收不得放行 stale 结果。

### 10.3 用量归属

会话不再兼做身份，用量按三个维度归档（每次 run 结束写快照，数据源是 `team_run_ledger`）：

| 维度                           | 用途                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| `run_id`                       | 一次编排花了多少（含失败尝试与验证开销），用于预算与历史对比 |
| `member_id`（+ `employee_id`） | 某个人在本次 run 干了多少；跨团队汇总到「人」                |
| `job`                          | 某岗位在所有团队里的总成本，用于性价比判断                   |

会话树仍可用于会话页面展示（任务级子会话挂在主会话下），但**成本归属以账本为准**，避免同一个人跨团队时被重复计算。

## 11. 权限与安全

### 11.1 有效权限取交集

```text
有效权限 = 会话授权 ∩ 项目策略 ∩ 团队策略 ∩ 任务范围
```

- 判断放在**工具执行入口**，由代码强制执行，不依赖提示词。
- 团队策略只能**收紧**，不能放大项目或会话的授权（团队配置不是提权通道）。
- 任务范围（`Task.scope.paths`）同样只能收紧：任务声明只读，成员就不能写。

### 11.2 阻塞、拒绝与换人

| 情形              | 能否换人   | 说明                                                           |
| ----------------- | ---------- | -------------------------------------------------------------- |
| 能力不匹配        | 可以       | 换同岗位的另一个人是合理的                                     |
| 执行者失效 / 超时 | 可以       | 重新派给其他人                                                 |
| 档期冲突          | 可以       | 排队或换人                                                     |
| **权限被拒**      | **不可以** | 换成「权限更高」的员工执行同一动作属于提权，必须由用户显式放行 |
| 缺输入            | 不可以     | 换人也没用，需要补输入或上升给用户                             |

- 同一动作的拒绝结果在本次运行内保持有效，不重复弹窗。
- 拒绝不可被 `catchCause` 吞掉；必须写 `blocked` 事件并出现在看板上。
- 局部阻塞不冻结整次运行（见 §4.4）。

### 11.3 证据与脱敏

之前的「命令、URL 永不落库」与「证据可展示、可复跑」冲突，改为分层的脱敏策略：

| 内容     | 处理                                                                              |
| -------- | --------------------------------------------------------------------------------- |
| 验证命令 | 保存**受控配置里的命令**（不含用户输入的秘密），执行时用脱敏后的环境变量          |
| 命令输出 | 保存摘要 + 前 N 行；命中秘密模式（token / key / password / URL 带凭据）时逐行打码 |
| URL      | 保存 host + path 模板；query 与凭据段替换为 `***`                                 |
| 环境变量 | 只保存变量名，不保存值                                                            |
| 原始秘密 | 永不落库；需要复跑时从运行时环境重新注入                                          |

看板上展示的是脱敏后的证据；用户明确点击「查看原始」时，从本地文件系统读取并只在界面显示，不进入数据库、不进入事件日志。

## 12. 可观测性

- **运行看板**：运行状态 + 当前阶段、轮次、预算（预占 / 已结算）、每个团队的任务 / 验证 / 裁决 / 证据。
- **事件流**：只读日志（`plan.created`、`task.assigned`、`tool.started`、`verification.recorded`、`verdict.rejected`、`budget.reserved`…）。
- **指标**（本地统计，不做遥测上报）：每次运行的成本、轮次分布、驳回原因 TopN、阻塞率、失败尝试占比、验证开销占比。
- **回放**：从事件日志重建决策链（「为什么它认为完成了」）。

### 12.1 员工表现的表述边界

员工维度的数据只做**事实记录**，不做排名：

- 记录：参与次数、返工次数、驳回原因分类、平均耗时、验证一次通过率。
- **不**输出「谁更好」的结论或排行榜：任务难度、依赖质量、验证严格程度都会污染这个指标，容易被误读成对人的评价。
- 想比较时，只能在同一类任务、同一套验收标准下比较，并在界面上明确标注样本量。

沿用现有 workspace 级 `/team` 命名空间（SDK 已生成 `client.team.*`）。

| 方法        | 路径                       | 说明                                                                                                |
| ----------- | -------------------------- | --------------------------------------------------------------------------------------------------- |
| GET         | `/team/profiles`           | 团队模板列表（含名册、策略、自动可调度）                                                            |
| POST        | `/team/profiles`           | 新建模板                                                                                            |
| PATCH       | `/team/profiles/:id`       | 改名 / 名册 / 策略（递增 `version`）                                                                |
| DELETE      | `/team/profiles/:id`       | 删除（有运行中的 run 时拒绝，除非 `force`）                                                         |
| GET         | `/team/runs`               | 运行列表（按团队 / 状态 / 时间过滤）                                                                |
| POST        | `/team/runs`               | 创建运行 `{ mode, teamIDs, goal, brief, acceptance?, budget }`，返回 `{ runID, plan, planVersion }` |
| GET         | `/team/runs/:id`           | 运行详情：状态 / 阶段 / plan / teams / tasks / verifications / verdicts / usage                     |
| GET         | `/team/runs/:id/events`    | 事件流（分页 / SSE）                                                                                |
| POST        | `/team/runs/:id/approve`   | 批准 Plan：`{ planVersion, budgetCap }`；版本不匹配返回 409                                         |
| POST        | `/team/runs/:id/rework`    | 主智能体打回 `{ teamID, failed[], suggestions[] }`                                                  |
| POST        | `/team/runs/:id/cancel`    | 三段式取消                                                                                          |
| POST        | `/team/runs/:id/resume`    | 从检查点恢复；存在 `unknown` 操作时要求先核对                                                       |
| GET         | `/team/runs/:id/artifacts` | 产物与版本（用于下游依赖与失效判断）                                                                |
| POST        | `/team/runs/:id/merge`     | 显式合并；与 `done` 独立，失败记 `merge_failed` 且可重试（§3.2）                                    |
| GET / POST  | `/team/missions`           | 持久目标：列表 / 新建（内部 id + 展示编号 `M-xxx`）                                                 |
| GET         | `/team/missions/:id`       | 目标详情：状态、关联运行、从 `baseSHA` 起的累计差异                                                 |
| POST        | `/team/missions/:id/runs`  | 在该目标下再发起一次运行（复用同一 worktree 与 `baseSHA`）                                          |
| GET         | `/employees`               | 员工库（人）：名字、岗位、覆盖项、归档状态                                                          |
| POST        | `/employees`               | 新建员工（人），指定现有岗位或新建岗位                                                              |
| PATCH       | `/employees/:id`           | 改名 / 换岗位 / 改覆盖项 / 归档                                                                     |
| GET         | `/employees/:id/usage`     | 这个人在各团队 / 各 run 的用量（事实数据，不做排名）                                                |
| GET / PATCH | `/team/orchestration`      | 总控开关、默认模式、员工并发额度（项目级配置）                                                      |

工具（主智能体侧，**只新增 1 个**）：

```ts
team_run({
  team?: string,                 // 省略时走 Auto 的 plan.teams
  goal: string,
  brief?: { scope?, constraints?, files?, context? },
  acceptance?: Acceptance[],     // 可省略：省略时由 Plan 生成，但派发前必须补齐并通过校验
  budget?: { tokens?, wallMs? },
  mode?: "team" | "auto",
}) => { runID, state, plan?, planVersion?, result? }
```

返回值语义：

- **同步能完成的短任务**：直接带回 `result`（团队 Report + 验证结果）。
- **异步长任务**：返回 `{ runID, state, plan, planVersion }` 句柄，主会话通过以下任一方式拿到结果：
  1. 工具内短轮询（默认等待 60s，超时返回句柄）；
  2. 完成时向主会话投递一条 `Note` + 结构化结果引用（复用 `background` 的完成通知通道）；
  3. 主智能体显式查询 `GET /team/runs/:id`。
- `state = awaiting_approval` 时句柄有效但不会推进，需要 `/approve`。
- 会话恢复（重启 / 切换分支）后，按 `runID` 重新关联；未完成的运行出现在会话的「进行中的运行」区。

### 13.1 关键约束（由代码强制）

- `acceptance` 可省略，但**派发前必须存在且校验通过**（非空、有 verifier、有 version）。
- 批准必须匹配 `planVersion`；Plan 一变即失效。
- `team_run` 不返回「消息已发送」这种模糊结果，只有 `result` 或 `handle`。
- `done` **不等于**已合并：合并有独立接口与独立状态，不由验收结果自动触发。
- 总控开关关闭时：**不删除任何数据、不停止已在跑的运行**；对模型返回 `team.feature_disabled` 与一句可执行话术
  （「团队功能已关闭，请改用普通对话继续」），而不是一个无解释的失败。

## 14. 与内核既有特性、CC 的关系

### 14.1 内核开关的边界

| 特性                          | 语义                 | 与本文关系                                                                 |
| ----------------------------- | -------------------- | -------------------------------------------------------------------------- |
| `teams`（`GET /kernel` 上报） | 团队工具是否加载     | 保持不变，本文不改它的含义                                                 |
| `team_orchestration`（新）    | 团队编排总控         | 关闭时 `team_run` 工具不注入、选择器隐藏                                   |
| `auto_delegate`               | 单会话内并行工具调用 | 开启 `team_orchestration` 且选择 Auto 时，**优先按团队派活**，避免双重委派 |
| `background_subagents`        | 子代理后台运行       | 本文的成员执行依赖它；关闭时 run 只能串行                                  |
| `plan_approval`               | 子代理计划审批       | Auto 的 Plan 关卡可复用这套 UI 与数据                                      |

优先级规则（写入系统提示词）：_当会话选择了团队时，优先把可结果化的任务交给 `team_run`；只有轻量、单文件、无验收需求的探索才使用 `task` 子代理。_

### 14.2 与 Claude Code agent teams 的差异（更正）

CC 的 agent teams 已经具备：队长 + 成员、共享任务列表、任务依赖（`blocks` / `blockedBy`）、跨成员消息、跨成员权限同步。因此：

- **不能说「独有」的是**：多代理团队、队长分派、共享任务、依赖管理。
- **可以主张的是**：

| 维度       | CC agent teams     | 本方案                               | 可验证方式             |
| ---------- | ------------------ | ------------------------------------ | ---------------------- |
| 交付可信度 | 任务由成员标记完成 | 验收三层 + 验证器 + 证据绑定代码快照 | 误判通过率（§17）      |
| 成本控制   | 无显式预算账本     | 预占 / 结算 + 共享尝试上限 + 硬上限  | 超支次数 = 0           |
| 故障恢复   | 进程级重启         | 工具操作级检查点 + 未知操作核对      | 崩溃注入测试           |
| 组织复用   | 会话内临时组队     | 团队模板 + 员工库 + 兼任规则         | 同一模板跨会话复用次数 |

差异化要靠对照实验证明，不能靠文档宣称。

## 15. 风险与开放问题

| 风险                       | 影响           | 缓解                                                                                              |
| -------------------------- | -------------- | ------------------------------------------------------------------------------------------------- |
| **两级评审互相放水**       | 「完成」不可信 | 独立 verifier + 逐条裁决 + 证据复跑 + 误判通过率指标                                              |
| **验收标准写不出来**       | 无法判定       | Plan 阶段强制生成；写不出就降级为 `rubric` 并给出评分规则，仍无规则则要求用户确认，**不采信自述** |
| **验收规则被诱导**         | 模型凑答案     | 用覆盖面 + 证据要求，禁止「至少 N 条」这类可凑数指标；允许「未发现问题」                          |
| **多团队合并冲突**         | 集成阶段爆炸   | 隔离先于并行 + 团队内单写者 + 串行集成 + 合并后全局验收                                           |
| **成本爆炸**               | 用户流失       | 预占 + 结算 + 共享尝试上限 + 硬上限 + 区间预估                                                    |
| **权限反复阻塞**           | 流水线停摆     | 权限交集 + 局部阻塞不冻结运行 + 拒绝持久化 + 上升路径                                             |
| **崩溃导致重复副作用**     | 数据损坏       | 幂等键 + 操作日志 + 检查点 + 租约 epoch + `needs_review`                                          |
| **提示词漂移**             | 队长行为不稳定 | 信封与裁决结构由代码强校验                                                                        |
| **首版范围过大**           | 交付不了       | 阶段一限定「只读审查」，其余进后续阶段（§16）                                                     |
| **临时团队与组织资产混淆** | 用户困惑       | UI 明确区分「临时团队（随会话）」与「团队模板（可复用）」                                         |
| **验证开销过高**           | 用户弃用       | 三档验证（轻 / 中 / 重）+ 同快照缓存；合并后强制重档（§19.1）                                     |
| **`unverified` 被折叠**    | 特色失效       | 硬规则：分列计数、降级措辞、禁止折算；代码审查门禁（§19.2 / §21.3）                               |
| **验证器本身不可信**       | 假通过         | 缺陷注入集 + 对照组的回归，作为发布门禁（§19.3）                                                  |
| **误判通过率靠自评**       | 数字失真       | 人工抽样 10–20% 复核，超阈值不放行（§21.3）                                                       |

开放问题：

1. 团队模板与员工库是否需要跨项目共享（全局库 vs 项目内）？
2. Auto 是否允许「发现没有合适团队时自动临时组队」？（首版不做）
3. 集成角色是内置 agent，还是用户可配置的员工？
4. 员工级记忆（跨团队长期经验）是否要做？若做，必须「按项目隔离 + 读取快照 + 提交时校验版本」，并在一次 run 内独占写入。
5. 同一个「人」在不同团队能否有不同称呼？当前为员工级统一名字，团队内用 `duty` 区分职责。

## 17. 验证与对照实验

上线前，用一批真实任务做三组对照，尽量固定模型、输入与验收标准：

| 组  | 配置                      | 作用                                             |
| --- | ------------------------- | ------------------------------------------------ |
| A   | 单 Agent 直接做           | 现状基线                                         |
| B   | 单 Agent + **同等验证器** | **关键对照**：把「质量提升」与「多代理协作」解耦 |
| C   | 团队编排                  | 本方案                                           |

指标：

| 指标                 | 说明                                           |
| -------------------- | ---------------------------------------------- |
| 可复验交付成功率     | 通过验证的任务占比（不是「成员说完成」的占比） |
| 误判通过率           | 标记通过但人工复核不通过的占比 —— 越低越好     |
| 每份合格交付的总成本 | 含失败尝试、验证、评审开销                     |
| 用户介入时间         | 用户从发起到拿结果需要操作几次、多久           |
| 端到端耗时           | 墙钟时间分布                                   |
| 异常恢复正确率       | 崩溃 / 取消 / 权限拒绝后能正确停止或恢复的比例 |

结果分层（照搬「先分类、再比较」的做法，避免用平均值掩盖失败）：

| 分层                                  | 含义                     | 允许发布什么               |
| ------------------------------------- | ------------------------ | -------------------------- |
| `both_pass`（A/B/C 都通过）           | 结果可比                 | 才允许比较耗时与成本       |
| `only_team_pass` / `only_single_pass` | 结果本身不同             | 只报结果差异，**不比成本** |
| `both_fail` / `indeterminate`         | 没通过，或证据不足以判断 | 什么都不发布               |

**「更快失败」不算效率。** 团队比单 Agent 先失败、或先给出错误结论，只能说明它崩得更快；一旦允许在 `both_fail`
里比较耗时，排行榜就会奖励错误答案。因此成本与耗时的比较**只在 `both_pass` 分层内**进行。

计量口径（缺一不可，否则数字不可比）：

| 字段     | 要求                                                                     |
| -------- | ------------------------------------------------------------------------ |
| 时钟     | 耗时只用同一个单调时钟的 派发→终态 区间；墙上时间戳不能冒充单调耗时      |
| 并发聚合 | 并行区间要区分「合并后的墙钟占用」与「各成员相加」，两者不能混用         |
| 用量来源 | token / 成本只接受提供方权威回报；**没有回报就是未知，不允许估算或补零** |
| 覆盖率   | 每个数字都带覆盖率；部分覆盖不得展示成完整账单                           |

决策规则：

- 若 **B ≈ C**，说明收益主要来自验收机制，而非团队协作 → 优先把验证器做进单 Agent，团队编排降级为可选能力。
- 若 **C 显著优于 B**，且成本可控 → 扩大 Auto 与多团队投入。
- 若 C 成本高而收益不明显 → 只保留「团队模板 + 单团队」，放弃 Auto。

结论也分等级，不能跳级说话：

| 等级 | 证据                                 | 可以说的话                     |
| ---- | ------------------------------------ | ------------------------------ |
| L1   | 单个对照 pair                        | 「这一次，团队版更好/更差」    |
| L2   | 多个预注册、结构一致的 pair          | 「在这个任务集上平均差异是 X」 |
| L3   | 未见过的留出集 + 盲评                | 「对这一类任务有有限泛化」     |
| L4   | 隔离环境 + 足够样本 + 预注册统计检验 | 才能说「协作带来了因果收益」   |

任何一级都不支持「更聪明」「通用能力更强」这类说法。

## 18. 生产级门禁（G1–G6）

「生产级」在本方案里不是形容词，而是**六个可判定的门禁**。每个门禁都要能用一个具体操作验证通过或失败；做不到判定的，不算达成。

| 门禁                    | 定义                                                                       | 判定方式                                                                                            | 现有基础                                             | 缺口                                                    | 阶段                     |
| ----------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------- | ------------------------ |
| **G1 交付可复验**       | 任一「通过」都能回答：在哪个代码快照、由谁验的、实测值是什么               | 随机点开一条 `pass`，能看到 `snapshot_id`、`verifier_version`、`measured`；改动代码后旧证据自动失效 | 无                                                   | `team_acceptance` / `team_verification` / `snapshot_id` | P1                       |
| **G2 失败有终态**       | 格式错、超时、权限拒绝、崩溃、取消五种情况都有明确结果，不存在「一直转圈」 | 逐项注入异常，运行必须落到 `failed / exceeded / blocked / needs_review / cancelled` 之一            | 部分（`catchCause` 会吞掉原因）                      | 运行状态机 + 异常映射表                                 | P1                       |
| **G3 崩溃可恢复**       | 能回答「这个工具到底执行了没有」；重启后可续跑或明确拒绝重跑               | 工具执行中途强制终止进程，重启后 `team_run_op` 必须列出该项为 `unknown`，且不自动重跑               | 无                                                   | 操作日志 + 检查点 + 租约 epoch                          | P1                       |
| **G4 成本有硬上限**     | 并发调用也不会超支；超限必降级                                             | 并发压测下 `reserved + settled ≤ cap`；超限产出降级报告而不是继续调用                               | `src/session/usage.ts` 的 `add / sum / delta / mark` | 预占 / 结算两态账本                                     | P1                       |
| **G5 不越权**           | 有效权限 = 会话 ∩ 项目 ∩ 团队 ∩ 任务范围，由代码强制，不靠提示词           | 构造越权任务（团队策略要求写、项目策略只读）→ 工具入口必须拒绝并写事件                              | `Prompt` 循环里的工具执行漏斗 + `Tool.Capabilities`  | 权限取交集；`Capabilities` 全量声明                     | P1（交集）/ P2（写操作） |
| **G6 不破坏用户工作区** | 取消或集成失败后无残留进程、无半成品、无重复副作用                         | 取消一次带写操作的运行，检查 `git status`、进程表、临时目录                                         | `src/tool/worktree.ts` / `worktree-helper.ts`        | 团队内单写者 + 合并后全局验收                           | P2                       |

### 18.1 可复用的现有锚点

三个已有机制让 G3 / G4 / G5 不需要从零造：

1. **唯一工具执行漏斗**：`src/session/prompt.ts` 里 `PreToolUse → execute → PostToolUse / PostToolUseFailure` 是一条串行路径（当前约 1170–1240 行）。操作日志埋点、幂等键生成、权限交集判定都挂在这里，不必改任何工具实现。
2. **worktree 工具**：`src/tool/worktree.ts` + `worktree-helper.ts` 已经能创建 / 切换 / 删除 worktree，P2 的团队级隔离直接复用。
3. **用量原语**：`src/session/usage.ts` 的 `add / sum / delta / mark / attribute / readMark` 已经能表达「按归属累加」，账本只需要在它之上加 `reserved / settled` 两种状态。

### 18.2 真正的硬缺口

仓库目前**没有任务级检查点**（`src/session/session.ts` 无 checkpoint / resume 概念）。这是 P1 里唯一需要新造的地基，也是最容易被低估工作量的一块：它不只是存快照，还要定义「从检查点继续」时哪些副作用已经发生过。

## 19. 验证开销与「未验证」的呈现

### 19.1 验证必须随任务规模伸缩

如果每个任务都全量重跑测试，产品会显得又慢又贵——用户第一次用完就会得出「不划算」的结论，然后这个能力再也不会被打开。按影响面分三档：

| 档位   | 触发条件                                | 验证方式                                                     | 预期开销     |
| ------ | --------------------------------------- | ------------------------------------------------------------ | ------------ |
| **轻** | 只读分析、单文件改动、`scope.paths` ≤ 2 | 结构校验（文件存在、含 `path:line`、diff 可读）+ 抽样 rubric | 秒级         |
| **中** | 改动命中某些目录，且能推导受影响测试    | 只跑受影响的测试子集（按 `scope.paths` → 测试映射）          | 与子集成正比 |
| **重** | 跨模块改动、依赖安装、合并后            | 无条件全量：构建 + 全量测试 + 静态检查                       | 分钟级       |

约束：

- 档位由**调度器按规则判定**，不由成员自报（否则一定会自报「轻」）。
- 合并后的全局验收**永远是重档**，不接受缓存与子集。
- 同一 `snapshot_id` 下命令类验收结果可缓存；缓存命中必须在 UI 上标注「复用同快照结果」，不能伪装成新验证。

### 19.2 `unverified` 必须可见，且不得折叠

这是差异化能否成立的关键点，写成硬规则：

1. **`unverified` 是合法终态**：验不了不等于失败，也不等于通过。
2. **报告必须分列计数**：「3 项通过 / 2 项未验证」，不允许合并成「5 项通过」。
3. **最终结论要降级措辞**：未验证项占比超过阈值（默认 30%）时，交付结论从「已完成」改为「已完成（部分未验证）」，并列出未验证的是什么、为什么没验。
4. **任何把 `unverified` 折算成 `pass` 的实现都是缺陷**，包括：默认值补全、接口层归一化、UI 层颜色映射、汇总时四舍五入。
5. **看板颜色规则**：`pass` 绿、`fail` 红、`unverified` 必须用**中性警示色**（不是绿、不是灰），并在图例里解释含义。

### 19.3 验证器自身要有回归

验收结论只有在验证器可信时才可信。rubric 写松了，`pass` 一样是假的。

- 维护一小批**已知有问题**的历史 diff（缺陷注入集）与**已知没问题**的对照组。
- 每次修改 rubric 或验证器版本，跑一遍回归：有问题的必须被判 `fail`，无问题的不能被误杀。
- 回归结果作为**发布门禁**的一部分（见 §21.3），不通过不允许上线。

**实现（2026-10-30）：** 判断逻辑抽到 `src/team/verifier.ts`，只保留两个纯函数 —— `prompt()`（问什么）
与 `interpret()`（怎么读）。读回结果时有两条硬规则：

1. 解析不了 JSON、或回答了 `pass`/`fail`/`unverified` 之外的值 → `unverified`，绝不默认通过；
2. **声称 `pass` 却没有给出证据位置 → 降级为 `unverified`**。没有证据的通过只是验证器在自说自话，
   与没验过没有区别；`fail` 不要求证据（否定结论不会把坏东西放过去）。

`evaluate(cases)` 计算缺陷集召回率与对照组误杀率，`GATE` 固定为「召回 ≥ 90% / 误杀 ≤ 5%」，
`gate(score)` 直接给出发版结论。夹具见 `test/team/verifier.test.ts`：10 条缺陷样本 + 20 条对照组，
另含「无证据的 pass」「乱码回复」「未知取值」三类边界。**新增规则先改夹具再改实现**，否则回归没有意义。

## 20. 差异化：可辩护与不可辩护

### 20.1 不可辩护的部分

| 主张                     | 为什么守不住                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------- |
| 多代理团队 / 队长 / 成员 | CC 的 `swarm/`、`SendMessageTool`、`TaskCreateTool` 的 `blocks / blockedBy` 已具备 |
| 共享任务板与依赖管理     | 同上，CC 已有等价物                                                                |
| 「更聪明的任务拆解」     | 提示词层面的东西，复制成本极低，而且效果不可测                                     |
| Auto 自动选团队          | 演示效果最好，但失误成本最高，且无法验证「选得对不对」                             |

把上述任何一条当卖点，用户一对照就会失分。

### 20.2 可辩护的部分（2026-10 修订：把「入场券」和「差异」分开）

**先更正一条过强的说法。** 我们此前把「证据绑定快照、`unverified` 不冒充 `pass`」当成竞品缺乏动力去做的事。
对照 Rovai-ai（见 §24）后必须承认：它已经把同一条原则写进产品宪法——「未知与部分状态要显示覆盖率与具体解释」
「缺失字段保持 unknown，永不变成 0」，并且同样把 Team/Solo 配对实验作为协作价值的唯一证据来源。

也就是说，**这两条已经是入场券，不是差异化**。任何把它们当卖点的表述，用户对照一下就会失分。真正还能守住的，
是在同一条原则之下**做得更细、更敢公开**的部分：

| 层级       | 主张                                                                | 判定方式                                        |
| ---------- | ------------------------------------------------------------------- | ----------------------------------------------- |
| **入场券** | 证据绑定快照与验证器版本；`unverified` 不折算成 `pass`；未知不补零  | 竞品也已具备，只能作为「不比别人差」            |
| **入场券** | Team/Solo 配对对照（同时固定模型、输入、验收标准）                  | 同上                                            |
| **可辩护** | 每条 `pass` 都能点开到**实测值 + 证据位置**，而不只是「有验证记录」 | 随机抽 10 条 `pass`，全部能追溯到具体命令与输出 |
| **可辩护** | 验证开销按影响面分档，用户看得见「为什么这次验得重/轻」             | 运行详情里每条验收带档位与判定理由              |
| **可辩护** | 成本同时给出**已结算**与**用量不明**两列，未结算按保守上界计入额度  | 超支次数为 0，且不存在被伪装成实际花费的估算值  |
| **可辩护** | 团队模板 / 验收标准库 / 历史证据三样资产可导出、可复用、可检索      | 同一模板跨会话、跨项目复用次数                  |

一句话：**同一条原则做到「每一条都能点开、每一个数字都有来源」，才算差异化。** 「我们也做了」不算。

### 20.3 一次投入，两个目标

「生产级」与「特色优势」在本方案里**不是两笔预算**：

```text
证据管线（G1）  → 既满足生产级「结果可信」，又构成「可复验交付」的卖点
操作日志（G3）  → 既满足生产级「崩溃可恢复」，又支撑「可本地审计」
预算账本（G4）  → 既满足生产级「不超支」，又支撑「成本敢说出口」
团队模板        → 既满足生产级「可复用」，又沉淀用户资产
```

反过来，为了「特色」先上 Auto 多团队，两条目标会同时落空：不可信的编排规模越大，用户损失越大，口碑越差。

### 20.4 迁移成本即护城河

用户在某个产品里积累了三样东西后很难离开：

1. **团队模板**（谁负责什么，怎么验收）；
2. **验收标准库**（这个项目的「合格」长什么样）；
3. **历史运行证据**（过去每次交付为什么可信）。

这三样都是**用时间换来的**，竞品无法通过一次更新提供。因此产品设计上要刻意强化它们的可积累性：模板可导出、验收标准可复用、历史证据可检索。

## 21. P1 落地清单与发布门禁

### 21.1 P1 的交付物（只做「可信的单团队审查」）

| #   | 交付                                                                                                       | 判定标准                                                      |
| --- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 1   | 内置「代码审查」团队模板（开箱可用）                                                                       | 新用户不配置任何组织，三步拿到第一份带证据的问题清单          |
| 2   | `team_acceptance` / `team_verification` / `team_run_ledger` / `team_run_op` / `team_run_checkpoint` 五张表 | 任一 `pass` 可点开看到快照哈希 + 验证器版本 + 实测值          |
| 3   | 工具操作日志（挂 `prompt.ts` 漏斗）+ 幂等键 + 租约 epoch                                                   | 强制终止进程后重启，能列出「已执行 / 未知」，未知项不自动重跑 |
| 4   | 预算预占 + 结算 + 共享业务尝试上限                                                                         | 并发压测不超支；超限产出降级报告                              |
| 5   | 三段式取消 + 任务级检查点                                                                                  | 取消后无残留进程；重启可续跑或明确拒绝续跑                    |
| 6   | `unverified` 在 UI 与报告中显式呈现                                                                        | 报告分列「通过 / 未验证」，未验证项可点开看原因               |
| 7   | 验证开销三档自动化                                                                                         | 轻档秒级返回；合并后强制重档                                  |
| 8   | 验证器回归集（缺陷注入 + 对照）                                                                            | rubric 改动后能跑出「该抓的抓到、该过的没被误杀」             |

**P1 明确不做**：写操作、多团队、Auto、员工库完整管理、任务级工作区。不是为了演示砍功能，而是先让「可信」这件事在每个环节都成立——否则之后每加一层都在放大不可信。

### 21.2 前置技术债（必须先做，且没有演示价值）

| 项                                                                               | 为什么必须先做                                                                          |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **`Tool.Capabilities` 全量声明**（只读 / 破坏性 / 幂等 / 可并发 / 最大结果字节） | 「团队内写串行、只读并行」和「验证阶段禁止写操作」都依赖它；现在只有少数工具声明了      |
| **异常原因不被吞**                                                               | `catchCause` 目前把失败折成文本；G2 要求保留结构化 `blocker.kind`，否则五种异常无法区分 |
| **状态与事件同事务**                                                             | 否则会对不上账，恢复逻辑无从判断                                                        |

### 21.3 发布门禁（不通过不发版）

| 门禁                | 判据                                                            |
| ------------------- | --------------------------------------------------------------- |
| G1 可复验           | 抽样 20 条 `pass`，全部能展开到快照 + 验证器版本 + 实测值       |
| G2 终态覆盖         | 五种异常逐项注入，全部落到预定义终态，无「卡住」                |
| G3 崩溃恢复         | 工具执行中途强制终止，重启后 `unknown` 项被正确列出且不自动重跑 |
| G4 预算             | 并发压测 10 轮，`reserved + settled` 从未超过 cap               |
| 误判通过率          | 抽样 10–20% 人工复核；超过阈值（初定 10%）不允许发布            |
| 验证器回归          | 缺陷注入集召回率 ≥ 90%，对照组误杀率 ≤ 5%                       |
| `unverified` 不折叠 | 代码审查：任何汇总路径都不得把 `unverified` 计入 `pass`         |

**实现（2026-10-30）：** `bun run script/release-gate.ts`（`gate:release`）。G1–G5、G7 由
`test/team/release-gate.test.ts` 真的跑一遍再汇总，任何一条没有执行记录都按失败处理
（「没跑到」不是「通过了」；默认 reporter 只打印失败项，所以用 JUnit 输出逐用例判读）。
判定逻辑在 `src/team/release-gate.ts`，全是纯函数：

| 门禁 | 判定方式                                                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1   | `auditPassEvidence`：每条 `pass` 必须有非空且不为 `unknown` 的快照、非 `none` 的验证器版本、非空实测值                                              |
| G2   | `auditAnomaly`：五种异常各注入一次，必须落到 `failed/partial`（格式/超时/权限）、`needs_review`（崩溃）、`cancelled`（取消）；留在 `running` 判失败 |
| G3   | `auditRecovery`：`markUnknown` 必须真的标记到、`needsReview` 必须列出、同键重放必须被拦住                                                           |
| G4   | `auditBudget`：10 轮 8 路并发预占 + 半结算半释放，`committed` 每个采样点都不得越过 cap                                                              |
| G5   | `auditVerifier`：直接跑 `verifier.ts` 的缺陷注入集，阈值固定在被测模块之外                                                                          |
| G6   | **不自动化**：`--sample` 按 20% 确定性抽样并生成复核模板，`reviewed: 0` 一律判失败                                                                  |
| G7   | `auditNoFold`：把 4 种结论的 341 种组合全部喂进 `summarize`，逐条核对计数与判定                                                                     |

G6 是唯一保留人工的一条：判定「这条 `pass` 是不是假的」本身需要人，脚本只负责抽样与核对阈值。
**没有复核记录 = 没复核 = 不通过**，这条刻意不做「缺省放行」——那正是 §21.4 第 4 条警告的失效方式。

### 21.4 最可能的失败方式（提前写下来）

1. **把 P1 做成 demo 而不是门禁**：一旦为了「看起来能用」把 `unverified` 折成通过，两条要求（生产级 + 特色）同时失效。
2. **验证器没人验**：rubric 一松，`pass` 就是假的，且没人会察觉。靠 §19.3 的回归集兜住。
3. **过早 Auto**：编排规模越大，不可信的代价越高。P4 之前不碰。
4. **误判通过率靠自评**：必须人工抽样，不能由模型自己判断「我通过了吗」。
5. **预算只做事后统计**：看起来有数字，实际上拦不住并发超支。
6. **把「多代理」当卖点**：用户一对照 CC 就会发现并没有独特性，反而暴露其他短板。

### 21.5 与目标的对应关系

| 你的要求         | 本方案的回答                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| 生产级可用       | G1–G6 六个可判定门禁 + §21.3 发布门禁；可靠性属于 P1，不是后续打磨                                     |
| 真正做成特色优势 | 卖点落在「可复验交付、成本可控、可本地审计、组织可复用」；由 §17 的 A/B/C 对照实验证明，而不是文档宣称 |

### 22.1 示例 brief

    {
      "id": "AC-1",

      "expected": "四个维度均有结论段落；允许「未发现问题」，但必须说明查了什么",

}

### 22.2 示例 report 与验证结果

成员报告（只是声明）：

```json
{
  "taskID": "task_ab12",
  "claim": "done",
  "summary": "四个维度均已检查，发现 4 处验证缺失",
  "assertions": [
    { "criterion": "AC-1", "basis": "四段结论 + 局限说明，见 review.md#scope", "artifacts": ["review.md"] },
    { "criterion": "AC-2", "basis": "4 条，均含 path:line 与复现步骤", "artifacts": ["review.md#findings"] }
  ],
  "artifacts": ["review.md"]
}
```

验证环节写入的记录（决定最终状态）：

```json
{
  "acceptanceID": "AC-2",
  "attempt": 1,
  "snapshotID": "tree:9f3c1a…+dirty:2f",
  "verifierVersion": "rubric@1",
  "outcome": "pass",
  "measured": "4/4 条含 path:line；3/4 条含可执行复现步骤",
  "evidenceRef": "evidence/ev_7f21.json"
}
```

注意：`measured` 里如实写出「3/4」，是否算通过由 `expected` 与 rubric 阈值决定，而不是由成员声明决定。

**与设计不一致（以代码为准，并说明取舍）**

1. **合并阶段重验的是全部验收项，而不只是全局项。** 设计原文只说「合并后的全局验收永远是重档」。实现时发现：只要最终快照与团队验证时的快照不同，团队证据就会全部变成 `stale`，此时只验全局项会永远无法 `done`。因此合并阶段对所有验收项在最终快照上重跑一次，代价是验证开销上升，换来的是结论可信。若日后要省成本，正确做法是让各团队在**同一 worktree 快照**上验证后再合并，而不是省掉重验。
2. **验证器出错记为 `unverified`，不是 `fail`。** `verification.record` 接受 `unverified` 作为落库结论，`verifier-error` 作为该记录的 `verifier_version`，便于在 UI 上把「产品没做到」与「验证器坏了」分开。
3. **`phase` 只做展示。** 调度器所有判断都读 `state` 与 `team_run_team.phase`（团队阶段），运行级 `phase` 不参与任何分支。

**重放语义（与设计一致，但把原因写死在这里）：**

- 上次 `succeeded` / `failed` → **不重跑**，把「已执行过、键是什么、结论是什么」原样告诉模型；

| `test/team/worktree.test.ts`        | 真实临时仓库：创建 → 提交一致 → worktree 内写入不进用户 `git status` → 删除连分支一起清          |

三条边界，代码与文档保持一致：

1. **建不成不算失败，但要留下原因。** 非 git 仓库、空仓库都返回 `skipped` 并写事件 ——
   静默降级成「在工作区里跑」才会让证据失去意义。
2. **worktree 不隔离进程与外设，也不替代单写者。** 它共享仓库对象，只解决「看到哪份代码」。
3. **worktree 不隔离进程与外设，也不替代单写者。** 它共享仓库对象，只解决「看到哪份代码」。

**串行集成与合并后全局验收（2026-10-30 追加，§10.2）**

团队各自的 `pass` 不等于可交付：只有合到一起还成立，才算做成。所以运行在团队全部交付后多走一步：

| 文件                             | 内容                                                                                                  |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `src/team/integration.ts`        | 从**分岔点**建集成分支 `novaway/integrate/<run>`，按团队顺序 `--no-ff` 逐个合并；冲突即停并 `--abort` |
| `orchestrator.ts` 的 `integrate` | 集成结果决定终态：`conflict` / `failed` 一律不能落进 `done`，最多 `partial`；事件记 `integration.*`   |
| `handlers/run.ts` 的快照切换     | 集成成功后 `snapshot()` 改读集成 worktree 的 `HEAD`，合并重验落在合并后的代码上                       |
| `verifyMerged`                   | 全局验收（不归属团队）在合并快照上单独验证 —— 此前没有接线，会一律记 `unverified`                     |

四条语义写死：

1. **集成不进用户分支。** 合进用户的分支是用户的动作；运行只回答「合到一起还成立吗」。
2. **冲突不自动解。** 自动解冲突是「把代码改对」的猜测，恰恰最该被验证器盯住；冲突文件列出来交给返工或人。
3. **顺序即依赖。** 后面的团队是基于「前面的都成立」才验证的，遇到冲突就停，不把冲突扩散到更多文件。
4. **集成失败仍保留证据。** 团队快照上的结论留在历史记录里，但不再充当最终结论。

**工作区清理（2026-10-30 追加，§21.1 第 5 项）**

`DELETE /run/:runID/worktrees` 删除某次运行的团队 worktree 与集成 worktree（连同分支），
只在终态可用 —— 运行中删工作区等于把成员脚下的地板抽走。集成分支是这次运行的可交付物，
所以**不做跑完自动删**：运行页在终态显示「清理工作区」，由用户先合并或明确放弃后再点。

**Mission 持久目标（2026-10-30 追加，§3.2 / §16 P2）**

在 Mission 之前，每次运行各建一份 worktree、各自从当时的 `HEAD` 起集成 —— 「长期做一件事」
在数据里没有落点：这次没做好，下次从零开始。现在多了一层薄的目标：

| 文件                               | 内容                                                                                                           |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 迁移 `20261030000000_team_mission` | `team_mission`（id / number / goal / status / base_sha / worktree / branch）+ `team_run.mission_id`            |
| `src/team/mission.ts`              | 建目标（全局单调编号、冻结 `baseSHA`）、`prepare()`（准备或复用工作区，目录被删按同一 `baseSHA` 重建）、改状态 |
| `src/team/worktree.ts`             | `createMission()`：分支 `novaway/mission/<id>`，目录在全局数据目录，不随运行清理                               |
| `src/team/integration.ts`          | `integrateInto()`：合并进目标工作区当前分支；工作区不干净直接拒绝，冲突 `--abort`                              |
| `groups/mission.ts` + handler      | `GET/POST /team/mission`、`GET/PATCH /team/mission/:id`；`M-xxx` 只在视图里出现                                |
| `handlers/run.ts`                  | 建运行时校验目标的目录/状态/占用，先 `prepare()` 再建运行；团队 worktree 从目标 HEAD 起分支                    |
| 运行页                             | 发起表单可选「持久目标」（含新建）；列表与详情显示 `M-xxx`，悬停给出目标描述                                   |

四条语义写死：

1. **编号不复用。** 全局单调、唯一索引兜底；删除/停用都不会把号码还给下一个目标 ——
   否则「M-003 那次到底改了什么」在历史记录里会指错人。
2. **状态互不推导。** `mission.status` 只能由用户（或成员）显式改；运行成功不会自动完成目标，
   目标标 `done` 也不会停掉正在跑的运行（§3.2 第 2 条）。
3. **一个目标同时只跑一次运行。** 同一份工作区、同一个分支被两个运行同时改，证据会互相污染；
   建运行时就拒绝，而不是在集成时才发现。
4. **目标工作区不随运行清理。** `DELETE /run/:runID/worktrees` 只删本次运行自己的东西；
   属于目标的工作区会被跳过并说明原因。

两处与设计原文的偏差，以代码为准：

1. **准备时机提前到「建运行」而不是「第一次批准后」。** 团队 worktree 在计划阶段就要从某个
   提交起分支，等批准再准备会让「团队看到哪份代码」晚一步才确定。代价是：只建计划、从不执行
   的运行也会留下一个目标工作区（空分支，不影响用户仓库）。
2. **合并动作合并的是目标分支。** 运行页的「合并到当前分支」对目标运行指向 `novaway/mission/<id>`，
   包含该目标历次运行的累计结果，而不只是这一次；累计差异按 `baseSHA → 目标 HEAD` 计算。

**显式合并动作（2026-10-30 追加，§3.2 / §16 P2）**

「跑完」「已验证交付」「已合并」是三件事，此前只实现了前两件：集成分支一直停在
`novaway/integrate/<run>` 上，没有任何路径把它带进用户的分支。现在这一步由用户点一下完成：

| 文件                            | 内容                                                                                             |
| ------------------------------- | ------------------------------------------------------------------------------------------------ |
| `src/team/integration.ts`       | `mergeInto()`：`git status` 干净 → `git merge --no-ff`；冲突列出文件并 `--abort`，不留半成品     |
| `groups/run.ts`                 | `POST /run/:runID/merge`（`run.merge`），返回 `RunMergeResult`                                   |
| `handlers/run.ts`               | 非终态 400；没有 `integration.merged` 事件则拒绝；成功写 `merge.settled`，拒绝写 `merge.refused` |
| 运行页                          | 终态且还有 worktree 时显示「合并到当前分支」，成功后用一行提示说明合进了哪个分支、哪个提交       |
| `test/team/integration.test.ts` | 真实临时仓库：合并到当前分支并指认提交；工作区不干净时拒绝且不动 HEAD                            |

三条边界：

1. **拒绝不是错误。** 工作区脏、没有集成分支、冲突都以 `merged: false` + `message` 返回，
   并写 `merge.refused` 事件；用 400 会把「需要用户先处理什么」丢在通用错误里。
2. **绝不覆盖未提交改动。** 只做「干净工作区上的合并」，不 stash、不 `reset --hard`。
3. **合并与验收解耦。** `partial`（部分验收未过）仍然可合并 —— 是否接受这份代码是用户的判断；
   但 `failed` / `exceeded` / `cancelled` 没有可交付物，接口不提供这条路。

**用量归属落到运行快照（2026-10-30 追加，§10.3）**

账本以前只回答「这次运行花了多少」。现在运行结束时会按三个维度写一份归属快照：

**团队改动落成提交（2026-10-30 追加，§10.1 / §16 P2）**

接上 Mission 之后发现一个真实的断点：`git merge` 与验证都只认**提交**，而成员是在磁盘上写文件的。
成员写完没提交时，验证对着旧 `HEAD` 得出「通过」，集成合并到的是一个没有这些改动的分支 ——
「跑完了」与「代码变了」可以同时为真。

| 文件                                 | 内容                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------ |
| `src/team/worktree.ts` 的 `commit()` | `git add -A` → 有改动才 `git commit`；作者固定为 `NovaWay Team`，`--no-verify`             |
| `orchestrator.ts` 的 `commit` 钩子   | 每队交付后、取快照**之前**调用；集成前再调用一次                                           |
| 提交失败                             | 该队记 `failed`（`reason: "commit"`），集成前失败则并入 `integrationBroken`，都不进 `done` |
| `handlers/run.ts`                    | 失败时让整次 commit 抛错并写事件；成功的提交记 `worktree.committed`（含 sha 与文件数）     |

三条边界：

1. **没有改动就不产生空提交。** 空提交会让「第几轮改了什么」变得难读；返回 `clean` 而不是成功。
2. **尊重 `.gitignore`，其余全部纳入。** 宁可提交得多，也不能漏掉成员真正写下的东西。
3. **跳过用户钩子（`--no-verify`）。** 钩子可能要求交互或直接改动工作区；团队提交只是把改动
   变成可复验的快照。质量门槛由随后的验证器负责 —— 它跑的是项目自己的测试与构建。

**Mission 累计差异（2026-10-30 追加，§3.2）**

## 24. 外部对照：Rovai-ai（2026-10 调研）

调研对象：`github.com/murray17/rovai-ai`（MIT，233★，Rust Core + Electron，MIT，3559 commits）。
它和本方案的定位几乎重合：**长期存活的 AI 员工团队 + 共享会话 + 任务分派 + 协作记忆 + 证据优先**。

结论先说：**理念层面高度重合，工程层面它比我们成熟得多；它验证了两个关键赌注，也否掉了我们流程里最危险的一环。**

### 24.1 它的三条产品宪法

| 原文立场                                                    | 对我们的意义                                  |
| ----------------------------------------------------------- | --------------------------------------------- |
| 「保留来源：每个运行结论都要说明它的权威与质量」            | 和 §6.2 三层验收同源                          |
| 「让不确定可用：unknown 与 partial 要显示覆盖率与具体解释」 | 和 §19.2「`unverified` 不可折叠」是同一条原则 |
| 「缺失字段保持 unknown，永不变成 0」                        | 比我们写得更狠：**连 Usage 都不许补零**       |

它还有一条我们没写、但值得直接抄的治理句：
「本文不证明代码已经实现这些规则；实现状态必须由代码、迁移、测试与验收共同证明。」
我们这份文档的 §23.4 就是被这句话提醒才补上的。

### 24.2 必须吸收的六条（按优先级）

#### ① 不要在内核里做「收集齐所有成员再汇总」的屏障

它曾经做过：Gather / Barrier / captured return / completion Run，**后来整套退役**，理由是：

- 收齐才唤醒一次，会把「某个成员慢」放大成「整轮卡住」；
- Core 一旦负责计数与收齐，就必然要为「谁算回复」「少一个怎么办」写规则，规则越写越厚；
- 退役后改为：普通多目标消息 + 普通回复进入 FIFO，「尽量收齐再汇总」降级为**提示词里的纪律**，而不是内核机制。

**对我们的直接约束：** §8.2 的「队长等所有成员」不能实现成内核调度器里的屏障。
本方案的实现里，这个等待发生在**队长自己的一次运行内部**（队长通过任务板分派、自己决定何时汇总），
内核只负责「派发一轮 → 收验证结果 → 决定打回或交付」。

因此新增一条硬规则，写进 §9：**内核不得出现「回复计数」「收齐判定」「完成 Run」这类对象**；
如果将来想做并发多成员，也只能是队长自己发多条消息，而不是内核替它聚合。

#### ② 用量未知就记未知，不许用预占额或估算值冒充花费

它的规则是：token / 成本只接受提供方权威回执，提供方不暴露时为 `unavailable`，**禁止估算或填零**。

我们原来的实现有这个问题：`settle(tokens: report.usage?.tokens ?? reserveTokens)`——没回报用量时，
拿预占额当成实际花费写进账本。这既是数据造假，也让「成本敢说出口」变成空话。

**已改：** `ledger.settle` 的 `tokens` 改为可选；缺省时条目进入 `unknown` 状态，
**不计入已结算**、但仍按预占额保守占住额度（防超支），UI 上单独一列「用量不明」。
账本 `Usage` 增加 `unknown` 字段，`committed = reserved + settled + unknown`。

#### ③ 把「长期目标」和「一次运行」分成两层

它的 Mission 是一个**持久目标**：有独立业务状态、稳定显示编号（`M-001`，删除后号码不复用）、
在第一次被准许执行时才准备 worktree，之后**多次 Run 复用同一个 worktree 与同一个固定 `base_sha`**，
对外展示的是从 `base_sha` 到当前内容的累计差异。

我们的 `team_run` 目前是一次性的。用户说的「团队长期做一件事、这次没做好下次继续」在数据模型里没有落点。

**建议（P2，不阻塞 P1）：** 增加一层薄薄的 `team_mission`：`id` / `number`（单调、不复用）/ `goal` /
`status` / `base_sha` / `worktree`，`team_run` 增加 `mission_id`。累计差异按 `base_sha` 计算，
而不是每次运行各算各的。员工看到的仍是内部 id；`M-xxx` 只出现在界面上，不进模型上下文。

#### ④ 「跑完」「交付完成」「合并代码」是三件事

它的原则原文：**「结束一次运行、完成一个使命、合并代码是三个独立动作。」**

我们的状态机把「团队都交付 + 全局验收通过」直接叫 `done`，容易被读成「已经合进主干」。
**建议：** `done` 只表示「本次运行产出了通过验收的交付」，另设 `merged_at` 与显式的合并动作；
UI 上把「已完成」改成「已验证交付」之类不会被误读的措辞。

#### ⑤ 把「模型看到了什么」也当成证据

它的 ContextManifest 冻结的是**实际投喂给模型的字节**：有序输入、省略项、水位、附件引用、投递回执。
这解决的是「队长为什么判错」——很多时候不是它判断力差，而是它看到的 brief 被截断了，而没人记录这件事。

我们已经在 `roster_snapshot` 里冻结了「人」，但没冻结「话」。**建议：** `team_run` 增加 `context_manifest`
（json）：这一轮队长拿到的 brief 文本、验收项版本、名册版本、被省略/截断的条目与原因。
这条与 §19.2 同源：**截断必须可见**，不能悄悄发生。

#### ⑥ 模板是「复制」，不是「绑定」

它的 Team 只是创建模板：选中即在同一事务里拷贝权威输入，**不拥有、也不同步已经存在的会话**；
编辑或删除模板不会改变已存在的实例。

这条直接支撑我们 Team 页的「总控开关 + 团队选择器」设计：开关切换、模板编辑都不能影响正在运行的一次编排。
我们已有 `roster_snapshot` 做快照，但要把规则写成不变量：**模板变动对运行中的编排零影响；运行只认快照。**

另外它把「功能开关关闭」的语义写得很细，值得照抄：

| 规则                       | 说明                                                 |
| -------------------------- | ---------------------------------------------------- |
| 默认关闭                   | 新库默认 `false`                                     |
| 关闭不删除数据             | 任务、历史关联、事件、冻结输入全部保留               |
| 关闭不停止正在跑的         | 已领取的运行继续                                     |
| 关闭给模型一个可执行的话术 | 结构化错误 `feature_disabled` + 「改用普通消息继续」 |

我们团队总控开关关闭时，也要给出「继续用普通对话」的明确指引，而不是一个神秘的失败。

### 24.3 我们该拒绝照抄的四条

| 它做错的（对我们而言）           | 理由                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 完全不设协作预算                 | 它的用户是自己装 CLI 的开发者；我们的用户为结果付费，需要硬上限。**保留** §7 的预占账本，只吸收「未知不补零」 |
| 文档体系（40+ 契约、逐版本决策） | 3.5k commit 的产物，照抄会变成仪式。我们只取两条：**契约要有版本**、**文档不证明实现**                        |
| 词表（Camp / 队员 / Gather）     | 术语迁移成本极高，且会污染现有代码                                                                            |
| 常驻进程池、ACP 适配、渠道集成   | 属于它的宿主层，与团队编排正交                                                                                |

### 24.4 它还提醒我们注意的三个坑

1. **成员投影要小。** 它给同伴只投影「ID + 名字 + 团队角色 + 专业职责」，明确不投影性格、忙碌状态、
   可用性，且**已冻结的一次运行不会因为名册变化被原位打补丁**。我们的审计快照可以很全，但**投进提示词的必须很少**；
   审计快照 ≠ 模型上下文。
2. **任务注入要按「自己的」截断。** 它只注入当前成员自己负责的非终态任务，按稳定顺序与预算截断，
   并区分「真的是空」与「被上限截掉」——后者要记省略数量，不能泄露被排除的 ID。我们的任务板注入迟早会遇到这个问题。
3. **寻址失败要整体失败。** 它规定：任何一个目标解析不到当前成员，**整条发送失败**，返回完整的问题集合，
   不做部分扇出，也不静默降级。我们的派发同理：快照里的员工已被删除时，整轮派发失败并列出是哪个，而不是跳过。

### 24.5 已吸收进正文的条目（不只是「参考了」）

吸收不是加一行「参考了某某」就算数，必须落进正文的可执行约束里。逐条对应：

| ① 不做收齐式屏障           | §9                             | 「内核里不允许出现屏障类对象」+ 判断标准（有「数量」和「等」就不该在内核） |

### 24.6 三个问题的结论

| 问题                             | 结论                                                                                                                                      |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `Mission` 放 P2 还是 P3          | **放 P2。** 加得越晚迁移成本越高；而且它决定「跨运行累计差异」能不能成立，直接影响用户对「团队长期记忆」的预期。                          |
| `context_manifest` 记多细        | **只记 brief、验收 id + 版本、打回意见、省略项。** 验收项全文不存 —— 全文已在 `team_acceptance`，重复存只会让表变胖。                     |
| 总控开关关闭时，在跑的编排怎么办 | **继续跑完，但不接受新派发。** 开关的语义是「还能不能开始新的团队协作」，不是「立刻中止正在做的事」；中止是取消动作，更重、必须显式发起。 |
